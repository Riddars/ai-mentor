# Продолжение работы: поиск проблем всего проекта

Это точка входа для агента, который не видел обсуждение. Общаться с пользователем на русском. Реализация поиска выполнена, влита в main и развёрнута на ИТМО 2026-11-23 по поручению пользователя (код e729c80, PROJECT_AUDIT_ENABLED=true). Живую платную приёмку пользователь выполняет вручную.

## Что нужно получить

После первого подключения репозитория пользователь получает два независимых результата: карту проекта и затем подтверждённые замечания о проблемах уже существующего кода. Проверка PR продолжает работать по прежним правилам.

Карта строится первой. Только после её успешного сохранения автоматически запускается отдельный поиск ошибок по тем же выбранным файлам того же коммита. До поиска модель должна видеть уже существующие замечания и сведения о требованиях, чтобы не формулировать их заново. Поиск без инструментов: названия файлов и содержимое плюс отдельный промпт. При большом объёме используются существующие измерение контекста и разбиение. Нужна также кнопка «Проверить проект на ошибки» для повторного поиска без перестроения карты.

**Прочитай весь согласованный [подробный план](docs/документация/план%20—%20поиск%20проблем%20проекта.md) до начала реализации.** Он проверен субагентом-судьёй, его обязательные поправки включены. Изложенные в нём ограничения являются частью задачи.

## Исходное состояние и решения

- Базовый коммит реализации до этой документации: `e2402a9` в `main`, репозиторий `https://github.com/Riddars/ai-mentor.git`. На другом устройстве сначала проверить реальное состояние: после этой записи могли появиться новые коммиты.
- Уже реализованы карта по всему отфильтрованному содержимому без tools, разбиение больших запросов, сохранение частей в SQLite, контекстный разбор PR с полным diff, восстановление и учёт расходов.
- В режиме `INITIAL_OVERVIEW_MODE=parts` первоначальный и ручной полный обзор строят карту. Этот режим запрещает ненулевой `findings`: замена одного промпта не добавит поиск ошибок. Старые другие режимы обзора не подменять новым поиском незаметно.
- Текущая конфигурация обсуждавшейся системы: `INITIAL_OVERVIEW_MODE=parts`, `REVIEW_MODE=context`; Selectel основной, Provod резервный. Не менять провайдеров, лимиты и режим PR попутно. Актуальные значения проверить по `.env.local.example` и защищённым настройкам окружения, не выводя секреты.
- Полный отфильтрованный исходный MedChemJudge уже успешно давал карту с первой попытки. Это свидетельство только для построения карты, не доказательство качества ещё не реализованного поиска проблем.
- Первая версия нового поиска **только добавляет подтверждённые новые замечания**. Не закрывает и не переоткрывает старые. Требования берутся из существующих материалов, отдельную систему требований не изобретать.
- Сам поиск ничего не публикует в GitHub. Последующие PR могут учитывать и отображать эти project-замечания обычным способом. Постоянная скрытость от студентов не входит в задачу.

## Порядок реализации и контрольные точки

1. **Контекст.** Получение закреплённых исходников, карта, полная история замечаний/сведения о требованиях; контекст до поиска, измерение и большие истории без молчаливого усечения. Проверки: один SHA, исключения, notebook, project/branch scope, история перед поиском.
2. **Поиск.** Отдельный no-tools pipeline с текущим форматом кандидатов, разбиением и сохранением частей. Проверки: один запрос для малого проекта, покрытие большого, восстановление и format repair/fallback. Модель в тестах подставная.
3. **Принятие результатов.** Проверка доказательств, дедупликация, полная сверка истории и новые project-находки без изменения старых статусов. Повторная сверка при параллельных изменениях, отчёт об устаревшем SHA без применения его кандидатов. Проверки: дубли, снятые/закрытые/ожидающие, возможная регрессия, сбой проверки, транзакционные повторы.
4. **Очередь и интерфейс.** Атомарный автоматический запуск ровно один раз после карты, ручная кнопка, новый job kind, сохранение причин и бюджета, все ветки worker, отсутствие GitHub-публикаций поиска. Проверки: перезапуск между стадиями, гонки, права доступа, актуальность карты, очистка проекта.
5. **Регрессия и включение.** Полный набор офлайн-проверок, проверка сборки, затем ограниченный платный сценарий после предупреждения пользователя. Сначала флаг выключен по умолчанию; не запускать поиск массово на старых проектах.

По уточнению пользователя в этом чате: выполнить всю реализацию и офлайн-тесты, затем один раз вызвать субагента-судью для итоговой проверки всего изменения. Исправить существенные замечания и записать итог проверки. Судья плана уже дал PASS; это не разрешение объявлять ещё не выполненную реализацию проверенной.

## Начало работы на другом устройстве

В каталоге репозитория:

```powershell
git status --short
git branch --show-current
git remote -v
```

Если есть чужие незакоммиченные изменения — сохранить их; не делать reset/clean и не перезаписывать. После проверки чистоты получить `main` обычным `git pull --ff-only origin main`, находясь на `main`. Для реализации создать отдельную ветку:

```powershell
git switch -c codex/project-audit
node --version
npm ci
```

Предпочтительно Node.js 24; нужен рабочий встроенный `node:sqlite`. Следовать актуальному lock-файлу. Секретов с другого устройства в Git нет и быть не должно. Для офлайн-тестов реальные LLM-ключи не нужны; тесты должны использовать временную БД (`DATABASE_PATH`) и заглушки транспорта, не рабочую базу.

Сначала прочитать код из таблицы и ближайшие selftests; уточнить реализацию в пределах утверждённых решений, затем выполнять этапы выше. Не начинать с платного запуска или деплоя.

## Проверки

Текущие команды офлайн-регрессии (проверить актуальность `package.json` перед запуском):

```powershell
npx tsc --noEmit
npm run test:context
npm run test:pr-context
npm run test:context-recovery
npm run test:reviews
npm run test:review-migration
npm run test:reliability
npm run test:inactivity
npm run lint
npm run build
```

Добавить отдельные selftests для нового поиска, например `scripts/project-audit-selftest.mts` и `scripts/project-audit-queue-selftest.mts`, и команду package.json. Имена можно уточнить. Подставной транспорт должен позволять проверить число/содержимое запросов и отсутствие tools. Перехватить GitHub-транспорт и доказать ноль публикаций поиска, включая обработку ошибок и повторов.

Готовность: чистое подключение ставит карту, успешная карта один раз ставит поиск; новые подтверждённые недублирующиеся замечания появляются в панели с правильным SHA и scope; старые статусы сохранены; после сбоя не повторяется уже завершённый поиск; неудача/ограничение не показаны как «проблем нет»; PR-регрессия проходит. Поиск может честно не завершиться при внешнем сбое/исчерпании бюджета — требуется понятная причина и предусмотренное восстановление, а не обещание отсутствия любых сбоев.

## Платный тест и сервер

Пользователь просил минимизировать платные проверки и заранее коротко объяснять: что проверяется, что считается успехом и неуспехом. Для данного продолжения отдельный платный запуск ещё не согласован: сначала описать его и получить разрешение, не считать этот документ разрешением на расходы. Офлайн-тесты не равны реальному тесту на модели.

Проблемный репозиторий: приватный `ai-chem-curator/MedChemJudge`. Оригинал в панели: `https://curator.aicidlab.itmo.ru/projects/6`. Не удалять его, не очищать историю и не запускать его платный обзор самовольно. Не создавать публичных копий или публичных артефактов с кодом/отчётами. Отчёт прошлого теста, рабочая БД, `.env.local` и ключи в Git не добавляются.

На этом этапе не деплоить, не менять сервер, не создавать тестовые репозитории и не сливать реализацию в main без отдельного поручения. Серверный runbook для будущего согласованного этапа: `docs/документация/сервер центра.md` (общий хост, не использовать произвольную standalone/systemd-инструкцию).
