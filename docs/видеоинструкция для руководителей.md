# Видеоинструкция для руководителей проектов

Статус: архивный сценарий для **руководителей проектов** (роль `supervisor` в сервисе). Он описывает старый порядок с обязательным ruleset. Перед новой съёмкой сценарий нужно переписать под единый рекомендательный режим; раздел «Управление» больше не предлагает импорт ruleset. Демонстрация проведена на отдельном публичном [учебном репозитории](https://github.com/ai-chem-curator/curator-video-demo) без данных студентов. Локальный видеомонтаж хранится в `video-production/` и не публикуется в GitHub.

Голос: [«Молодой Аналитик» · 33azawx2](https://beta.fish.audio/m/868377a7b08f4c0d9acf8c9f059571aa/), `reference_id` — `868377a7b08f4c0d9acf8c9f059571aa`. Озвучка создана отдельными сценами. Скрипт читает API-ключ только из переменной окружения и не сохраняет его в проекте.

## Подготовка съёмки

1. Войти в панель под демонстрационной учётной записью **руководителя проекта**, а в GitHub — под учётной записью руководителя с правами настройки репозитория. Не использовать панель руководителя центра. Скрыть уведомления, почту, список вкладок и личные данные.
2. Создать для ролика отдельный репозиторий `curator-video-demo` из рабочего шаблона в организации проектов. Если имя занято, добавить короткий суффикс. Не подключать реальный студенческий проект.
3. Подготовить небольшой учебный PR в этом репозитории **от учётной записи руководителя**, с содержательным изменением и заполненным описанием: что сделано, зачем, как проверялось. Для демонстрации PR не нужен отдельный студент: руководитель имеет доступ к созданному им репозиторию. В ролике явно обозначить этот PR как учебный пример. Замечание куратора заранее не обещать: модель может не найти проблему.
4. Перед съёмкой проверить, что у GitHub App есть право создавать issue «Обзор проекта (AI Curator)». Если issue ещё не публикуется, эту сцену снять по существующему проекту или исключить из ролика без заявления, что issue создано автоматически.
5. Не приглашать студента в демонстрационный репозиторий. Шаг приглашения объяснить устно и показать ссылку в панели без нажатия `Add people`.
6. Если запись ведётся одним дублем, остановки на ожидание обзора и PR-разбора вырезать при монтаже. Показать короткую подпись «Ожидаем завершения проверки».

## Покадровый сценарий

### 1. Зачем сервис — 0:00–0:25

**Экран:** главная панель и пример страницы проекта. Без прокрутки мелких деталей.

**Диктор:** «Это ИИ-куратор исследовательских проектов. Он проверяет изменения студентов в GitHub, сохраняет найденные замечания и помогает руководителю понять, что обсудить со студентом. Выводы куратора можно проверить и оспорить; решение остаётся за руководителем и студентом».

**Подпись:** «PR студентов → проверка → замечания в панели».

### 2. Создаём репозиторий — 0:25–1:05

**Клики:** панель → «Управление» → «Новый проект» → «Создайте репозиторий из шаблона». В GitHub ввести имя, оставить публичную видимость, нажать `Create repository`.

**Диктор:** «Открываем раздел “Управление”. Ссылка ведёт к шаблону проекта в GitHub. Вводим имя репозитория и создаём его публичным. Публичная видимость нужна для обязательной проверки в выбранной конфигурации GitHub».

**Подпись:** «Репозиторий создаётся в организации проектов».

### 3. Подключаем проект — 1:05–1:35

**Клики:** вернуться в «Управление», заполнить форму подключения новым репозиторием, открыть страницу проекта.

**Диктор:** «Возвращаемся в панель и подключаем созданный репозиторий. Теперь куратор знает, какой проект нужно проверять. На странице проекта видим следующие шаги подготовки».

**Подпись:** «Сначала подключение в панели, затем правила GitHub».

### 4. Вручную импортируем ruleset — 1:35–2:25

**Клики крупным планом:** в блоке «Подготовка репозитория» нажать **«Скачайте файл настройки»**. Показать скачанный `ai-curator-ruleset.json` в загрузках браузера. Нажать **«настройки репозитория»**. На GitHub нажать `New ruleset` → `Import a ruleset`, выбрать скачанный JSON в системном окне, подтвердить выбор, прокрутить страницу вниз и нажать `Create`. Вернуться в панель и нажать «Обновить». Дождаться отметки «Готово» у шага «Защитите основную ветку».

**Диктор:** «Файл правила скачиваем прямо из панели. Затем открываем настройки этого репозитория в GitHub. Нажимаем “New ruleset”, затем “Import a ruleset”, выбираем скачанный файл на компьютере и внизу страницы нажимаем “Create”. Возвращаемся в панель и обновляем страницу: здесь должно появиться подтверждение, что изменения проходят через pull request с проверкой куратора».

**Подписи:** «1. Скачать JSON» → «2. Импортировать в GitHub» → «3. Нажать Create» → «4. Проверить “Готово”».

**Проверка перед монтажом:** если отметка не появилась, проверить импортированное правило и источник обязательной проверки `AI Curator`; не скрывать ошибку монтажом.

### 5. Доступ студента — 2:25–2:40

**Экран:** в блоке «Подготовка репозитория» показать шаг «Пригласите студентов» и ссылку «список участников репозитория». Никого не добавлять.

**Диктор:** «Когда будете подключать настоящий проект, здесь же откройте список участников GitHub и пригласите своих студентов с ролью Write. После принятия приглашения они появятся в панели. В учебный репозиторий сейчас никого не добавляем».

### 6. Открываем PR и смотрим ответ — 2:40–3:45

**Клики:** под учётной записью руководителя показать подготовленную учебную ветку и открытие PR в `main`, заполнить описание по шаблону, нажать `Create pull request`. Показать проверку `AI Curator` в процессе; затем монтажный переход к завершённой проверке и комментарию.

**Диктор:** «Чтобы показать результат, я открываю учебный pull request сам. В реальном проекте это делает студент: работает в своей ветке и описывает, что сделал и как проверил результат. Куратор запускает разбор и публикует комментарий. Здесь видны его замечания, основания и предложение, что исправить».

**Подпись на монтажном переходе:** «Разбор может занять несколько минут».

### 7. Что делать с замечанием — 3:55–4:25

**Клики:** показать обычное поле комментария в PR. При необходимости написать учебный ответ от имени руководителя и показать результат сверки, явно обозначив его как демонстрацию механики комментария. При наличии нового коммита показать повторный разбор.

**Диктор:** «В работе студент может исправить проблему новым коммитом или объяснить своё решение обычным комментарием в PR. После коммита куратор снова проверит изменения. Для объяснения нужно общее поле комментария: ответы в обсуждении отдельной строки кода пока не обрабатываются».

### 8. Работа руководителя в панели — 4:25–5:10

**Клики:** главная → проект → открытое замечание → карточка с основанием, ответом студента и историей. При необходимости показать раздел «Решение руководителя», но не менять статус демонстрационного замечания без подготовленной причины.

**Диктор:** «Руководитель видит открытые замечания по своим проектам, историю разборов и ответы студентов. В карточке можно проверить, на чём основан вывод. Если куратор ошибся, руководитель может закрыть замечание со своей причиной; при необходимости закрытое замечание можно вернуть в открытые».

### 9. Обзор проекта и завершение — 5:10–5:40

**Клики:** если issue доступно, открыть GitHub issue «Обзор проекта (AI Curator)» и показать его заголовок и несколько строк. Завершить на панели с адресом сервиса.

**Диктор:** «В issue “Обзор проекта” куратор сохраняет заметки о том, как он понял репозиторий. Это дополнение к проверке pull request. Для начала работы откройте curator.aicidlab.itmo.ru, создайте проект из шаблона, подключите его и проверьте оба шага подготовки».

**Подпись:** «curator.aicidlab.itmo.ru».

## Монтаж и озвучка

- Снимать реальные клики; не заменять импорт JSON схемой или слайдом. Участок с системным выбором файла оставить в кадре. Во всех кадрах панели должна быть роль руководителя проекта, без разделов управления учётными записями и расходом центра.
- Накладывать подписи только на важные действия и ожидание. В субтитрах писать `GitHub`, `PR`, `ruleset`, `AI Curator` единообразно.
- Генерировать голос по сценам, без эмоциональных тегов. Проверить ударения и произношение технических слов на короткой пробе. Если `ruleset` звучит странно, в речи заменить на «правило репозитория», оставив `ruleset` в подписи.
- Не показывать пароли, API-ключи, токены, личные вкладки и реальные студенческие данные.
