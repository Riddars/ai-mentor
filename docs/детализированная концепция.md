# Детализированная концепция работы системы

## 1. Общая схема

ИИ-куратор представляет собой единое веб-приложение, размещённое на сервере университета. Оно выполняет три основные функции:

1. Проверяет изменения, которые студенты вносят через pull request.
2. Раз в месяц анализирует состояние исследовательского проекта целиком.
3. Показывает научному руководителю общую картину по всем проектам.

Сервис получает события из GitHub, собирает необходимый контекст, запускает автоматические проверки, обращается к языковой модели и сохраняет результаты. Через это же приложение руководитель открывает панель наблюдения за проектами.

Содержательный анализ выполняется моделью Claude через API Anthropic. Управление расписанием, память проектов, сбор статистики, связь с GitHub и интерфейс руководителя реализуются внутри приложения.

## 2. Организация работы в GitHub

Для проектов создаётся единая GitHub-организация. Каждый исследовательский проект размещается в отдельном репозитории, созданном из общего шаблона.

Шаблон определяет:

- структуру каталогов для кода, данных, экспериментов и документации;
- заготовку README;
- форму описания pull request;
- файл с описанием исследования;
- базовые автоматические проверки.

Студент поддерживает описание исследования в актуальном состоянии. В нём фиксируются цель проекта, используемые данные и методы, выполненная работа, текущий этап и ближайшие планы. Единая структура помогает студентам организовывать работу, а системе даёт предсказуемую точку входа для анализа.

Студенты получают права, необходимые для работы с кодом и pull request. Административные права остаются у ответственных сотрудников центра, чтобы правила защиты основной ветки нельзя было изменить или отключить.

## 3. Проверка pull request

Все изменения в основную ветку вносятся через pull request. После его открытия начинается следующий процесс:

1. GitHub отправляет сервису событие об открытии или обновлении pull request.
2. Сервис запускает обязательную проверку AI Curator.
3. GitHub временно блокирует слияние.
4. Сервис получает изменения, описание проекта, связанные файлы и историю предыдущих замечаний.
5. Выполняются автоматические и интеллектуальные проверки.
6. Результат публикуется в pull request.
7. Проверка получает успешный статус, после чего слияние становится доступным.

Проверку создаёт зарегистрированное GitHub App центра. В настройках защищённой ветки приложение указывается как доверенный источник статуса. GitHub позволяет принимать обязательную проверку только от выбранного приложения, поэтому участник проекта не сможет самостоятельно подменить её результат. Такой механизм предусмотрен [правилами обязательных проверок GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

Если сервис недоступен и проверка не была выставлена, pull request остаётся заблокированным. Это поведение выбрано намеренно: отсутствие ответа не должно превращаться в разрешение. На такой случай предусматривается ручное снятие блокировки ответственным сотрудником центра.

Условием слияния является завершение анализа, а окончательное решение принимает студент. Он может исправить замечания, объяснить выбранное решение или выполнить слияние без изменений.

Каждый новый коммит в pull request запускает проверку повторно. При этом система не изучает проект заново: она разбирает только новые изменения, опираясь на сохранённый контекст и результаты предыдущего анализа этого же pull request. Это сокращает и время ответа, и расходы на обращения к модели.

Правила защиты применяются только к репозиториям студенческих проектов. При создании нового репозитория сервис автоматически устанавливает необходимую конфигурацию.

## 4. Анализ изменений

Для анализа сервис собирает четыре группы данных:

- изменения из pull request;
- актуальное описание исследования;
- связанные с изменениями файлы;
- внутреннюю память проекта.

Языковая модель анализирует изменения в контексте исследовательской задачи. В итоговый ответ включаются находки, которые способны повлиять на результаты или выводы работы. Например:

- утечка данных между обучающей и тестовой выборками;
- некорректное разделение данных;
- дубликаты в датасете;
- неподходящая метрика;
- невоспроизводимость эксперимента;
- расхождение между описанием проекта и фактической реализацией;
- ошибки в коде, которые изменяют результат без явного сбоя программы.

Каждая находка получает категорию, уровень серьёзности и оценку уверенности модели. Перед публикацией выполняется дополнительная проверка: модель должна указать конкретный фрагмент кода или другой материал, подтверждающий вывод. Находки без достаточного подтверждения исключаются из ответа.

Затем результат сверяется с памятью проекта. Если аналогичное замечание уже рассматривалось и было снято после объяснения студента, система учитывает это решение и не создаёт его повторно без новых оснований.

Ответ в pull request содержит:

1. Краткое описание проверенных изменений.
2. Список существенных находок.
3. Объяснение возможного влияния каждой находки.
4. Ссылки на соответствующие строки или файлы.
5. Рекомендации по проверке или исправлению.

Если существенных проблем не найдено, сервис публикует короткое подтверждение завершённой проверки.

## 5. Ежемесячный обзор проекта

Раз в месяц сервис анализирует проект целиком. В отличие от проверки pull request, этот обзор оценивает не только качество реализации, но и направление исследования.

Для обзора используются:

- актуальное описание проекта;
- изменения за последний месяц;
- история pull request;
- открытые и закрытые замечания;
- активность участников;
- код, данные и результаты экспериментов;
- связанные научные публикации.

Система оценивает прогресс проекта, соответствие фактической работы заявленному плану, целостность методики и состояние ранее обнаруженных проблем. Дополнительно выполняется поиск научных публикаций по теме проекта. Найденные работы сопровождаются ссылками и кратким объяснением их связи с исследованием.

Результат публикуется в репозитории как отдельный GitHub Issue с меткой ежемесячного обзора. Он содержит:

1. Что изменилось за месяц.
2. Какие прошлые проблемы были устранены.
3. Какие технические и методические риски остаются.
4. Какие изменения в плане или подходе заметила система.
5. Какие публикации и альтернативные методы стоит изучить.
6. Какие действия рекомендуется выполнить до следующего обзора.

Регламент предусматривает один содержательный ответ студента. В нём можно уточнить контекст, объяснить принятое решение или сообщить о планируемом исправлении. Ответ сохраняется в памяти системы и учитывается при следующем анализе. После обработки ответа Issue закрывается.

Описание проекта создаётся в начале исследования и обновляется студентом по ходу работы, обязательно — перед очередным ежемесячным обзором. История изменений этого файла позволяет системе видеть, как менялись цель, план и понимание задачи.

## 6. Память проекта

Внутренняя память хранится на сервере приложения. Репозиторий содержит только материалы самого проекта, комментарии к pull request и опубликованные обзоры.

Структурированная информация размещается в базе данных:

- проекты и участники;
- события GitHub;
- история проверок;
- найденные проблемы;
- серьёзность и уверенность;
- ответы студентов;
- текущие статусы;
- показатели активности.

Объёмные тексты, фрагменты кода и сформированные отчёты могут храниться отдельными файлами. База данных содержит ссылки на эти материалы.

Для первой версии используется SQLite.

Для каждой находки хранится история изменений состояния:

| Состояние | Значение |
| :---- | :---- |
| Открыта | Проблема обнаружена и остаётся актуальной |
| Ожидает проверки | Студент сообщил об исправлении или дал объяснение |
| Закрыта | Исправление подтверждено повторной проверкой |
| Снята | Объяснение студента принято, замечание признано неприменимым |
| Открыта повторно | Новые изменения снова создали ту же проблему |

(этот список не финальный и будет редактироваться)

Если студент выполняет слияние без реакции на существенную находку, она сохраняет открытый статус и отображается руководителю.

## 7. Панель научного руководителя

Панель является частью основного веб-приложения. Доступ получают только уполномоченные сотрудники.

Информация представлена на трёх уровнях.

### Общий список проектов

Главный экран показывает таблицу всех проектов. Для каждого проекта выводятся:

- название и краткое описание;
- участники;
- текущий этап;
- дата последней содержательной активности;
- регулярность коммитов и pull request;
- дата последнего обзора;
- количество открытых серьёзных замечаний;
- общий статус внимания;
- причина установленного статуса.

(этот список не финальный и будет редактироваться)

Таблицу можно фильтровать и сортировать по срочности, активности, количеству проблем и дате последней проверки. Дополнительно может быть доступно представление в виде карточек проектов.

Здесь же каждый проект можно подключить к системе или отключить от неё отдельным переключателем. Это нужно для случаев, когда работа над проектом приостановлена по объективным причинам и замечания системы теряют смысл. Поведение системы после паузы требует отдельной проработки: что происходит с накопленными замечаниями, нужен ли повторный полный разбор при возобновлении. Предполагается, что такие ситуации будут редкими.

Статус внимания обозначается цветом, но всегда сопровождается объяснением. Например, система указывает, сколько дней в проекте не было изменений, какая проблема остаётся открытой и как долго студент на неё не реагирует. Сам набор показателей и правила, по которым проект помечается как требующий внимания, — предварительная гипотеза. Возможен и более простой вариант, при котором система показывает руководителю фактические данные без собственной оценки.

Тексты хранятся в Markdown. Графики и схемы вставляются через специальные блоки и отображаются непосредственно внутри отчёта. Подсветка кода используется для выделения конкретных строк.

Раз в две недели сервис формирует короткую сводку для руководителя: какие проекты требуют внимания, что изменилось и почему рекомендуется вмешательство. Сводка содержит ссылки на соответствующие страницы панели. Способ её доставки — электронная почта, мессенджер или отдельная страница внутри панели — пока не выбран.

## 8. Технологическая основа

Приложение разрабатывается на Next.js и TypeScript. Интерфейс строится на Tailwind CSS с использованием готового набора компонентов.

Основные компоненты решения:

- Next.js для серверной логики и пользовательского интерфейса;
- GitHub App для получения событий и публикации проверок;
- API Anthropic для содержательного анализа;
- SQLite для структурированных данных;
- файловое хранилище для объёмных текстов и фрагментов;
- Recharts для графиков;
- Shiki для подсветки кода;
- системный планировщик для ежемесячных обзоров и регулярного сбора статистики.

Все компоненты работают в рамках одного развёрнутого приложения.

## 9. Предварительная оценка расходов

Основная переменная статья расходов связана с API языковой модели. Для тридцати проектов предварительный ориентир составляет $100-250 в месяц. Итоговая сумма будет зависеть от количества pull request, размера репозиториев, глубины анализа, выбранных моделей и частоты научного поиска.

Предлагается использовать разные классы моделей:

- модель среднего уровня для проверки pull request;
- старшую модель для ежемесячных обзоров;
- бюджетную модель для предварительной фильтрации и вспомогательных решений.

Ежемесячные обзоры можно отправлять через пакетный API Anthropic. Пакетная обработка тарифицируется со скидкой 50 процентов относительно стандартных запросов, согласно [документации Anthropic](https://platform.claude.com/docs/en/build-with-claude/batch-processing).

Расчёт $100-250 является предварительной гипотезой.

## 10. Порядок реализации

Работа делится на пять последовательных этапов.

### Этап 1. Интеграция с GitHub

Создаются GitHub-организация, шаблон репозитория и GitHub App. Сервис принимает события, запускает обязательную проверку и публикует тестовый ответ в pull request.

### Этап 2. Проверка изменений

Добавляются получение контекста, анализ через языковую модель, фильтрация находок и итоговый комментарий.

### Этап 3. Память проекта

Реализуются хранение находок, их статусы, ответы студентов, история проверок и повторная проверка исправлений.

### Этап 4. Ежемесячный обзор

Добавляются анализ проекта целиком, поиск публикаций и публикация структурированного отчёта в GitHub Issues.

### Этап 5. Панель руководителя

Создаются общий список проектов, страница проекта, досье проблемы, графики активности и регулярная сводка.

После запуска на реальных проектах уточняются проверочные списки, уровни серьёзности и правила определения статуса внимания.
