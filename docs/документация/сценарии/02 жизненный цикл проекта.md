# Жизненный цикл проекта

Обновлено: 2026-10-16. Пометки — см. `00 обзор.md`.

Состояния проекта в панели: **`active`** (разбирается) и **`paused`** (не разбирается)
**[есть]**. Состояния «архив» нет — вместо него удаление или пауза.

Что хранится о проекте (SQLite на сервере): проект, участники, pull request'ы, разборы
(с опубликованным комментарием и материалами), замечания со статусами и историей, ответы
студентов, назначенные руководители **[есть]**. В репозитории студента система ничего не
хранит — иначе студент мог бы отредактировать историю своих ошибок.

## Подключение нового проекта

Кто: руководитель центра в панели, после создания репозитория (см.
`01 организация и репозиторий.md`).

1. «Управление» → «Добавить проект»: `owner/repo`, название **[есть]**.
2. Назначить руководителя проекта **[есть]**; без руководителя проект виден только центру и
   отмечается «не назначен».
3. С этого момента события репозитория разбираются **[есть]**. До подключения события
   игнорируются целиком — ни проверки, ни записи в память **[есть]**.

Что происходит с тем, что было до подключения:

- Pull request'ы, открытые до подключения, в памяти не появятся, пока в них не придёт новый
  коммит или комментарий **[есть]**. Если правило ветки уже требует проверку, такие PR
  заблокированы до нового коммита.
- При подключении в очередь ставится **полный обзор** проекта: агент читает основную ветку
  целиком, заводит замечания о крупных ошибках, составляет заметки о проекте и публикует их
  в issue «Обзор проекта (AI Curator)» **[есть]**. Если поставить не удалось, обзор поставит
  сверка с GitHub в течение 10 минут: у проекта без обзора нет коммита памяти **[есть]**.
- Без права приложения Issues: Read and write обзор сохраняется в панели, но issue не
  публикуется; на странице разбора — пометка «не опубликовано» **[есть]**.

Ошибки при подключении — см. `07 нештатные ситуации.md`, «Настройка».

## Работа

См. `03 работа студента и руководителя.md`. Замечания принадлежат проекту: исправление,
пришедшее в любом следующем PR, закрывает замечание **[есть]**. Проектом замечание становится,
когда его код в основной ветке; замечание о коде, который есть только в ветке неслитого PR,
принадлежит этой ветке — другие PR его не видят и не закрывают **[есть]** (см. `07`, 2.11).

## Пауза

Когда: работа приостановлена по объективной причине (академический отпуск, студент
временно занят другим), и замечания теряют смысл. Предполагается редкой.

Кто: руководитель центра, «Управление» → проект → «Пауза» **[есть]**.

Что происходит:

- Новые коммиты и PR не разбираются. Обязательная проверка ставится и сразу завершается
  успехом с текстом «Проект на паузе — разбор не выполняется»; комментарий не публикуется —
  слияние не блокируется **[есть]**.
- Комментарии студентов в PR проекта на паузе **не сохраняются** — вебхук пропускает проект
  целиком **[есть]**. Решено так и оставить: пауза значит, что проект стоит.
- Закрытие и слияние PR на паузе **записываются** (состояние PR нужно панели) **[есть]**.
- Накопленные замечания сохраняются как были **[есть]**. На главной проект скрыт, пока не
  включён фильтр «показать на паузе» **[есть]**.

## Возобновление

Кто: руководитель центра, «Управление» → «Возобновить» **[есть]**.

Что происходит сейчас:

- Со следующего события проект снова разбирается **[есть]**.
- В очередь ставится **полный обзор** (без ограничения «раз в 7 дней»): агент читает
  актуальную основную ветку, заводит замечания о том, что слито за паузу, закрывает
  устаревшие открытые замечания, если исправление видно в коде, и обновляет заметки о
  проекте и issue **[есть]**.
- Открытые PR, получившие во время паузы проверку «на паузе — успех», не перепроверяются до
  нового коммита **[есть]**.

## Удаление

Кто: руководитель центра, «Управление» → проект → «Удалить» с подтверждением вводом
`owner/repo` **[есть]**.

Что происходит:

- Память проекта удаляется каскадно и безвозвратно: история → ответы → замечания → разборы →
  PR → участники → назначения → проект **[есть]**. Резервной копии перед удалением нет
  **[нет]**; резервное копирование базы вообще не настроено **[нет]** (SQLite — один файл,
  копия делается копированием файла).
- Репозиторий на GitHub **не трогается** — панель не управляет GitHub **[есть]**.
- Дальнейшие события репозитория игнорируются как «не подключён» **[есть]**. Если правило
  ветки требует проверку `AI Curator`, **все PR в репозитории заблокированы навсегда**.
  Поэтому удаление в панели должно сопровождаться действием на GitHub: снять правило или
  архивировать репозиторий. Сейчас это только ручная процедура, панель об этом не
  напоминает **[нет]**.
- Повторное подключение того же репозитория начинает память с нуля **[есть]**.

Когда удалять: проект создан по ошибке или тестовый. Для завершённых проектов — пауза
(память сохраняется).

## Завершение проекта

Магистерская работа защищена, студент ушёл. Решено (см. `принятые решения.md`):

1. Пауза в панели — память сохраняется **[есть]**.
2. Ответственный сотрудник архивирует репозиторий на GitHub — он становится только для
   чтения, события не приходят (ручная процедура).
3. Открытые замечания остаются как есть — это часть истории проекта.
4. Публичные комментарии куратора после защиты не удаляются.

## Переименование и передача репозитория

- Проект в памяти связан с репозиторием **по имени** `owner/repo` **[есть]**, а не по
  постоянному идентификатору GitHub.
- В панели `owner/repo` можно изменить, **только пока по проекту не было PR** **[есть]** —
  иначе рвётся связь событий.
- Если репозиторий переименуют или передадут на GitHub, события придут с новым именем,
  проект не найдётся, и события будут игнорироваться **[нет]** защиты — см.
  `07 нештатные ситуации.md`, «Настройка». Правильно — хранить постоянный `repository.id`
  GitHub и искать по нему.

## Смена участников и руководителя

- Руководителя назначает и снимает руководитель центра в «Управлении» **[есть]**; у проекта
  может быть несколько руководителей **[есть]**.
- Новый студент появляется в списке участников при первом своём PR **[есть]**. Ушедший не
  удаляется **[нет]**.
- Права студентов в GitHub меняет ответственный сотрудник вручную; панель о них не знает.
