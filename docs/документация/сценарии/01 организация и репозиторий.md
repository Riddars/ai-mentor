# Организация и репозиторий

Обновлено: 2026-09-30. Пометки — см. `00 обзор.md`.

## GitHub-организация

- Организация центра — одна на все проекты. Сейчас это `RiddarsCorp` (тестовая) **[есть]**.
- План GitHub — бесплатный; платный не покупаем, GitHub Education недоступен (см.
  `принятые решения.md`).
- Настройки организации на 2026-09-27 (проверено через API) **[есть]**: план `free`; базовое
  право участников на репозитории — `read`; участники **могут создавать репозитории**;
  администраторы репозитория могут менять его видимость и удалять его. Решено: запретить
  участникам создавать репозитории — иначе появятся проекты вне шаблона и без правил
  **[нет]**, настройка организации.
- Правила на уровне организации (org rulesets), чтобы не настраивать каждый репозиторий
  вручную, — по общим сведениям требуют платного плана; **[проверить]** в интерфейсе
  организации (через API не проверить без прав `admin:org`). Сейчас правила заданы в каждом
  репозитории отдельно.

## GitHub App «AI Curator»

- Зарегистрирован, установлен в организацию **на все репозитории** (с 2026-09-30) **[есть]**:
  новые репозитории получают события автоматически. Сервис разбирает только проекты,
  подключённые в панели; события остальных репозиториев игнорируются.
- Права приложения (проверено через API) **[есть]**: `checks: write`, `contents: read`,
  `issues: read`, `metadata: read`, `pull_requests: write`. Для ежемесячного обзора (этап 4)
  понадобится `issues: write`.
- Подписки на события: `pull_request`, `issue_comment` **[есть]** (подписка на Issue comment
  включена при этапе 3 — без неё объяснения студента без коммита не доходят). На
  `check_run` приложение не подписано — поэтому кнопка «Re-run» у проверки в GitHub ничего не
  делает; на `pull_request_review` и `pull_request_review_comment` — тоже нет.
- Адрес вебхука — адрес сервиса. Постоянного адреса нет: при проверках сервис поднимался
  локально через туннель **[нет]** постоянного развёртывания.
- Секрет вебхука (`GITHUB_WEBHOOK_SECRET`) — каждое событие проверяется по HMAC-подписи;
  поддельное событие отклоняется **[есть]**.

## Шаблон репозитория `project-template`

Публичный репозиторий-шаблон **[есть]**. Содержимое на 2026-09-27:

| Файл | Назначение | Кто заполняет |
|---|---|---|
| `RESEARCH.md` | Суть исследования: научный вопрос, смысл и ценность, данные (источник, объём, разбиение), методы (модели, метрики) | студент в начале, обновляет по ходу |
| `PLAN.md` | План по этапам и шагам с чекбоксами; живой документ, не переписывается начисто | студент |
| `README.md` | Техническое устройство: где что лежит, внешние материалы (Colab, датасет), как запустить | студент |
| `.github/PULL_REQUEST_TEMPLATE.md` | Форма описания PR: что сделано, зачем, как проверялось | подставляется GitHub в каждый PR |

- Имена `RESEARCH.md` и `PLAN.md` обязательны: на них опирается система (сказано в
  `README.md` шаблона).
- Структуры каталогов и «базовых автоматических проверок» в шаблоне нет и не будет —
  решено: студенты работают в разных форматах (модули, ноутбуки, один Colab). Упоминания
  убраны из концепции.
- Как куратор использует файлы шаблона сейчас:
  - `RESEARCH.md` и `PLAN.md` — читаются на коммите PR и передаются модели (до 20 000
    символов каждый) **[есть]**;
  - `README.md` — модели не передаётся и не будет (решено: там техническое);
  - описание PR (по шаблону: что сделано, зачем, как проверялось) — передаётся модели (до
    5 000 символов) **[есть]**.

## Создание репозитория проекта

Порядок (делает ответственный сотрудник центра, вручную) **[есть как ручная процедура]**:

1. Создать репозиторий в организации **из шаблона** `project-template`. Публичный —
   обязательно: на бесплатном плане защита ветки с обязательными проверками работает только
   в публичных репозиториях.
2. Настроить правило (ruleset) для основной ветки — см. ниже.
3. Добавить студентов (см. «Люди и права»).
4. Подключить репозиторий в панели: «Управление» → добавить `owner/repo`, назначить
   руководителя.
5. Студент заполняет `RESEARCH.md`, `PLAN.md`, `README.md` — первым pull request.

Автоматизации этого порядка нет: панель не создаёт репозитории и не настраивает правила в
GitHub. Решено: пока не автоматизировать — при ~30 проектах хватит ручного порядка. Ошибки
ловит проверка при подключении: панель через API проверяет, что правило ветки есть и
проверка в нём привязана к приложению, и показывает предупреждение **[нет]**. Для этого приложению нужно право `administration: read`.

Порядок шагов 2 и 4 важен: если правило требует проверку `AI Curator`, а проект в панели не
подключён, куратор события игнорирует, проверка не появляется, и **слияние заблокировано
навсегда**. Правило и подключение должны появляться вместе.

## Правило основной ветки (ruleset)

На `test-project-2` правила нет вовсе — слияние там не блокируется никогда (проверено через
API). На `test-project-1` на 2026-09-27 действует правило `main-protection` **[есть]**:

- применяется к ветке по умолчанию;
- изменения только через pull request (одобрения ревьюеров не требуются — 0);
- обязательная проверка `AI Curator`;
- разрешённые способы слияния: merge, squash, rebase;
- обходить правило не может никто (`bypass_actors` пуст).

Проблемы, найденные при сверке:

- **Проверка не привязана к нашему приложению [частично]** — в правиле указано только имя
  `AI Curator`, без источника (`integration_id`). Тогда подходит статус с этим именем от
  **любого** источника: студент с правом записи может сам выставить через API коммиту статус
  `AI Curator: success` и обойти проверку. Концепция (раздел 3) требует, чтобы проверка
  принималась только от приложения. Нужно указать в правиле наше приложение как источник —
  **[нет]**, сделать при настройке каждого репозитория.
- Запрет принудительной перезаписи (force-push) и удаления основной ветки отдельными
  правилами не задан. Требование «только через pull request» без обходов, по документации
  GitHub, уже не даёт пушить в основную ветку напрямую, в том числе принудительно, —
  **[проверить]** на тестовом репозитории.
- Никто не может обойти правило, включая администраторов, — и не нужно: ручного снятия
  блокировки больше нет. Разбор повторяется автоматически, после 30 минут без разбора
  проверка завершается «не разобрано», а руководитель может перезапустить разбор из панели
  **[есть]** (см. `07 нештатные ситуации.md`, 5.3). Для кнопки «Re-run» в GitHub приложение
  должно быть подписано на `check_run`.

## Люди и права

- **Студенты** — участники организации с правом `write` на репозиторий своего проекта
  (через команду проекта или напрямую). Не `admin`: иначе могут изменить правила ветки.
  Сейчас в `test-project-1` единственный участник — владелец организации (`admin`).
  Решено: на каждый проект — команда GitHub с правом `write`; студенты — участники
  организации; право `write` через команду и делает их участниками проекта для куратора;
  `admin` — никогда.
- **Руководители** — в GitHub им права не обязательны: они работают в панели. Если хотят
  комментировать PR — нужен хотя бы `read` (для публичного репозитория комментировать может
  любой пользователь GitHub). Их комментарии сейчас попадают в «ответы студента» — см.
  `07 нештатные ситуации.md`.
- **Ответственный сотрудник** — владелец организации (`admin`).
- **Участники в панели** — список логинов у проекта **собирается автоматически** из авторов
  pull request **[есть]**. Отдельный список в панели не нужен: участником проекта для
  куратора считается тот, у кого право записи в репозиторий или выше **[есть]**; поэтому
  студенты должны получить `write` (через команду проекта). Руководителю, чьи комментарии
  должны учитываться, тоже нужно право записи — иначе при скрытом членстве в организации его
  комментарии будут пропущены. Ушедший из проекта студент из списка не удаляется
  **[нет]**.
- Учётки панели (`head`, `supervisor`) — отдельно от GitHub, логин и пароль в панели
  **[есть]**. Связи «учётка панели ↔ логин GitHub» нет.
