## Шаблон репозитория `project-template`

Публичный репозиторий-шаблон **[есть]**. Содержимое на 2026-09-27:

| Файл | Назначение | Кто заполняет |
|---|---|---|
| `RESEARCH.md` | Суть исследования: научный вопрос, смысл и ценность, данные (источник, объём, разбиение), методы (модели, метрики) | студент в начале, обновляет по ходу |
| `PLAN.md` | План по этапам и шагам с чекбоксами; живой документ, не переписывается начисто | студент |
| `README.md` | Техническое устройство: где что лежит, внешние материалы (Colab, датасет), как запустить | студент |
| `.github/PULL_REQUEST_TEMPLATE.md` | Форма описания PR: что сделано, зачем, как проверялось | подставляется GitHub в каждый PR |

- Имена `RESEARCH.md` и `PLAN.md` обязательны: на них опирается система (сказано в
  `README.md` шаблона).
- Структуры каталогов и «базовых автоматических проверок» в шаблоне нет и не будет —
  решено: студенты работают в разных форматах (модули, ноутбуки, один Colab). Упоминания
  убраны из концепции.
- Как куратор использует файлы шаблона сейчас:
  - `RESEARCH.md` и `PLAN.md` — читаются на коммите PR и передаются модели (до 20 000
    символов каждый) **[есть]**;
  - `README.md` — модели не передаётся и не будет (решено: там техническое);
  - описание PR (по шаблону: что сделано, зачем, как проверялось) — передаётся модели (до
    5 000 символов) **[есть]**.

## Создание репозитория проекта

Заводит руководитель проекта (решено 2026-10-16), панель ведёт по шагам **[есть]**:

1. «Управление» → «Новый проект» → ссылка «Создайте репозиторий из шаблона» открывает GitHub с
   уже выбранными организацией (`GITHUB_ORG`), шаблоном `project-template` и видимостью
   Public; руководитель вводит имя и нажимает Create. Публичный — обязательно: на бесплатном
   плане обязательные проверки работают только в публичных репозиториях.
2. Там же — подключить репозиторий в панели. Ставится первичный полный обзор, панель
   открывает страницу проекта.
3. Блок «Настройка в GitHub» на странице проекта: «Скачайте файл правила» (JSON с ID нашего
   приложения) → «правила репозитория» → New ruleset → Import a ruleset → файл → Create.
4. Ссылка «добавьте их в репозиторий» — студенты с ролью Write.
5. Тот же блок проверяет через API и показывает галочки: приложение установлено, репозиторий
   публичный, изменения только через PR, проверка `AI Curator` обязательна и привязана к
   приложению **[есть]**; хватает права Metadata: read. Добавление студентов не проверяется.
6. Студент заполняет `RESEARCH.md`, `PLAN.md`, `README.md` — первым pull request.

Панель репозитории не создаёт и правила не ставит — это делает человек под своей учёткой.
Подключение (шаг 2) идёт до правила (шаг 3): если наоборот, куратор события игнорирует,
проверка не появляется, и **слияние заблокировано**, пока проект не подключат. Сохраняет ли
импорт правила привязку проверки к приложению — **[проверить]** вживую; если нет, блок
покажет крестик у последнего пункта.

## Правило основной ветки (ruleset)

На `test-project-2` правила нет вовсе — слияние там не блокируется никогда (проверено через
API). На `test-project-1` на 2026-09-27 действует правило `main-protection` **[есть]**:

- применяется к ветке по умолчанию;
- изменения только через pull request (одобрения ревьюеров не требуются — 0);
- обязательная проверка `AI Curator`;
- разрешённые способы слияния: merge, squash, rebase;
- обходить правило не может никто (`bypass_actors` пуст).

Проблемы, найденные при сверке:

- **Проверка не привязана к нашему приложению [частично]** — в правиле указано только имя
  `AI Curator`, без источника (`integration_id`). Тогда подходит статус с этим именем от
  **любого** источника: студент с правом записи может сам выставить через API коммиту статус
  `AI Curator: success` и обойти проверку. Концепция (раздел 3) требует, чтобы проверка
  принималась только от приложения. Нужно указать в правиле наше приложение как источник —
  **[нет]**, сделать при настройке каждого репозитория. REST API принимает привязку к
  установленному приложению сразу при создании правила, до первой проверки в репозитории
  (проверено 2026-10-13), — см. `развёртывание с нуля.md`, раздел 6.
- Запрет принудительной перезаписи (force-push) и удаления основной ветки отдельными
  правилами не задан. Требование «только через pull request» без обходов, по документации
  GitHub, уже не даёт пушить в основную ветку напрямую, в том числе принудительно, —
  **[проверить]** на тестовом репозитории.
- Никто не может обойти правило, включая администраторов, — и не нужно: ручного снятия
  блокировки больше нет. Разбор повторяется автоматически, после 30 минут без разбора
  проверка завершается «не разобрано», а руководитель может перезапустить разбор из панели
  **[есть]** (см. `07 нештатные ситуации.md`, 5.3). Для кнопки «Re-run» в GitHub приложение
  должно быть подписано на `check_run`.

## Люди и права

- **Студенты** — с правом `write` на репозиторий своего проекта; не `admin`: иначе могут
  изменить правила ветки. Решено 2026-10-16 (вместо команд и членства в организации): **внешние
  соавторы** своего репозитория с ролью `write`; участниками организации не становятся,
  репозитории создавать не могут; `admin` — никогда.
- **Руководители проектов** — участники организации `ai-chem-curator`; сами создают
  репозитории своих проектов из шаблона и становятся в них администраторами (решено
  2026-10-16). Видимость менять и удалять репозитории не могут. Их комментарии в PR сейчас
  попадают в «ответы студента» — см. `07 нештатные ситуации.md`.
- **Ответственный сотрудник** — владелец организации (`admin`).
- **Участники в панели** — список логинов у проекта **собирается автоматически**: студент
  появляется, как только принял приглашение в репозиторий (событие `member` приложения;
  страница проекта в «Управлении» дописывает тех, чьё событие потерялось), и уходит из списка,
  когда его удалили из репозитория; авторы PR тоже попадают в список (с 2026-10-16) **[есть]**.
  Участником проекта для куратора считается тот, у кого право записи в репозиторий или выше
  **[есть]**; поэтому студенты получают `write`. Руководителю, чьи комментарии должны
  учитываться, тоже нужно право записи.
- Учётки панели (`head`, `supervisor`) — отдельно от GitHub, логин и пароль в панели
  **[есть]**. Связи «учётка панели ↔ логин GitHub» нет.
