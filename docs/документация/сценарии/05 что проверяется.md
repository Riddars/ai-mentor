# Что проверяется

Обновлено: 2026-09-27. Пометки — см. `00 обзор.md`.

## Цель проверки

Найти то, что **может повлиять на результаты или выводы исследования**, пока на этом не
построена работа. Не цель: стиль кода, производительность, архитектура, оформление —
если они не меняют результат.

## Области

Каждое замечание относится ровно к одной области **[частично]** — это требование промпта;
если модель вернёт неизвестную область, замечание сохранится «без области» (так же с
серьёзностью):

| Область | Что сюда относится | Примеры для химии и ML |
|---|---|---|
| Код (`code`) | ошибка в коде, меняющая результат без явного сбоя | неверная ось усреднения, перепутанные столбцы, молчаливое отбрасывание строк |
| Данные (`data`) | качество и обработка данных | дубликаты молекул (разные SMILES одной молекулы), противоречивые метки, пропуски, выбросы, неверные единицы |
| Методология (`methodology`) | схема эксперимента | утечка между train и test, случайное разбиение вместо разбиения по скелету или семейству, подбор гиперпараметров на тесте, неподходящая метрика, нет бейзлайна |
| Воспроизводимость (`reproducibility`) | можно ли повторить результат | не зафиксированы сиды, версии пакетов, недостающие шаги, данные вне репозитория без ссылки |
| Постановка задачи (`problem`) | цель, гипотеза, целевая переменная | не определён критерий успеха, задача не проверяема, целевая переменная не отвечает вопросу |
| Научная логика (`reasoning`) | выводы и рассуждения | вывод не следует из результатов, сравнение по одному запуску без разброса, противоречие между разделами |
| Новизна и контекст (`novelty`) | место работы среди известного | задача решена известными методами, нет сравнения со стандартным подходом |
| Расхождение с планом (`plan`) | описание против фактической работы | заявлена регрессия — сделана классификация; метод из `RESEARCH.md` не реализован |

Ограничения при разборе PR (модель видит diff и `RESEARCH.md`, см. `04 куратор изнутри.md`):

- `novelty` и значимая часть `reasoning` требуют взгляда на проект целиком и знаний о
  литературе — основной их источник ежемесячный обзор (**[нет]**, этап 4);
- `plan` проверяется только по `RESEARCH.md`: `PLAN.md` модели не передаётся **[нет]**;
- `data` — модель видит данные, только если их текстовый diff попал в PR и влез в лимит.

## Уровни серьёзности

Три уровня **[есть]**:

- **Критично** (`critical`) — может исказить результаты или выводы работы. На главной
  окрашивает число замечаний в красный.
- **Важно** (`important`) — снижает надёжность или качество, но выводы, вероятно, устоят.
- **К сведению** (`info`) — стоит учесть, на выводы не влияет.

Уровни и области приняты 2026-09-27; решено пересмотреть через 1–2 месяца реальной работы.

## Правила для каждого замечания

- **Подтверждение.** Замечание включается, только если модель указала конкретный фрагмент
  кода, данных или текста, на котором оно основано **[есть]** (требование промпта; кодом не
  проверяется — модель может нарушить).
- **Основания.** Список мест: файл и строки, документ и раздел, набор данных, иное. Может
  быть пустым — для логической ошибки **[есть]**.
- **Язык.** Все тексты — на русском, простым языком **[есть]** (требование промпта).
- **Не повторять снятое.** Замечание, снятое по объяснению студента, не поднимается снова без
  новых оснований **[есть]** (требование промпта). Но снятые замечания модели не передаются
  (см. `04`), поэтому модель знает о них только из ответа студента в текущем PR —
  **[частично]**: в следующем PR снятая проблема может быть поднята заново.

## Декомпозиция замечаний

Проблема: если одно замечание объединяет несколько дефектов, частичное исправление приводит
к ошибке — модель пометит «исправлено» целиком, хотя исправлена часть, или наоборот не
закроет исправленное.

Правила приняты 2026-09-27, в промпте и коде **[нет]**:

1. **Одно замечание — одна проблема с одним признаком исправления.** Независимые дефекты
   (утечка в масштабировании и не зафиксированный сид) — отдельными замечаниями.
2. **Частичное исправление не закрывает замечание.** Оно остаётся открытым; модель
   переписывает «что не так» под оставшуюся часть и пишет в причине, что уже сделано.
3. **Признак исправления** — новое поле замечания «как проверить, что исправлено»: модель
   формулирует его при создании и сверяется с ним при следующих разборах. Требует поля в базе
   и строки в досье.
4. **Удаление — не исправление.** Если проблемный код удалён или вынесен из репозитория,
   замечание не закрывается как «исправлено» — отдельная причина «код удалён» (см. `07`, 2.14).
5. **Серьёзность и суть не меняются после создания** — это уже решено (2026-09-27, в коде
   **[нет]**): модель меняет только статус (см. `07`, 3.12). Руководитель серьёзность тоже
   не меняет — решено, что это лишнее.
6. **Незаполненное описание исследования.** Если `RESEARCH.md` пуст или остался шаблоном,
   модель заводит замечание области «постановка задачи» — отдельной пометки в панели не
   нужно.

Решение — после прогона живых PR: посмотреть, как часто модель ошибается без этих правил.

Систематических списков методических ошибок (для задач QSAR, предсказания свойств,
реакций, спектров и т. п.) нет **[нет]** — названы главной ценностью системы в

руководителями; это содержательная работа, не программная.

## Чего куратор не проверяет

- Стиль, форматирование, читаемость кода — только если меняют результат.
- Корректность вычислений на реальных данных — модель код не запускает **[есть]**.
- Графики и картинки в ноутбуках — модель их не видит (см. `06 языковая модель.md`).
- Данные вне репозитория (Google Drive, Colab) — недоступны.
- Код, слитый без PR-разбора (до подключения, во время паузы), — пока его не коснётся PR или
  ежемесячный обзор.
