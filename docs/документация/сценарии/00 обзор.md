# Сценарии работы системы: обзор

Обновлено: 2026-09-27.

Эта папка описывает, **как система работает на практике**: от создания репозитория до
нештатных ситуаций. Она ближе к техническому заданию, чем `детализированная концепция.md`:
концепция описывает замысел, а сценарии — что конкретно происходит на каждом шаге, кто что
делает и что система делает в ответ. Где сценарии пересекаются с концепцией, текст может
повторяться — это сознательно, чтобы каждый файл читался сам по себе. При расхождении
замысла прав главный документ, `детализированная концепция.md`; при расхождении с кодом —
см. пометки ниже.

## Пометки

Каждое утверждение о поведении системы помечено:

- **[есть]** — реализовано в коде и так работает сейчас;
- **[частично]** — реализовано не полностью; что именно не так — сказано рядом;
- **[нет]** — нужно, но не реализовано;
- **[не решено]** — непонятно, как должно быть; нужно решение пользователя;
- **[проверить]** — факт о внешнем мире (GitHub, провайдер модели), который надо проверить
  прежде, чем на него опираться.

Без пометки — описание ожидаемого поведения людей или пояснение.

## Файлы

1. `01 организация и репозиторий.md` — GitHub-организация, шаблон репозитория, настройки,
   GitHub App, роли и права людей.
2. `02 жизненный цикл проекта.md` — подключение, пауза, возобновление, удаление, завершение
   проекта: что делает человек и что происходит с памятью.
3. `03 работа студента и руководителя.md` — обычная работа: pull request, коммиты,
   ответы, слияние; что видит руководитель.
4. `04 куратор изнутри.md` — какие события обрабатываются, что собирается в запрос к
   модели, промпт, как обновляется память, что публикуется.
5. `05 что проверяется.md` — области, уровни серьёзности, правила находок, декомпозиция,
   признак исправления.
6. `06 языковая модель.md` — облачный API или локальная модель, без интернета, без
   картинок: что работает в любом случае и что зависит от модели.
7. `07 нештатные ситуации.md` — халатность, ошибки, попытки обойти систему, сбои; для
   каждой — что происходит сейчас и что должно происходить.

## Решения по сценариям (2026-09-27)

Приняты пользователем; в коде ещё **не реализованы** — в файлах помечены **[нет]**. Причины —
в `принятые решения.md`, раздел «Сценарии работы».

1. **Ответ студента** — только комментарии, у которых GitHub `author_association` — владелец,
   участник организации или соавтор репозитория; остальные пропускаются. Комментарии
   руководителей учитываются как ответы. PR от посторонних (из fork) не разбираются:
   проверка сразу «успех — автор не участник проекта» (`07`: 2.13, 3.9, 4.1).
2. **Закрытие в два шага.** Исправление видно в PR → `pending` «исправлено, ждёт слияния»;
   PR слит в основную ветку → `closed`; PR закрыт без слияния → снова `open`. PR в
   неосновные ветки разбираются, но окончательно закрывает только слияние в основную
   (`07`, 3.10).
3. **Сбой сервиса.** Автоматические повторы: периодически разбирать открытые PR без
   завершённой проверки. Не разобрано за **30 минут** → проверка завершается успехом с
   пометкой «не разобрано» в PR и панели, разбор остаётся в очереди. Кнопка «перезапустить
   разбор» в панели. Обход правила ветки — никому (`07`, 5.3).
4. **Публикация** — полный текст замечаний в PR, как сейчас; после защиты ничего не
   удаляется (`07`, 4.7).
5. **Секреты** — своей защиты не делаем; включить сканирование секретов GitHub
   (**[проверить]** бесплатность для публичных репозиториев); вернуться к вопросу, если
   секреты начнут попадать в репозитории (`07`, 2.16).
6. **Черновые PR** не разбираются: проверка сразу «успех — черновик»; разбор — при переходе
   в «готов к ревью» (`07`, 2.15).
7. **Расходы** — разбор через несколько минут после последнего коммита, только последний
   коммит; по комментарию модель вызывается, только если у проекта есть открытые замечания;
   лимит **50 запросов в сутки на проект**; при превышении проверка сразу завершается
   «не разобрано — лимит», разбор выполняется на следующие сутки (`07`, 5.10).
8. **Модель не меняет серьёзность и суть** замечания после создания — только статус и
   причину; остальные поля обновляются только непустыми значениями (`07`: 3.11, 3.12).
9. **Руководитель меняет статус сам.** В досье — «вернуть в открытые» и «закрыть как
   ложное» с обязательным комментарием; доступно руководителю проекта (по своим проектам) и
   руководителю центра; в истории помечается как решение человека (`03`, `07` 3.6, 4.2).
10. **Возобновление и подключение** — внеочередной обзор проекта целиком (механизм
    ежемесячного обзора, этап 4). **Завершение** — пауза в панели и архивирование
    репозитория на GitHub (делает ответственный сотрудник); открытые замечания остаются
    как история (`02`).

Вопросы второго порядка решены тем же днём (подробности — в файлах): студенты не создают
репозитории, права — через команду проекта с `write`; структуры каталогов и автоматических
проверок в шаблоне нет; при подключении панель проверяет настройки репозитория через API;
`README.md` и сообщения коммитов модели не передаются, `PLAN.md` и описание PR — передаются;
сырой ответ модели хранится; сверка по комментарию только меняет статусы; студенту
сообщается об отклонённом объяснении; ответы в ветках к строкам и тексты ревью принимаются;
на паузе комментарии не сохраняются; серьёзность не меняет никто; пустой `RESEARCH.md` —
замечание «постановка задачи»; правила декомпозиции приняты; литературу ищет сервис через
OpenAlex / Semantic Scholar; картинки модели не передаются; минимальная конфигурация модели —
требование; сводка руководителю и пересчёт расходов — после запуска.

Проверено независимо двумя субагентами 2026-09-27: «адвокат дьявола» искал непокрытые
ситуации, «судья» сверял пометки с кодом и настройками GitHub. Их находки внесены.

## Участники

- **Студент** — ведёт исследование в репозитории, работает через pull request. Панелью не
  пользуется.
- **Руководитель проекта** (`supervisor`) — научный руководитель 2–5 студентов; смотрит
  панель по своим проектам.
- **Руководитель центра** (`head`) — видит все проекты (~30), администрирует панель.
- **Ответственный сотрудник центра** — администрирует GitHub-организацию: создаёт
  репозитории, настраивает правила, снимает блокировку при сбоях. Кто это — **[не решено]**
  (см. «Чего не хватает» в `состояние работ.md`); технически сейчас это владелец организации.
- **Куратор** — наш сервис: GitHub App + веб-приложение + языковая модель.

## Как всё связано (коротко)

1. Студент открывает pull request или добавляет в него коммит.
2. GitHub присылает событие **вебхуком** нашего GitHub App на адрес сервиса. Это не GitHub
   Actions: в репозитории студента ничего не запускается, и студент не может отключить или
   подменить проверку, редактируя файлы репозитория.
3. Сервис ставит обязательную проверку `AI Curator` (слияние временно заблокировано), в фоне
   собирает изменения и описание исследования, берёт из своей базы открытые замечания
   проекта и отправляет всё одним запросом языковой модели.
4. Модель возвращает структурированный ответ (JSON). **Модель ничего не хранит**: вся память
   проекта — в базе SQLite на нашем сервере.
5. Сервис сохраняет замечания, публикует комментарий в pull request и завершает проверку
   успехом — слияние разрешено (куратор совещательный).
6. Руководитель видит замечания, их историю и разборы в панели.
