## Кто запускает разбор

Никакого расписания и опроса: разбор запускает только **событие GitHub**, присланное
вебхуком GitHub App **[есть]**. GitHub Actions не используются. Ежемесячный обзор по
расписанию — этап 4 **[нет]**.

## Режимы работы (`CURATOR_REVIEWER`)

| Режим | Что делает | Когда |
|---|---|---|
| `simulate` — **по умолчанию** | заглушка без модели; подрежим `CURATOR_SIM_MODE` | только для проверки связки с GitHub |
| `llm` | реальный разбор моделью, память проекта | рабочий режим |

Подрежимы `simulate` **[есть]**: `manual` (по умолчанию) — проверка ставится «в процессе» и
ждёт ручного завершения; `auto-approve` / `auto-block` — через `CURATOR_SIM_DELAY_MS`
завершается успехом / `action_required` с текстом-заглушкой; `offline` — событие
игнорируется, проверка не ставится (сценарий недоступного сервиса).

В режиме `simulate` нет памяти, участников, дедупликации доставок; комментарии студентов
игнорируются **[есть]**.

**Опасное умолчание закрыто.** Без `CURATOR_REVIEWER` сервис работал бы в `simulate` +
`manual`: каждый PR получал бы проверку «в процессе» навсегда. Поэтому при
`NODE_ENV=production` без явного `CURATOR_REVIEWER` сервис не стартует — ошибка
конфигурации **[есть]**. В разработке умолчание — по-прежнему `simulate`.

Обязательные переменные: `GITHUB_APP_ID`, ключ приложения, `GITHUB_WEBHOOK_SECRET` и
`SIM_ADMIN_TOKEN` — **в любом режиме**; без них каждое событие получает ответ 500 **[есть]**.
В режиме `llm` ещё `LLM_PROVIDER` и ключ провайдера.

## Путь события

1. **Приём.** `POST /api/github/webhook`. Проверка HMAC-подписи; неверная → 401 **[есть]**.
2. **Дедупликация** (только `llm`). Идентификатор доставки (`X-GitHub-Delivery`)
   записывается **до** фильтрации, для любых событий; повторная доставка с тем же
   идентификатором пропускается **[есть]**. Таблица доставок не чистится, в том числе при
   удалении проекта **[есть]**.
3. **Фильтр событий.** Обрабатываются только `pull_request` и `issue_comment`; остальное
   принимается и игнорируется **[есть]**.
4. **Ворота подключения.** Проект ищется по постоянному идентификатору репозитория GitHub
   (`repository.id`), а если его ещё нет — по `owner/repo` без учёта регистра, и id
   запоминается. Переименованный или переданный репозиторий находится по id, имя в памяти
   обновляется. Не найден → событие игнорируется целиком **[есть]**.
5. **Закрытие PR** (`closed`) → записать «слит» / «закрыт без слияния» и выполнить второй
   шаг закрытия замечаний, исправленных в этом PR (см. «Как обновляется память») **[есть]**.
6. **Открытие, коммит, переоткрытие, «готов к ревью»** → записать PR как открытый вместе с
   его последним коммитом **[есть]**.
7. **Проверка без разбора** — ставится и сразу завершается «успех» с пояснением, слияние не
   блокируется **[есть]**:
   - проект на паузе (комментарии тоже игнорируются);
   - автор PR не участник проекта: `author_association` не владелец, не участник
     организации и не соавтор репозитория (например, PR из fork постороннего);
   - черновой PR — разбор при переводе в «готов к ревью» (`ready_for_review`).
8. **Разбор коммита** или **сверка по комментарию** (см. ниже).
9. **Ответ GitHub.** GitHub ждёт ответ на вебхук около 10 секунд, модель отвечает дольше,
   поэтому разбор идёт в фоне **[есть]**:
   - ветка коммита: ошибка **до** фоновой части (не получен токен, не создалась проверка) →
     ответ 500, запись о доставке снимается; в панели следа нет — разбор не записан
     **[есть]**;
   - ветка комментария запускается в фоне целиком — ответ всегда 200 **[есть]**.
   GitHub неудачные доставки сам **не повторяет**; вручную их можно повторить в настройках
   приложения за последние 3 дня (по документации GitHub). Повтор приходит с тем же
   идентификатором доставки, поэтому доставка, уже получившая 200, будет отброшена как
   дубликат **[есть]** — ручной повтор помогает только для недошедших и получивших 500.

## Разбор коммита

Запускается на `opened` / `synchronize` / `reopened` / `ready_for_review` у нечернового PR
участника проекта.

1. Записать участника (автора PR) и PR **[есть]**.
2. Если по этому коммиту (head) этого PR уже есть **успешный** разбор (`ok`) — выйти
   **[есть]**. После `error` или `parse_error` повторное событие на том же коммите (например,
   закрыть и переоткрыть PR) запускает разбор заново.
3. Создать проверку `AI Curator` «в процессе» — **с этого момента слияние заблокировано**
   **[есть]**.
4. В фоне: собрать контекст, запросить модель, разобрать ответ, сохранить, опубликовать
   комментарий, завершить проверку **«успех»** **[есть]**. Если ответ модели не разобрался
   как JSON — **один повторный запрос**; не разобрался и он (`parse_error`) — в PR коротко
   «Разбор не удался… подробности у руководителя», сырой ответ сохраняется только в разборе
   (виден в панели), память не меняется, проверка «успех» **[есть]**.
5. Ошибка на любом шаге фоновой части (в том числе тайм-аут модели, см. `06`) → разбор с
   исходом `error`, комментарий «Не удалось выполнить разбор… слияние остаётся
   заблокированным до ручной проверки», проверка `action_required` — **слияние
   заблокировано** **[есть]**. Снятие — см. `07 нештатные ситуации.md`, «Сбои».

## Сверка по комментарию

Запускается на `issue_comment.created` в PR, если режим `llm`, автор комментария не бот и
его `author_association` — владелец, участник организации или соавтор репозитория
**[есть]**. Комментарии посторонних не сохраняются и модель не вызывают. Комментарии
руководителей, если они участники организации, учитываются как ответы. Срабатывает и в
слитых, и в закрытых PR **[есть]**.

1. Получить у GitHub актуальное состояние PR **[есть]**. Ошибка здесь (нет токена, GitHub
   не ответил) → ответ студента **не сохраняется**, разбор не записывается — следа нет
   **[есть]**.
2. Сохранить комментарий как ответ; уже сохранённый — выйти **[есть]**.
3. Если у проекта нет открытых замечаний — выйти: сверять нечего, модель не вызывается
   **[есть]**.
4. Собрать тот же контекст, что для коммита, на текущем head, и запросить модель. Сверка по
   комментарию **только меняет статусы** прошлых замечаний; новые находки из ответа
   отбрасываются — их заводит разбор коммита **[есть]**. Проверка не создаётся — слияние не
   затрагивается.
5. Ответ студенту **[есть]**: «Учёл ответ» — какие замечания исправлены или сняты и
   «Объяснение не сняло замечание: X — причина» для прошлых замечаний, которые модель
   оставила открытыми. Если модель не сказала ничего о прошлых замечаниях или ответ не
   разобрался — молчание.
6. Ошибка во время разбора → разбор с исходом `error` **[есть]**. Ошибка публикации ответа
   после успешного разбора — не записывается **[есть]**.

## Что получает модель (контекст запроса)

Один запрос: системный промпт + сообщение с контекстом **[есть]**:

| Что | Откуда | Ограничения |
|---|---|---|
| Описание исследования `RESEARCH.md` | репозиторий, на коммите PR | целиком, **без лимита**; нет файла — «не найдено» |
| Открытые замечания проекта | наша база | все открытые, кроме замечаний из PR, закрытых без слияния; id, PR, статус, область, серьёзность, суть, основания; **без лимита** — растут, пока замечания не закрыты |
| Ответы студента | наша база | все ответы **текущего** PR, **без лимита** — накапливаются |
| Изменения PR | GitHub, список файлов PR | весь diff PR относительно основной ветки; см. ниже |

Как собираются изменения **[есть]**:

- запрашивается одна страница списка файлов — **не больше 100 файлов**; остальные не
  запрашиваются и нигде не отмечаются;
- файлы идут в порядке GitHub (по пути); к каждому — patch;
- лимит 50 000 символов: на **первом файле, который не помещается целиком**, сборка
  останавливается — он и **все следующие** файлы отбрасываются, модель получает пометку
  «часть изменений обрезана». Один большой файл данных или ноутбук в начале алфавита
  отрезает весь код после него; если первый файл больше лимита — модель не получает ни
  одного diff;
- файлы без текстового diff (бинарные, слишком большие для GitHub) — только имя.

Нужно: пропускать непомещающийся файл и идти дальше; код и документы — первыми; отмечать,
какие файлы не отправлены **[нет]**.

Список «Изменённые файлы» на странице разбора в панели показывает **все** файлы PR, в том
числе не отправленные модели, — вводит в заблуждение **[частично]**.

Без лимитов на `RESEARCH.md`, замечания и ответы запрос может переполнить окно модели:
например, студент вставил в комментарий лог на 200 КБ — после этого каждый разбор этого PR
падает с `error`, и новый коммит не спасает (ответ остаётся в базе) **[нет]** защиты.
Оценка «20–30 тысяч токенов» верна только для diff.

Чего модель **не получает**:

- `PLAN.md` **[нет]** — нужно добавить (область «расхождение с планом»);
- описание PR (что сделано, зачем, как проверялось) **[нет]** — стоит добавить;
- файлы целиком — только diff **[есть]**. Концепция (раздел 4) говорит о «связанных с
  изменениями файлах» — их сбор **[нет]**;
- `README.md`, данные, результаты, картинки **[нет]**;
- закрытые и снятые замечания **[нет]**.

**Итоговый diff целиком.** Каждый раз разбирается весь diff PR относительно основной
ветки, с учётом открытых замечаний проекта **[есть]** — модель видит итоговое состояние PR.
Решено так и оставить; концепция и `принятые решения.md` исправлены (раньше там было
«только новые изменения»).

## Промпт

Системный промпт (`SYSTEM_PROMPT` в `lib/curator/review.ts`) **[есть]** задаёт:

- роль: куратор исследований на стыке химии и ML; память находок проекта между проверками;
- что искать: методические и содержательные ошибки, способные повлиять на выводы;
- области и уровни серьёзности с определениями (см. `05 что проверяется.md`);
- основания: список мест, в том числе пустой;
- правила сверки: находки этого PR сверять все; находки других PR упоминать, только если
  изменения или ответ студента их касаются, закрывать — только если исправление видно;
  повтор прошлой проблемы — через `prior_id`; объяснённое и принятое не поднимать без новых
  оснований;
- каждую находку подтверждать фрагментом;
- формат: строго один JSON-объект (`summary`, `findings[]`), тексты на русском.

Чего в промпте нет: проверочных списков, правил декомпозиции и признака исправления (см.
`05`), правила «удаление кода не равно исправлению» (см. `07`), отделения материалов
студента от инструкций (см. `07`, 3.7) **[нет]**.

Параметры запроса: `max_tokens` (по умолчанию 8000), температура (0.2), тайм-аут (5 минут);
ответ, обрезанный по лимиту токенов (`finish_reason = length`), считается ошибкой **[есть]**.
Режим структурированного вывода не используется **[нет]** — см. `06 языковая модель.md`.

## Разбор ответа модели

- JSON ищется внутри блока кода, иначе — от первой `{` до последней `}`. Не разобрался —
  один повторный запрос, затем `parse_error` **[есть]**. Рассуждающие модели с фигурными
  скобками в тексте до JSON этот приём ломают.
- Находка без заголовка отбрасывается; неизвестный статус → `open`; неизвестная область →
  без области; серьёзность `high/medium/low` → `critical/important/info`, иная → без
  серьёзности; основания без `target` отбрасываются, неизвестный вид → `other` **[есть]**.
- `prior_id` принимается, **только если это замечание было передано модели в этом запросе**;
  любой другой (чужой проект, несуществующее, закрытое, снятое) → находка считается новой, а
  при сверке по комментарию отбрасывается **[есть]**.

## Как обновляется память

- Запись разбора (с материалами, фактическим провайдером и моделью, сырым ответом) —
  отдельным шагом **до** обработки находок **[есть]**.
- Находки и история — в одной транзакции **[есть]**:
  - новая находка → замечание со статусом «открыто» + запись истории;
  - прошлая находка → модель меняет **только статус и причину**. Область, серьёзность и суть
    фиксируются при создании; описание, основания, подтверждение, влияние и рекомендация
    обновляются, только если модель прислала непустое значение **[есть]**;
  - ответ модели «исправлено» записывается как `pending` — «исправлено, ждёт слияния» — с
    номером PR, в котором видно исправление; окончательное `closed` ставит слияние этого PR
    (ниже) **[есть]**;
  - замечания, которых модель не упомянула, не трогаются;
  - замечание остаётся привязанным к PR, где его нашли, даже если исправлено другим PR.
- Второй шаг закрытия — на `pull_request.closed` **[есть]**: PR слит в ветку по умолчанию →
  его `pending`-замечания становятся `closed` («Исправление слито в основную ветку»); закрыт
  без слияния → снова `open`; слит в другую ветку → остаются `pending`.
- Текст комментария сохраняется в разбор после публикации — отдельным шагом **[есть]**.

Если транзакция находок упадёт после записи разбора, останется разбор `ok` без находок,
проверка уйдёт в `action_required`, а повтор на том же коммите будет пропущен как «уже
разобран» **[есть]** — редкий, но тупиковый случай.

Жизненный цикл замечания:

| Статус | Когда | Кто ставит |
|---|---|---|
| `open` — открыто | найдено; или PR с исправлением закрыт без слияния; или человек вернул | модель, система, человек **[есть]** |
| `pending` — исправлено, ждёт слияния | исправление видно в diff PR | модель («исправлено») **[есть]** |
| `closed` — исправлено | PR с исправлением слит в ветку по умолчанию | система **[есть]** |
| `dismissed` — снято | объяснение студента принято; или человек закрыл как ложное | модель, человек **[есть]** |
| `reopened` — открыто повторно | проблема вернулась после закрытия | модель; закрытые модели не передаются, поэтому в задуманном смысле почти не возникает; при живой проверке этапа 3 модель поставила его, **отклонив объяснение студента** — не по смыслу **[есть]** |

Решение человека **[есть]**: в досье руководитель проекта (по своим проектам) или руководитель
центра может закрыть открытое замечание как ложное или вернуть закрытое в открытые — с
обязательной причиной; в истории статуса запись помечается логином человека.

## Что сохраняется и как долго

База SQLite (`DATABASE_PATH`, по умолчанию `./data/curator.db`) **[есть]**: всё бессрочно,
удаляется только вместе с проектом. Резервного копирования нет **[нет]**. Сырой ответ модели
каждого разбора хранится и виден на странице разбора свёрнутым блоком **[есть]**; полный

Провайдер и модель в разборе — **фактический** исполнитель, в том числе резервный, если
ответил он **[есть]**.

## Фоновая работа и её хрупкость

- Разбор — фоновая задача внутри процесса **[есть]**. Перезапуск процесса во время разбора
  теряет его: проверка остаётся «в процессе» — **слияние заблокировано**, в панели не видно
  **[нет]** защиты (фаза 2: очередь разборов).
- Тайм-аут запроса к модели — 5 минут (`LLM_TIMEOUT_MS`); по истечении — исход `error`
  **[есть]**.
- Несколько событий одного проекта разбираются **параллельно**, без очереди **[есть]**.
  Возможны гонки: две одинаковые проблемы заведутся дважды; поздний разбор старого коммита
  перезапишет статусы после свежего. Нужно: очередь на проект и отбрасывание результата,
  если head PR к моменту записи сменился **[нет]**.
- Резерв провайдера: при ошибке основного — один повтор у резервного, если задан **[есть]**.

Что с этим делать — см. `07 нештатные ситуации.md`, «Сбои».

## Ручное завершение проверки

`POST /api/simulate/conclude` с заголовком `x-sim-admin-token` (`SIM_ADMIN_TOKEN`) и
`owner/repo/prNumber` **[есть]**: находит проверку `AI Curator` на текущем коммите PR и
завершает её (`success` по умолчанию). Работает **в любом режиме**, в том числе `llm`, — это
сейчас единственный способ снять блокировку без нового коммита. Недостатки: публикует в PR
текст-заглушку симуляции (устаревший — про «обращения к Anthropic API на этом этапе нет»),
ничего не пишет в память, нужен доступ к токену и HTTP-клиент **[частично]**. Если проверки
на коммите нет вовсе (событие не дошло) — 404, не помогает.
