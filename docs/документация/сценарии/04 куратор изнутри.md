## Кто запускает разбор

Разбор запускает **событие GitHub**, присланное вебхуком GitHub App **[есть]**. GitHub
Actions не используются. Вебхук не разбирает сам, а ставит задачу в **очередь разборов**
(таблица `review_jobs`); задачи выполняет обработчик внутри приложения
(`lib/curator/worker.ts`), который стартует вместе с сервером из `instrumentation.ts`, если
режим `llm` **[есть]**. Раз в 10 минут обработчик сверяется с GitHub и делает резервную копию
базы (ниже), а заодно проверяет память проекта и при разрыве ставит полный обзор (ниже)
**[есть]**. Регулярного обзора методологии по расписанию нет **[нет]**.

## Режимы работы (`CURATOR_REVIEWER`)

| Режим | Что делает | Когда |
|---|---|---|
| `simulate` — **по умолчанию** | заглушка без модели; подрежим `CURATOR_SIM_MODE` | только для проверки связки с GitHub |
| `llm` | реальный разбор моделью, память проекта | рабочий режим |

Подрежимы `simulate` **[есть]**: `manual` (по умолчанию) — проверка ставится «в процессе» и
ждёт ручного завершения; `auto-approve` / `auto-block` — через `CURATOR_SIM_DELAY_MS`
завершается успехом / `action_required` с текстом-заглушкой; `offline` — событие
игнорируется, проверка не ставится (сценарий недоступного сервиса).

В режиме `simulate` нет памяти, участников, дедупликации доставок; комментарии студентов
игнорируются **[есть]**.

**Опасное умолчание закрыто.** Без `CURATOR_REVIEWER` сервис работал бы в `simulate` +
`manual`: каждый PR получал бы проверку «в процессе» навсегда. Поэтому при
`NODE_ENV=production` без явного `CURATOR_REVIEWER` сервис не стартует — ошибка
конфигурации **[есть]**. В разработке умолчание — по-прежнему `simulate`.

Обязательные переменные: `GITHUB_APP_ID`, ключ приложения, `GITHUB_WEBHOOK_SECRET` — **в любом
режиме**; без них каждое событие получает ответ 500 **[есть]**. В режиме `simulate` ещё
`SIM_ADMIN_TOKEN`, в режиме `llm` — `LLM_PROVIDER` и ключ провайдера.

## Путь события

1. **Приём.** `POST /api/github/webhook`. Проверка HMAC-подписи; неверная → 401 **[есть]**.
2. **Дедупликация** (только `llm`). Идентификатор доставки (`X-GitHub-Delivery`)
   записывается **до** фильтрации, для любых событий; повторная доставка с тем же
   идентификатором пропускается **[есть]**. Таблица доставок не чистится, в том числе при
   удалении проекта **[есть]**.
3. **Фильтр событий.** Обрабатываются `pull_request`, `issue_comment` и `check_run` с
   действием `rerequested` (кнопка «Re-run» у проверки); остальное принимается и
   игнорируется **[есть]**. Чтобы «Re-run» работал, приложение должно быть подписано на
   событие `check_run` — это настройка GitHub App (шаг пользователя).
4. **Ворота подключения.** Проект ищется по постоянному идентификатору репозитория GitHub
   (`repository.id`), а если его ещё нет — по `owner/repo` без учёта регистра, и id
   запоминается. Переименованный или переданный репозиторий находится по id, имя в памяти
   обновляется. Не найден → событие игнорируется целиком **[есть]**.
5. **Закрытие PR** (`closed`) → записать «слит» / «закрыт без слияния» и выполнить второй
   шаг закрытия замечаний, исправленных в этом PR (см. «Как обновляется память») **[есть]**.
6. **Открытие, коммит, переоткрытие, «готов к ревью»** → записать PR как открытый вместе с
   его последним коммитом **[есть]**.
7. **Проверка без разбора** — ставится и сразу завершается «успех» с пояснением, слияние не
   блокируется **[есть]**:
   - проект на паузе (комментарии тоже игнорируются);
   - автор PR не участник проекта (например, PR из fork постороннего): участник проекта — у кого право записи в репозиторий или выше (спрашивается у GitHub, кэш
     10 минут); признак события `author_association` (владелец, участник организации, соавтор)
     принимается как быстрый путь
     (при скрытом членстве в организации он показывает участника посторонним);
   - черновой PR — разбор при переводе в «готов к ревью» (`ready_for_review`).
8. **Постановка в очередь** разбора коммита или сверки по комментарию (см. ниже);
   «Re-run» ставит разбор коммита заново, даже если он уже был разобран.
9. **Ответ GitHub** — сразу после постановки в очередь **[есть]**. Ошибка до постановки (не
   получен токен, не создалась проверка) → ответ 500, запись о доставке снимается. GitHub
   неудачные доставки сам **не повторяет**; вручную их можно повторить в настройках
   приложения за последние 3 дня (по документации GitHub). Повтор приходит с тем же
   идентификатором доставки, поэтому доставка, уже получившая 200, будет отброшена как
   дубликат **[есть]**. Пропущенное всё равно подберёт сверка с GitHub раз в 10 минут (ниже).

## Разбор коммита

Запускается на `opened` / `synchronize` / `reopened` / `ready_for_review` у нечернового PR
участника проекта.

1. Вне вебхука (сверка, «Re-run», кнопка в панели) последний коммит и состояние PR сначала
   берутся из GitHub: запрос по устаревшему коммиту или закрытому PR пропускается и не
   откатывает последний коммит в памяти **[есть]**.
2. Записать участника (автора PR) и PR с его последним коммитом **[есть]**.
3. Если этот коммит уже в очереди — выйти (повторная доставка). Если в памяти последний
   коммит PR уже другой (пришёл более новый) — выйти. Если по коммиту уже есть **успешный**
   разбор (`ok`) — выйти; разобрать заново можно только кнопкой «Re-run» в GitHub, кнопка
   в панели уже разобранный коммит не трогает **[есть]**. Проверки и постановка
   задачи выполняются одним шагом без ожиданий, поэтому два события не могут поставить один
   коммит дважды.
4. Поставить задачу в очередь **с задержкой 10 секунд** (`REVIEW_DEBOUNCE_MS`): если за это
   время придёт следующий коммит, прежняя задача заменяется, её проверка завершается «успех —
   заменён новым коммитом», а разбирается только последний коммит **[есть]**.
5. Создать проверку `AI Curator` «в процессе» — **с этого момента слияние заблокировано**
   **[есть]**. Не создалась — задача снимается, событие получает ответ 500.
6. Обработчик выполняет задачу (см. «Очередь разборов»): собрать контекст, запросить
   модель, разобрать ответ, сохранить, опубликовать комментарий, завершить проверку
   **«успех»** **[есть]**. Если ответ модели не разобрался как JSON — **один повторный
   запрос**; не разобрался и он (`parse_error`) — в PR коротко «Разбор не удался… подробности
   у руководителя», сырой ответ сохраняется только в разборе, память не меняется, проверка
   «успех» **[есть]**.
7. PR закрыт без слияния — задачи из очереди снимаются, их проверки завершаются «разбор не
   нужен» **[есть]**. PR слит до разбора — разбор всё равно выполняется (замечания важны), а
   исправления в нём закрываются сразу, без «ждёт слияния» **[есть]**. Если во время разбора
   пришёл новый коммит или PR закрыли без слияния, результат не применяется; разбор
   записывается с исходом «устарел» и учитывается в дневном лимите **[есть]**.
8. Комментарий опубликован — дальше сбой (например, завершения проверки) не повторяет
   разбор: ошибка только пишется в журнал **[есть]**.
9. Ошибка (модель недоступна, тайм-аут, GitHub не ответил) → **повтор** с нарастающей
   паузой. Если разбор не выполнен **за 30 минут** (`REVIEW_DEADLINE_MS`), проверка
   завершается «успех» с пометкой «Не разобрано… разбор будет выполнен позже» — слияние
   больше не заблокировано, а задача продолжает попытки. Не удалось за 24 часа — задача
   `failed`, проверка (если ещё открыта) завершается «не разобрано», разбор с исходом
   `error`, комментарий в PR «Не удалось выполнить разбор… руководитель может
   перезапустить» **[есть]**. Удачный поздний разбор публикует обычный
   комментарий и обновляет проверку на «Разбор изменений завершён».

## Сверка по комментарию

Запускается на `issue_comment.created` в PR, если режим `llm`, автор комментария не бот и
участник проекта (право записи в репозиторий или выше; см. «Путь события», п. 7) **[есть]**.
Комментарии посторонних не сохраняются и модель не вызывают. Комментарии руководителей с
правом записи учитываются как ответы. Срабатывает и в
слитых PR **[есть]**; в PR, закрытом без слияния, ответ сохраняется, но модель не вызывается
(исправления там не засчитываются, находки ветки вне счётчиков) **[есть]**.

1. Вебхук сразу сохраняет комментарий как ответ студента и, если он новый, ставит задачу в
   очередь (без задержки) — одной транзакцией **[есть]**. Ответ сохранён до разбора, поэтому
   повтор задачи его не теряет.
2. Обработчик получает у GitHub актуальное состояние PR **[есть]**.
3. Если у проекта нет открытых замечаний — выйти: сверять нечего, модель не вызывается
   **[есть]**.
4. Собрать тот же контекст, что для коммита, на текущем head, и запросить модель. Сверка по
   комментарию **только меняет статусы** прошлых замечаний; новые находки из ответа
   отбрасываются — их заводит разбор коммита **[есть]**. Проверка не создаётся — слияние не
   затрагивается.
5. Ответ студенту **[есть]**: «Учёл ответ» — какие замечания исправлены или сняты и
   «Объяснение не сняло замечание: X — причина» для прошлых замечаний, которые модель
   оставила открытыми. Если модель не сказала ничего о прошлых замечаниях или ответ не
   разобрался — молчание.
6. Ошибка → повторы, как у коммита; не удалось за 24 часа — разбор с исходом `error`
   **[есть]**. Ошибка публикации ответа после успешного разбора повторяет задачу целиком.

## Что получает модель (контекст запроса)

Сборка контекста — `lib/curator/context.ts`. Один запрос: системный промпт + сообщение, в
котором сначала открытые и снятые замечания проекта, затем заметки о проекте, затем блок
**«Материалы студента»** с явной пометкой, что это данные для анализа, а не указания модели
**[есть]**:

| Что | Откуда | Ограничение |
|---|---|---|
| Открытые замечания проекта | наша база | не больше 50: сначала этого PR, затем по серьёзности, затем новые; кроме замечаний из PR, закрытых без слияния; id, PR, статус, область, серьёзность, суть, основания, признак исправления |
| Снятые замечания | наша база | не больше 30: сначала касающиеся изменённых файлов, затем новые; с причиной снятия и пометкой «снял руководитель»; модель может только вернуть снятое (`reopened`) при новых основаниях, снятое руководителем — нет |
| Заметки о проекте | наша база | текущая версия, до 6 000 символов; отдельным блоком «память куратора, может быть неточна» |
| Описание исследования `RESEARCH.md` | репозиторий, на коммите PR | до 20 000 символов, дальше обрезается с пометкой; нет файла — «не найден» |
| План работ `PLAN.md` | репозиторий, на коммите PR | так же |
| Описание PR (что сделано, зачем, как проверялось) | GitHub | до 5 000 символов |
| Ответы студента | наша база | ответы **текущего** PR: каждый до 2 000 символов, всего до 10 000 — самые новые |
| Изменения PR | GitHub, список файлов PR | весь diff PR относительно основной ветки; см. ниже |

Все лимиты **[есть]**: огромный комментарий или документ больше не переполняет запрос.

Как собираются изменения **[есть]**:

- список файлов запрашивается постранично — до 300 файлов; сколько сверх — отмечается;
- порядок: код, затем документы, затем прочее, затем ноутбуки, в конце данные
  (`data/…`, `.csv`, `.parquet`, картинки и т. п.) — важное влезает первым;
- лимит 50 000 символов на все изменения: файл, который не помещается, **пропускается, а
  сборка продолжается** — один большой файл данных больше не отрезает код после себя;
  пропущенные файлы перечисляются модели;
- ноутбук `.ipynb` передаётся не JSON-патчем, а **текущими ячейками кода и текста без выводов
  и картинок** (до 15 000 символов на ноутбук);
- файлы без текстового diff (бинарные, слишком большие для GitHub) — только имя.

Охват виден **[есть]**: в комментарии студенту, если передано не всё, — «Проверено N из M
изменённых файлов; не проверено из-за объёма: …», а «существенных проблем не нашёл»
говорится только о проверенной части; на странице разбора — отдельный список «Не переданы
модели из-за объёма» и наличие `PLAN.md`.

Чего модель **не получает**:

- файлы целиком — только diff (кроме ноутбуков) **[есть]**. Концепция (раздел 4) говорит о
  «связанных с изменениями файлах» — их сбор **[нет]**;
- `README.md` (решено: там техническое), сообщения коммитов (решено: шум), данные,
  результаты, картинки;
- закрытые и снятые замечания **[нет]**.

**Итоговый diff целиком.** Каждый раз разбирается весь diff PR относительно основной
ветки, с учётом открытых замечаний проекта **[есть]** — модель видит итоговое состояние PR.
Решено так и оставить; концепция и `принятые решения.md` исправлены (раньше там было
«только новые изменения»).

## Агентный разбор (`REVIEW_MODE=agent`)

Включается переменной `REVIEW_MODE=agent`; по умолчанию `diff` — один запрос, как описано выше.
Код — `lib/agent/`, план — `агентный разбор — план.md`. Прототип: проверен бесплатными
тестами (`scripts/agent-selftest.mts`), тестовым набором на модели и вживую 2026-10-11 на
`RiddarsCorp/test` (PR #3 — ошибка вне diff найдена, новый коммит отменил разбор; PR #4 — чистый,
находок нет) и 2026-10-12 (фаза 4: параллельные PR, PR в ветку другого PR, запасной разбор после
сбоя агента, исчерпанный бюджет — см. план) **[частично]**: нет фазы 5 и проверки на настоящих
PR.

1. Контекст собирается так же (раздел выше); к нему добавляются карта репозитория и связанные
   файлы — что импортируют изменённые `.py` и ноутбуки **[частично]**.
2. Сервис скачивает архив коммита ключом приложения (до 300 МБ) во временную папку и запускает
   агента **в отдельном процессе**, в окружении которого только ключ модели (`AGENT_API_KEY`) —
   без ключа приложения и прочих секретов **[есть]**.
3. Распаковка проверяет каждую запись до записи на диск: только обычные файлы и папки; ссылки,
   пути с `../` и абсолютные пути пропускаются и перечисляются в карте; файлы больше 50 МБ
   пропускаются; при 20 000 файлов, 500 МБ записанного или 2 ГБ прочитанного распаковка
   останавливается, копия помечается неполной **[частично]**.
4. Инструменты агента — только чтение: `list_files`, `read_file` (ноутбук — его ячейки; из
   файла данных — только первые 20 строк), `grep` (обычный текст), `table_info` (сводка CSV
   потоком). Содержимое изменённых файлов данных в diff не передаётся. Путь после разрешения ссылок обязан
   лежать внутри копии **[есть]**.
5. Лимиты: 30 вызовов инструментов, 400 тысяч токенов, 10 минут на разбор (`AGENT_*`); процесс,
   переживший лимит, убивается **[частично]** (вживую лимит не достигался). Новый коммит или
   закрытие PR отменяют агента между шагами **[есть]** (вживую: прежний разбор снят через 4 с,
   его проверка завершена «Заменён новым коммитом»).
6. Новые находки перепроверяются: несуществующие `файл:строки` отбрасываются сразу, затем
   короткий запрос видит находки с настоящим текстом этих строк и отсеивает всё, что этот
   текст прямо не подтверждает;
   сбой проверки — находки остаются **[есть]**.
7. Что агент прочитал, сколько токенов потратил и что отброшено перепроверкой — в конце сырого
   ответа разбора (виден руководителю); модель в разборе помечена «(agent)» **[есть]**.
8. Ответы на комментарии студента всегда идут по diff **[есть]**.
9. Сбой агента (лимит, тайм-аут, нечитаемый ответ, ошибка скачивания или процесса) — в той же
   задаче разбор по diff; причина и токены агента — в конце сырого ответа. Агент запускается не
   больше двух раз на задачу очереди, дальнейшие повторы — сразу по diff; если PR тем временем
   сменился, запасной разбор не выполняется **[есть]**. Токены каждого разбора — агента, запросов
   по diff, перепроверки, и неудачных тоже — пишутся в базу и входят в дневные бюджеты; упавший
   процесс агента списывает расход, о котором успел сообщить, зависший — весь бюджет прогона
   **[есть]**. Режим, токены и прочитанные файлы — на
   странице разбора в панели **[есть]**.
10. Защита от враждебного содержимого репозитория: все выводы инструментов, карта, пути, цели
   ссылок и цитаты перепроверки обрезаются; поиск импортов линейный, изменённые файлы больше 1 МБ
   не сканируются; ошибки файловой системы приходят модели без путей сервера; скачивание

## Разбор ответа модели

- JSON ищется внутри блока кода, иначе — от первой `{` до последней `}`. Не разобрался —
  один повторный запрос, затем `parse_error` **[есть]**. Рассуждающие модели с фигурными
  скобками в тексте до JSON этот приём ломают.
- Находка без заголовка отбрасывается; неизвестный статус → `open`; неизвестная область →
  без области; серьёзность `high/medium/low` → `critical/important/info`, иная → без
  серьёзности; основания без `target` отбрасываются, неизвестный вид → `other` **[есть]**.
- `prior_id` принимается, **только если это замечание было передано модели в этом запросе**;
  любой другой (чужой проект, несуществующее, закрытое) → находка считается новой, а
  при сверке по комментарию отбрасывается **[есть]**. По переданному снятому замечанию
  принимается только «открыто повторно», и только если его сняла модель, а не человек;
  остальное игнорируется — снятое не превращается в новую находку **[есть]**.

## Как обновляется память

- Запись разбора (с материалами, фактическим провайдером и моделью, сырым ответом) —
  отдельным шагом **до** обработки находок **[есть]**.
- Находки и история — в одной транзакции **[есть]**:
  - новая находка → замечание со статусом «открыто» + запись истории;
  - прошлая находка → модель меняет **только статус и причину**. Область, серьёзность и суть
    фиксируются при создании; описание, основания, подтверждение, влияние и рекомендация
    обновляются, только если модель прислала непустое значение **[есть]**;
  - ответ модели «исправлено» записывается как `pending` — «исправлено, ждёт слияния» — с
    номером PR, в котором видно исправление; окончательное `closed` ставит слияние этого PR
    (ниже) **[есть]**;
  - замечания, которых модель не упомянула, не трогаются;
  - замечание остаётся привязанным к PR, где его нашли, даже если исправлено другим PR.
- Второй шаг закрытия — на `pull_request.closed` **[есть]**: PR слит в ветку по умолчанию →
  его `pending`-замечания становятся `closed` («Исправление слито в основную ветку»); закрыт
  без слияния → снова `open`; слит в другую ветку → остаются `pending`.
- Текст комментария сохраняется в разбор после публикации — отдельным шагом **[есть]**.
- Заметки о проекте **[есть]**: разбор PR их не пишет, а отвечает, станут ли они неверными
  после слияния (поле `refresh_overview`, критерии — `prompts/review.md`). Причина хранится в
  разборе; при слиянии PR в основную ветку, если разобран слитый коммит, ставится полный обзор
  (с 2026-10-18). Пока PR открыт, панель пишет в блоке «О проекте»: «После слияния PR #N куратор
  перечитает проект: причина». Каждая правка заметок — новая версия.

Если транзакция находок упадёт после записи разбора, останется разбор `ok` без находок,
проверка уйдёт в `action_required`, а повтор на том же коммите будет пропущен как «уже
разобран» **[есть]** — редкий, но тупиковый случай.

Жизненный цикл замечания:

| Статус | Когда | Кто ставит |
|---|---|---|
| `open` — открыто | найдено; или PR с исправлением закрыт без слияния; или человек вернул | модель, система, человек **[есть]** |
| `pending` — исправлено, ждёт слияния | исправление видно в diff PR | модель («исправлено») **[есть]** |
| `closed` — исправлено | PR с исправлением слит в ветку по умолчанию | система **[есть]** |
| `dismissed` — снято | объяснение студента принято; или человек закрыл как ложное | модель, человек **[есть]** |
| `reopened` — открыто повторно | проблема вернулась после закрытия или снятия | модель; закрытые модели не передаются, снятые — передаются (с 2026-10-16), и модель может вернуть снятое ею при новых основаниях; при живой проверке этапа 3 модель поставила его, **отклонив объяснение студента** — не по смыслу **[есть]** |

Решение человека **[есть]**: в досье руководитель проекта (по своим проектам) или руководитель
центра может закрыть открытое замечание как ложное или вернуть закрытое в открытые — с
обязательной причиной; в истории статуса запись помечается логином человека.

## Очередь разборов

Задачи хранятся в базе (`review_jobs`), поэтому переживают перезапуск сервиса **[есть]**.
Обработчик (`lib/curator/worker.ts`) каждые 15 секунд:

1. **Срок.** Ожидающие задачи коммитов, не выполненные за 30 минут (`REVIEW_DEADLINE_MS`), —
   проверка завершается «успех» с пометкой «Не разобрано… будет выполнен позже»; задача
   продолжает попытки **[есть]**. Выполняющуюся задачу срок не трогает — она сама завершит
   проверку.
2. **Пауза.** Задача проекта, поставленного на паузу, снимается; проверка завершается
   «проект на паузе» **[есть]**.
3. **Запуск.** Берёт готовые задачи по одной: следующий разбор начинается, только когда
   закончился предыдущий
   (`REVIEW_CONCURRENCY`, по умолчанию 1 — ради надёжности, с 2026-10-10) **[есть]**.
4. **Лимит.** Не больше 50 разборов за скользящие сутки на проект (`REVIEW_DAILY_LIMIT`):
   считаются все разборы, получившие ответ модели, в том числе «устаревшие» и с нечитаемым
   ответом; разбор — одно или два обращения к модели (второе — повтор при нечитаемом
   ответе); сбои без ответа модели не считаются. Сверх лимита проверка сразу завершается
   «Не разобрано: исчерпан дневной лимит… разбор будет выполнен, когда лимит обновится», а
   задача откладывается до освобождения лимита **[есть]**.
5. **Устаревший результат.** Если, пока модель думала, в PR пришёл новый коммит, результат
   не применяется — задача помечается заменённой **[есть]**.
6. **Повторы.** Ошибка → повтор через 1, 2, 4… минут, не чаще раза в 30 минут; через
   24 часа (`REVIEW_RETRY_WINDOW_MS`) — окончательная неудача (см. «Разбор коммита»)
   **[есть]**.

Раз в 10 минут **[есть]**:

- **сверка с GitHub** — открытые PR активных проектов (кроме черновиков и PR посторонних),
  по последнему коммиту которых не было ни разбора, ни задачи, ставятся в очередь. Так
  подбираются доставки, не дошедшие до сервиса, и события, упавшие до постановки в очередь;
- **резервная копия базы** — раз в сутки `data/backups/curator-YYYY-MM-DD.db`, хранятся 7
  последних.

При старте сервиса задачи, прерванные перезапуском, возвращаются в очередь; задача,
оставшаяся «выполняется» после сбоя внутри процесса, возвращается на следующем шаге
обработчика **[есть]**.
Тайм-аут запроса к модели — 5 минут (`LLM_TIMEOUT_MS`), к API GitHub — 30 секунд **[есть]**. Резерв провайдера: при
ошибке основного — один повтор у резервного, если задан **[есть]**.

Перезапуск разбора **[есть]**: кнопка «Перезапустить разбор» на странице проекта, в блоке
«Не разобраны» (руководитель проекта по своим проектам, руководитель центра — по всем), и
кнопка «Re-run» у проверки в GitHub (нужна подписка приложения на `check_run`). Если задача
уже ждёт в очереди (повтор или лимит) — она выполняется сразу, но лимит по-прежнему
действует; иначе ставится новая на последний коммит из GitHub. Блок «Не разобраны»
показывает только открытые PR.

## Полный обзор проекта

Код: `lib/curator/overview.ts`, `lib/curator/memory.ts` **[есть]**.

- Задача очереди вида `overview`. Хранится как разборы служебного PR с номером 0 («обзор
  проекта»): его находки, разборы, расход и бюджеты считаются проекту как обычно, в сверку с
  GitHub он не попадает.
- Поводы: подключение проекта, возобновление после паузы, кнопка «Запустить полный обзор» на
  странице проекта, разрыв памяти, слияние PR, разбор которого попросил перечитать проект.
  Автоматически (подключение, разрыв) — не чаще раза в 7 дней на проект.
- Агент работает над копией основной ветки (до 60 вызовов инструментов, 600 тыс. токенов,
  20 минут); получает открытые и снятые замечания и прошлые заметки. Новые находки
  перепроверяются по тексту файлов, как в агентном разборе. Запасного разбора по diff нет:
  сбой — один повтор, затем задача «не удалась».
- Сверка: исправленное закрывается сразу (`closed`), без требования «исправление видно в
  изменениях»; снять замечание обзор не может; новые находки — находки проекта.
- Заметки о проекте переписываются; issue «Обзор проекта (AI Curator)» — только суть проекта,
  без замечаний — создаётся или обновляется на месте и закрывается для комментариев. Замечания
  обзора студент видит в блоке «Ещё открыто в проекте» в конце каждого комментария куратора к PR. Без права Issues: write обзор
  сохраняется, на странице разбора — пометка «не опубликовано».
- Коммит памяти (`projects.memory_sha`): обзор ставит его на разобранный коммит (если слияние
  за время обзора не сдвинуло его дальше); слияние PR в основную ветку — на коммит слияния,
  если тот новее. Раз в 10 минут: коммита нет — обзор сразу; основная ветка ушла вперёд или
  история переписана — обзор, если так две сверки подряд; изменились только `.md`, `.rst` —
  коммит просто сдвигается. Сдвиг — сравнением с ожидаемым значением: гонка двух слияний или
  слияния с обзором не откатывает коммит назад.
- Обзор идёт агентом при любом `REVIEW_MODE`; без разбора моделью и агентной модели не
  ставится. В очереди — после разборов PR; стартует, только если в дневных бюджетах есть место
  на весь прогон (600 тыс. токенов). Заметки, изменённые во время прогона, не перезаписываются.

Регулярного обзора методологии (раз в две недели, с поиском публикаций) нет **[нет]**.
Проверено: самопроверки на временной базе, миграция на копии рабочей базы; с моделью и
