# Работа студента и руководителя

Обновлено: 2026-09-27. Пометки — см. `00 обзор.md`.

## Ожидаемая работа студента

1. Студент работает в своей ветке (или ветках) и открывает pull request в основную ветку.
   Напрямую в основную ветку писать нельзя — правило ветки **[есть]**.
2. Заполняет описание PR по шаблону: что сделано, зачем, как проверялось.
3. Через несколько секунд в PR появляется проверка `AI Curator` «в процессе»; слияние
   временно заблокировано **[есть]**.
4. Через время ответа модели (десятки секунд — минуты) появляется комментарий куратора, и
   проверка завершается успехом **[есть]**.
5. Студент читает замечания и делает одно из трёх:
   - **исправляет** — новым коммитом в этот же PR или в любом следующем PR;
   - **объясняет** — комментарием в PR, почему это не ошибка;
   - **игнорирует** и сливает — это разрешено, куратор совещательный **[есть]**.
6. Сливает PR. Незакрытые замечания остаются открытыми в памяти проекта и видны
   руководителю **[есть]**.

Студент панелью не пользуется. Всё, что он видит от системы, — комментарии и проверка в PR.

## Что куратор делает на каждое действие студента

| Действие студента | Событие GitHub | Что делает куратор |
|---|---|---|
| Открыл PR | `pull_request.opened` | Проверка «в процессе» → разбор → комментарий → проверка «успех» **[есть]**. Черновик — проверка сразу «успех — черновик», без разбора **[есть]** |
| Перевёл черновик в «готов к ревью» | `pull_request.ready_for_review` | Разбор, как при открытии **[есть]** |
| Добавил коммит в PR | `pull_request.synchronize` | То же. Разбирается **весь diff PR** относительно основной ветки, не только новый коммит **[есть]** (см. `04 куратор изнутри.md`) |
| Переоткрыл закрытый PR | `pull_request.reopened` | То же, если по этому коммиту ещё нет успешного разбора; иначе ничего **[есть]** |
| Написал комментарий в PR (в том числе в слитом или закрытом) | `issue_comment.created` | Принимается только от владельца, участников организации и соавторов репозитория (`author_association`); остальные игнорируются **[есть]**. Ответ сохраняется; если у проекта есть открытые замечания — сверка их статусов с учётом ответа, **без новой проверки** и без новых замечаний; короткий ответ студенту (см. ниже) **[есть]** |
| Отредактировал или удалил комментарий | `issue_comment.edited/deleted` | Ничего — событие не обрабатывается **[есть]**; учитывается первоначальный текст |
| Ответил в ветке обсуждения к строке кода или текстом ревью | `pull_request_review_comment`, `pull_request_review` | Сейчас ничего — приложение на эти события не подписано. Решено: принимать как обычный ответ студента **[нет]** |
| Изменил название или описание PR | `pull_request.edited` | Ничего **[есть]** |
| Слил PR | `pull_request.closed` (merged) | Записывается состояние «слит»; замечания, исправленные в этом PR, закрываются окончательно, если слияние в ветку по умолчанию **[есть]** |
| Закрыл PR без слияния | `pull_request.closed` | Записывается «закрыт без слияния»; замечания этого PR не считаются открытыми для проекта **[есть]** |
| Запушил в ветку без PR | `push` | Ничего — событие не подписано **[есть]** |

## Что студент видит в комментарии

Комментарий куратора (Markdown) **[есть]**:

1. Краткое описание проверенных изменений.
2. Существенные находки — по каждой: суть (заголовок), `область · серьёзность`, что не так,
   почему это важно, основания (файлы и строки, разделы документов), подтверждающий фрагмент,
   что сделать. Повторно открытые помечены.
3. «С прошлой проверки» — что исправлено или снято, с причиной.
4. Строка «Решение по каждой находке остаётся за студентом».

Если существенного нет — «Существенных методических проблем в этих изменениях не нашёл».

После ответа студента без коммита — короткий комментарий «Учёл ответ» **[есть]**: какие
замечания исправлены или сняты и «Объяснение не сняло замечание: X — причина» для тех, что
модель оставила открытыми. Если модель ничего не сказала о прошлых замечаниях или её ответ не
разобрался — молчание **[есть]**.

На каждый коммит публикуется **новый полный** комментарий со всеми находками PR **[есть]** —
при частых коммитах это шум (см. `07`, 2.3).

## Как студент объясняет

- Писать обычным комментарием в PR (не в ветке обсуждения к строке — такие не учитываются).
- Объяснение привязывается к PR, а не к конкретному замечанию **[есть]**: модель сама
  понимает, к какому замечанию оно относится.
- Объяснение снимает замечание (`dismissed`), только если модель сочла его убедительным
  по существу **[есть]**. Снятые замечания руководитель видит отдельной выделенной группой —
  это решение модели, которое человек перепроверяет **[есть]**.
- Объяснить замечание из **прошлого** PR можно комментарием в текущем PR **[есть]**: модель
  получает открытые замечания всего проекта. Но ответы студента передаются модели только из
  текущего PR **[есть]**.

## Работа руководителя проекта

Руководитель заходит в панель (логин и пароль от руководителя центра) и видит только свои
проекты **[есть]**.

Типичные вопросы и где ответ:

| Вопрос | Где |
|---|---|
| Что куратор нашёл у моих студентов? | Главная: число открытых замечаний, красное — если есть критичные. Страница проекта: список открытых |
| Что обсудить со студентом? | Досье замечания: что не так, почему важно, основания, что сделать, ответы студента |
| Согласен ли я с тем, что модель сняла по объяснению студента? | Страница проекта → «Закрытые замечания» → «Сняты по объяснению студента» (выделены) |
| Студент вообще работает? | «Последняя активность» на главной и в шапке проекта; история разборов |
| На чём основан вывод модели? | Страница разбора: опубликованный комментарий, что получила модель |
| Где исправлено замечание? | Досье: «исправлено в PR #N» (и «ждёт слияния», пока PR не слит), история статуса со ссылками на разборы |
| Не согласен с моделью? | Досье, «Решение руководителя»: закрыть открытое как ложное или вернуть закрытое в открытые, с обязательной причиной; в истории — с логином **[есть]** |

Чего руководитель **не может** в панели:

- оставить свою заметку к замечанию **[нет]**;
- получить сводку без захода в панель — регулярная сводка раз в две недели **[нет]**.
  Решено отложить до запуска на реальных проектах: сначала посмотреть, заходят ли
  руководители в панель сами;
- менять серьёзность замечания — решено: не нужно (серьёзность не меняет ни модель, ни
  руководитель).

Руководитель может комментировать PR на GitHub, но его комментарий куратор считает ответом
студента **[есть]** — см. `07 нештатные ситуации.md`.

## Работа руководителя центра

То же, что у руководителя проекта, по всем проектам, плюс **[есть]**:

- столбец «Руководитель» и фильтр по нему, «без руководителя»;
- «Управление»: проекты (добавить, переименовать, пауза, удалить, назначить руководителей),
  учётки (создать, изменить, пароль, отключить, удалить).

Бейджи сбоев «слияние заблокировано» и «сбой разбора» на главной видят **обе роли** **[есть]**.
Действия при сбое — см. `07 нештатные ситуации.md`, «Сбои».
