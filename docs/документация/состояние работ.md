# Состояние работ

Обновлено: 2026-08-26.

## Где мы сейчас

Первый этап пройден, начат второй. В репозитории есть работающий каркас сервиса на Next.js,
который проходит связку GitHub → сервис → обязательная проверка → комментарий из конца в
конец. Разбор выполняет один из двух ревьюеров (переменная `CURATOR_REVIEWER`): `simulate` —
заглушка без модели (по умолчанию), `provod` — реальный разбор языковой моделью через шлюз
provod.ai.

Что уже реализовано:

- `POST /api/github/webhook` — приём событий GitHub с проверкой HMAC-подписи; реагирует на
  pull request (`opened`, `synchronize`, `reopened`).
- Аутентификация как GitHub App: JWT (RS256) из `appId` и приватного ключа, обмен на
  installation-токен с кэшированием (`lib/github/auth.ts`).
- Создание обязательной проверки `AI Curator` со статусом `in_progress` на head-коммите PR —
  именно она блокирует слияние.
- Публикация ответа в pull request и завершение проверки.
- Ревьюер `simulate`: заглушка `SIMULATED_ANSWER` (`lib/curator/simulate.ts`) с режимами
  через `CURATOR_SIM_MODE` — `manual` (ждём ручного завершения), `auto-approve` (успех через
  задержку), `auto-block` (блокировка через задержку), `offline` (событие игнорируется —
  сценарий недоступного сервиса). `POST /api/simulate/conclude` (защищён `SIM_ADMIN_TOKEN`)
  завершает проверку вручную.
- Ревьюер `provod`: реальный разбор языковой моделью. `lib/llm/provod.ts` — вызов
  OpenAI-совместимого шлюза provod.ai без стриминга; `lib/curator/provod-review.ts` — сбор
  изменённых файлов PR и `RESEARCH.md`, промпт куратора (методические ошибки на стыке химии и
  ML), публикация комментария и завершение проверки. При сбое модели слияние остаётся
  заблокированным. **Вживую против модели ещё не проверено** — нужен `PROVOD_API_KEY`.
- `GET /api/health` — проверка живости. Конфигурация через переменные окружения, см.
  `.env.local.example`.

Чего в коде ещё нет: базы данных и памяти проекта (этап 3), ежемесячного обзора (этап 4),
панели руководителя (этап 5).

**Инфраструктура и живая проверка.** Первый этап прогнан на настоящем GitHub, и его цель
достигнута:

- Создана организация `RiddarsCorp` с шаблоном `project-template` (файлы `RESEARCH.md` —
  описание исследования, `PLAN.md`, `README.md`, `.github/PULL_REQUEST_TEMPLATE.md`) и
  тестовыми репозиториями `test-project-1`, `test-project-2`.
- GitHub App зарегистрирован и запускался вживую; на PR #1 в `test-project-1` опубликован
  реальный комментарий проверки.
- Подтверждено главное: обязательная проверка `AI Curator` **реально блокирует слияние** до
  своего завершения. Этим снят ключевой риск — работает ли защита ветки с обязательной
  проверкой от GitHub App на бесплатном плане в открытом репозитории.

Чего по инфраструктуре ещё нет: постоянного развёртывания. Во время проверки сервис
поднимался локально, а вебхуки прокидывались через туннель; постоянного адреса (сервер
университета) пока нет.

## Что дальше

Первый этап по сути закрыт: связка с GitHub и блокировка слияния проверены вживую. Осталась
одна инфраструктурная задача — развернуть сервис на постоянном адресе вместо локального
запуска через туннель; её можно сделать в любой момент, разработку она не блокирует.

Второй этап начат: заглушку заменил реальный разбор через provod.ai. Ближайшее по нему —
проверить разбор вживую (нужен `PROVOD_API_KEY`), настроить промпт и фильтрацию находок на
реальных PR. Дальше — третий этап: память проекта на SQLite (хранение находок, их статусов,
ответов студентов, история проверок и повторная проверка исправлений).

## Чего не хватает

Это не проектные решения, а сведения и материалы, без которых не сдвинуть следующие шаги.
Спроси у пользователя.

- **Ключ provod.ai** (`PROVOD_API_KEY`, вида `sk_...`) и то, из какого бюджета он
  оплачивается. Нужен, чтобы включить реальный разбор (`CURATOR_REVIEWER=provod`) и проверить
  его вживую.
- **Проверочные списки методических ошибок.** В `docs/видение/идея и мотивация.md` они
  названы главной ценностью системы, но не написаны ни в каком виде. Содержательный разбор
  второго этапа без них беспредметен.
- Доступ к серверу университета: постоянный адрес, доступный извне, и кто им распоряжается.
  Нужен, чтобы развернуть сервис вместо локального запуска через туннель.
- Кто именно тот «ответственный сотрудник», который снимает блокировку вручную.

## Не решено

Пункты, помеченные в документах как открытые или названные предварительной гипотезой.

**Правила статуса внимания.** Набор показателей и пороги, по которым проект помечается как
требующий внимания, — гипотеза (раздел 7). Возможен более простой вариант, при котором
система показывает руководителю фактические данные без собственной оценки.

**Уровни серьёзности находок** уточняются после запуска на реальных проектах (раздел 10).

**Формат досье проблемы.** Состав полей будет подбираться на практике (раздел 7).

**Способ доставки сводки руководителю** — почта, мессенджер или отдельная страница внутри
панели (раздел 7).

**Поведение после паузы проекта.** Переключатель подключения проекта к системе описан, но
не решено, что происходит с накопленными замечаниями и нужен ли полный разбор при
возобновлении работы (раздел 7).

**Оценка расходов** $100–250 в месяц на тридцать проектов — предварительная гипотеза
(раздел 9). Распределение задач по классам моделей там же подано как предложение, а не как
решение.

**Состав списков в разделах, помеченных «этот список не финальный»** — разделы 5, 6 и 7.

**Необязательные возможности**, про которые сказано «может быть»: представление проектов
карточками в дополнение к таблице и показ последовательности шагов от ошибки до результата
в досье (раздел 7).

## Расхождения в документах

Ниже — места, где документы противоречат друг другу или обсуждению. Требуют решения
пользователя; пока решения нет, ничего не переписывать.

**Автоматические проверки кода.** В обсуждении прозвучало, что универсальные формальные
проверки вряд ли применимы: студенты работают в разных форматах — модули, ноутбуки,
смешанные структуры, — и делать проверки под каждый проект отдельно в задачу не входит.
Из описания анализа изменений (раздел 4) они убраны, но упоминания остались в трёх местах
`детализированная концепция.md`: в разделе 1 («запускает автоматические проверки»), в
перечне того, что задаёт шаблон репозитория (раздел 2) и в пятом шаге процесса проверки
pull request (раздел 3). Требуется решение: либо вернуть автоматические проверки в описание,
либо убрать эти упоминания.

**Оценка уверенности модели.** В разделе 4 она описана как утверждённая часть модели данных,
в `docs/видение/идея и мотивация.md` названа принципиально важной. В обсуждении прозвучало, что сам
механизм — предварительная гипотеза и от него можно отказаться. Противоречие не разрешено.

**Научные базы для поиска публикаций.** Раздел 5 говорит о поиске научных публикаций, но
конкретные источники нигде не названы и вопрос нигде не помечен как открытый. В обсуждении
прозвучало, что базы заранее не фиксируются и предполагается свободный поиск. В документе
это не отражено.

**Закрытые репозитории в раннем документе.** `docs/видение/концепция.md` описывает репозитории как
закрытые. Решение изменено на открытые, см. `принятые решения.md`.

**Провайдер языковой модели.** `детализированная концепция.md` называет исполнителем анализа
API Anthropic (раздел 8), и оценка расходов (раздел 9) построена на тарифах Anthropic. В
реализации по решению пользователя используется шлюз provod.ai (пока — вместо прямого
Anthropic). Требуется решение: внести provod в `принятые решения.md` и поправить разделы 8–9
детализированной концепции (провайдер и оценка расходов).
