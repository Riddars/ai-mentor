# Состояние работ

Обновлено: 2026-09-27.

## Где мы сейчас

Первый и второй этапы пройдены и проверены вживую на настоящем GitHub. В репозитории есть
работающий сервис на Next.js, который проходит связку GitHub → сервис → обязательная
проверка → комментарий из конца в конец. Разбор выполняет один из двух ревьюеров (переменная
`CURATOR_REVIEWER`): `simulate` — заглушка без модели (по умолчанию), `llm` — реальный разбор
языковой моделью через сменный провайдер (сейчас provod.ai).

Что уже реализовано:

- `POST /api/github/webhook` — приём событий GitHub с проверкой HMAC-подписи; реагирует на
  pull request (`opened`, `synchronize`, `reopened` — разбор; `closed` — только запись
  состояния) и на `issue_comment` (ответ студента). Только для проектов, подключённых в
  управлении; проекты на паузе не разбираются.
- Аутентификация как GitHub App: JWT (RS256) из `appId` и приватного ключа, обмен на
  installation-токен с кэшированием (`lib/github/auth.ts`).
- Создание обязательной проверки `AI Curator` со статусом `in_progress` на head-коммите PR —
  именно она блокирует слияние.
- Публикация ответа в pull request и завершение проверки.
- Ревьюер `simulate`: заглушка `SIMULATED_ANSWER` (`lib/curator/simulate.ts`) с режимами
  через `CURATOR_SIM_MODE` — `manual` (ждём ручного завершения), `auto-approve` (успех через
  задержку), `auto-block` (блокировка через задержку), `offline` (событие игнорируется —
  сценарий недоступного сервиса). `POST /api/simulate/conclude` (защищён `SIM_ADMIN_TOKEN`)
  завершает проверку вручную.
- Ревьюер `llm`: реальный разбор языковой моделью, провайдер-нейтрально. `lib/llm/chat.ts` —
  диспетчер по `LLM_PROVIDER` (provod/selectel/openai/openrouter — OpenAI-совместимые) с
  резервом на один повтор (`LLM_FALLBACK_PROVIDER`); переход на Claude позже = один адаптер.
  `lib/curator/review.ts` — сбор изменённых файлов PR и `RESEARCH.md`, промпт куратора
  (методические ошибки на стыке химии и ML), публикация комментария и завершение проверки.
  Находки публикуются комментарием и **не блокируют** слияние — куратор совещательный (см.
  `принятые решения.md`); блокировка сохраняется только при недоступности сервиса. Сквозной
  прогон через GitHub выполнен вживую: на PR с намеренной утечкой данных (масштабирование
  признаков до train/test split) модель точно указала ошибку, её последствия и способ
  исправления, опубликовала комментарий и завершила проверку.
- `GET /api/health` — проверка живости. Конфигурация через переменные окружения, см.
  `.env.local.example`.
- **Память проекта (этап 3)** реализована и проверена вживую. Хранилище на встроенном
  `node:sqlite` (`lib/db/index.ts`, путь — `DATABASE_PATH`, по умолчанию `./data/curator.db`),
  репозиторий `lib/curator/store.ts`. Таблицы: проекты, участники, pull requests, прогоны
  разбора (`analyses`), находки (`findings`) со статусами, история смены статусов
  (`finding_status_history`), ответы студентов, события GitHub (идемпотентность по
  `X-GitHub-Delivery`). Разбор (`lib/curator/review.ts`) переведён на структурированный
  (JSON) ответ модели: сохраняет находки, сверяет их с открытыми находками всего проекта
  (сверку делает сама модель; исправление может прийти в следующем PR — с 2026-09-27),
  ведёт жизненный цикл open → closed / dismissed / reopened и историю. Ответ студента без
  коммита обрабатывается через `issue_comment` (сверка по объяснению, без нового check-run).
  Уверенность модели не хранится (см. `принятые решения.md`).

- **Панель руководителя (этап 5)** — вторая версия, переработанная «от задачи
  руководителя» после того, как первая (дашборд с KPI, графиками и статусом внимания) была
  отвергнута как надуманная. Вход по логину/паролю, роли `head` / `supervisor` с одним
  интерфейсом и разной областью видимости; таблица проектов с фактами и сортировкой;
  страница проекта (открытые замечания, сворачиваемые закрытые, история разборов); досье;
  страница разбора (опубликованный комментарий, изменения по замечаниям, что получила
  модель); полный CRUD в управлении (проекты, учётки, пароли, удаление с подтверждением).
  Статусы проекта — `active` | `paused`, «архив» убран. Заодно три правки куратора:
  разбираются только подключённые проекты, пауза отключает разбор, вебхук пишет закрытие PR.
  Проверено локально (сборка, миграция, роли, действия через формы, вебхук подписанными
  запросами); вживую на GitHub правки вебхука не гонялись. Подробности —
  `панель руководителя.md`.
- **Универсальное замечание** (2026-09-27): фиксированная область из восьми, три уровня
  серьёзности, список оснований вместо «файл:строки», поле «что не так»; промпт, разбор ответа
  модели, комментарий в PR и панель переведены на эту структуру (миграция `user_version 6`).
  Интерфейс очищен от пояснений, мини-полоски, таблицы PR и итога под таблицей. Находка
  принадлежит проекту: разбор любого PR получает открытые находки всего проекта и может
  закрыть находку из прошлого PR; в досье видно, в каком PR она исправлена. Новый промпт на
  реальном PR ещё не прогонялся.

Чего в коде ещё нет: ежемесячного обзора (этап 4); регулярной сводки руководителю.

## Что дальше

Первый этап по сути закрыт: связка с GitHub и блокировка слияния проверены вживую. Осталась
одна инфраструктурная задача — развернуть сервис на постоянном адресе вместо локального
запуска через туннель; её можно сделать в любой момент, разработку она не блокирует.

Второй этап пройден: заглушку заменил реальный разбор языковой моделью (сейчас provod.ai),
сквозной прогон на реальном PR подтверждён вживую. Ближайшее по нему — проверочные списки
методических ошибок и настройка промпта на реальных примерах.

Третий этап (память проекта) пройден и проверен вживую на настоящем PR в
`RiddarsCorp/test-project-1`. Подтверждено из конца в конец: событие PR с утечкой → находка
сохранена как `open` и опубликован комментарий; правящий коммит → та же находка переведена в
`closed` с обоснованием модели; объяснение студента комментарием (через `issue_comment`) →
находки переведены в `dismissed`/`closed`, причём слабое, не подтверждённое кодом объяснение
модель обоснованно отклонила (`reopened`). Отработали и история смены статусов, и дедуп
повторных доставок вебхука. В настройках GitHub App включена подписка на **Issue comment**
(с разрешением Issues: Read) — без неё объяснения студента без коммита до сервиса не доходят.

Пятый этап (панель руководителя) доведён до третьей итерации по замечаниям пользователя к
интерфейсу; ближайшее — прогнать вживую на `RiddarsCorp/test-project-1` правки вебхука
(ворота подключения, пауза с check-run `success`, запись закрытия PR) и новый промпт
(комментарий в новой структуре, разбор в истории, закрытие находки слитого PR следующим PR);
см. `панель руководителя.md`. Остаётся четвёртый этап (ежемесячный обзор) и регулярная сводка.
Открытая инфраструктурная задача прежняя: постоянное развёртывание вместо локального
запуска через туннель.

Локальная dev-база: при проверке каскадного удаления 2026-09-14 память тестового проекта
`RiddarsCorp/test-project-1` (данные живой проверки этапа 3) была удалена, а снимок для
отката не сохранился. Для повторной живой проверки проект нужно подключить в `/admin`

## Чего не хватает

Это не проектные решения, а сведения и материалы, без которых не сдвинуть следующие шаги.
Спроси у пользователя.

- **Бюджет на модель.** Ключ provod.ai получен, проверен и оплачивается — остаётся уточнить,
  из какого бюджета. Учётки GitHub App (`GITHUB_APP_ID`, приватный ключ) в `.env.local`
  заполнены, сквозной прогон выполнен.
- **Проверочные списки методических ошибок.** В `docs/видение/идея и мотивация.md` они
  названы главной ценностью системы, но не написаны ни в каком виде. Содержательный разбор
  второго этапа без них беспредметен.
- Доступ к серверу университета: постоянный адрес, доступный извне, и кто им распоряжается.
  Нужен, чтобы развернуть сервис вместо локального запуска через туннель.
- Кто именно тот «ответственный сотрудник», который снимает блокировку вручную.

## Не решено

Пункты, помеченные в документах как открытые или названные предварительной гипотезой.

**Уровни серьёзности и список областей находок** — приняты три уровня и восемь областей
(2026-09-27), но уточняются после запуска на реальных проектах (раздел 10).

**Формат досье проблемы.** Состав полей будет подбираться на практике (раздел 7).

**Способ доставки сводки руководителю** — почта, мессенджер или отдельная страница внутри
панели (раздел 7). Отложено до запуска на реальных проектах: сначала посмотреть, заходят ли
руководители в панель сами.

**Сброс пароля руководителя центра.** Если `head` забыл пароль — только вручную в БД
(bootstrap из `HEAD_PASSWORD` работает лишь при пустой таблице пользователей). Отсюда же
ловушка: если демо залито до первого входа при заданном `HEAD_LOGIN`, учётка `head` из env
не создаётся никогда, а сообщения об этом нет.

**Комментарии к проекту на паузе** сейчас не сохраняются (вебхук пропускает проект целиком).
Сохранять ли ответы без сверки — не решено.

**Страница «Статистика» центра** — распределение находок по областям для методической
работы (какие ошибки студентов самые частые). Отложено до накопления реальных данных.

**Подсветка кода в досье (Shiki)** — когда будут храниться реальные фрагменты кода.

**Столбцы «этап исследования», «регулярность коммитов», «дата обзора»** в таблице проектов
(раздел 7) — нет источников данных до этапа 4 и до отслеживания коммитов вне PR.

**Оценка расходов** $100–250 в месяц на тридцать проектов — предварительная гипотеза
(раздел 9). Распределение задач по классам моделей там же подано как предложение, а не как
решение.

**Состав списков в разделах, помеченных «этот список не финальный»** — разделы 5, 6 и 7.

**Необязательные возможности**, про которые сказано «может быть»: представление проектов
карточками в дополнение к таблице и показ последовательности шагов от ошибки до результата
в досье (раздел 7).
