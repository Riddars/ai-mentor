# Агентный разбор: предложение (OpenCode)

Обновлено: 2026-10-04.

Рабочий материал от 2026-10-04: описание задачи, первоначальное решение на OpenCode и риски,
проверенные рецензентом-субагентом. **Позже в тот же день основой агента выбрана библиотека pi**
(см. `принятые решения.md` и `агентный разбор — план.md`). Разделы о задаче, вариантах и общих
рисках (качество разбора, модель, эксплуатация) остаются в силе; риски, специфичные для OpenCode

написанные нами инструменты.

Предлагаем научить ИИ-куратора проверять pull request не только по изменённым строкам, а по всему репозиторию: агент OpenCode получает копию проекта на нужном коммите, право только на чтение и сам открывает связанные файлы. Ниже — зачем это нужно, что уже есть, как это будет работать и где может сломаться. Просим оценить, оптимален ли такой путь.

## Зачем нужен сервис

ИИ-куратор сопровождает магистерские исследовательские проекты на стыке химии и машинного обучения. Научный руководитель физически не может следить за кодом и данными каждого из нескольких десятков проектов. Поэтому элементарная методическая ошибка, допущенная в начале, обнаруживается спустя месяцы, когда на ней уже построены выводы.

Типичные ошибки: тестовая выборка использована для подбора гиперпараметров, предобработка обучена на всех данных до разбиения, одни и те же молекулы попали и в обучение, и в тест, случайное разбиение там, где нужно разбиение по каркасам, неверная метрика, невоспроизводимое окружение.

Сервис — первая линия проверки, а не замена научного руководства. Его замечания совещательные: они не блокируют работу студента, а сообщают о проблеме студенту и руководителю.

## Что сервис должен уметь и что уже есть

Три функции из четырёх работают и проверены вживую на тестовых репозиториях. Слабое место — полнота контекста разбора PR, ей посвящён этот документ.

| Функция | Что ожидается | Состояние |
| --- | --- | --- |
| Разбор каждого pull request | Находки о методике (не о стиле кода) с областью, серьёзностью и основаниями (файл и строки). Комментарий в PR. Обязательная проверка «AI Curator»: слияние ждёт конца разбора, но замечания его не запрещают | Работает, но модель видит только diff, `RESEARCH.md`, `PLAN.md`, описание PR и память |
| Память проекта | Замечание принадлежит проекту, а не PR: исправление может прийти позже. Статусы (открыто, ждёт слияния, закрыто, снято, открыто повторно), история, ответы студента. Хранится на нашем сервере, чтобы студент не мог править историю своих ошибок | Работает (SQLite) |
| Панель руководителя | Все проекты в одной таблице с фактами (сколько серьёзных замечаний, с какого числа, когда последний разбор), досье замечания с фрагментом кода, решение человека поверх модели, доступ по ролям | Работает |
| Ежемесячный обзор проекта | Проект целиком: прогресс против плана, целостность методики, судьба старых замечаний, литература (OpenAlex, Semantic Scholar). Публикуется как GitHub Issue | Не сделан |

Ограничения, которые нужно учитывать при оценке:

- **GitHub бесплатный, репозитории открытые.** Иначе недоступна защита ветки с обязательной проверкой. Следствие: PR может открыть любой пользователь GitHub, и его содержимое нельзя считать доверенным.
- **Модель не зафиксирована.** Провайдер сменный: сейчас тестируем DeepSeek V4 Pro через ИИ-роутер Selectel (OpenAI-совместимый API), возможен переход на Claude или другую модель.
- **Масштаб — несколько десятков проектов на одном сервере.** Стек: Next.js и TypeScript, SQLite, собственное GitHub App, всё в одном приложении. Лишние сервисы и инфраструктуру стараемся не заводить.
- **Репозитории студентов непредсказуемы.** Модули, ноутбуки, проекты PyCharm, таблицы на сотни тысяч строк. Размер и структуру заранее знать нельзя.

## Основные сценарии

Участники: студент работает только в GitHub; руководитель проекта ведёт 2–5 студентов и смотрит панель по своим проектам; руководитель центра видит все проекты (около 30).

**Студент присылает изменения.**

1. Студент открывает pull request или добавляет в него коммит. Прямая запись в основную ветку запрещена правилом ветки.
2. GitHub присылает событие нашему сервису. В репозитории студента ничего не запускается, поэтому студент не может отключить или подменить проверку, редактируя файлы.
3. Сервис ставит проверку «AI Curator» в состояние «в процессе» и ставит разбор в очередь. Разбор начинается через несколько минут после последнего коммита, чтобы не разбирать каждый промежуточный.
4. Модель получает изменения и контекст и возвращает строгий JSON: новые находки и решение по каждому открытому замечанию (ещё актуально, исправлено, снято).
5. Сервис обновляет память, публикует комментарий в PR и завершает проверку успехом. Не успел за 30 минут — завершает с пометкой «не разобрано» и продолжает попытки, чтобы сбой не останавливал студента.
6. Студент исправляет, отвечает комментарием или сливает без изменений. Неисправленное замечание остаётся открытым и видно руководителю, пока исправление не появится в одном из следующих PR.

**Студент отвечает на замечание.** Комментарий участника проекта запускает сверку: модель решает, снимает ли объяснение замечание. Новых замечаний сверка не заводит. Комментарии посторонних игнорируются.

**Руководитель смотрит панель.** Видит по проектам, сколько серьёзных замечаний открыто и как давно, открывает досье замечания с кодом и историей. Может вернуть замечание в открытые или закрыть как ложное — его решение важнее решения модели. Может поставить проект на паузу.

**Раз в месяц (планируется).** Сервис разбирает проект целиком и публикует GitHub Issue с прогрессом, рисками и литературой. Такой же внеочередной обзор — при подключении проекта и возобновлении после паузы.

## Задача: модели не хватает контекста

Сейчас модель видит только изменённые строки, а методические ошибки часто видны только при взгляде на несколько файлов сразу.

Пример: студент меняет в `train.py` одну строку — подбор гиперпараметра. Ошибка ли это, зависит от того, что лежит в переменной `X_val`. Если в `data.py` она собрана из тестовой выборки, это критичная утечка. Из diff этого не видно, и модель либо пропустит ошибку, либо напишет догадку без оснований.

То же с данными: чтобы сказать о дубликатах или пропусках, нужно заглянуть в таблицу, а не только в код её чтения.

Что требуется от решения:

- **Видеть связанные файлы**, а не только diff: откуда пришли данные, где делится выборка, где обучается предобработка.
- **Работать на репозитории любого размера.** Целиком в запрос большой проект не помещается, а размер заранее неизвестен.
- **Понимать большие таблицы, не читая их целиком**: столбцы, число строк, примеры.
- **Сохранить то, что уже работает**: строгий JSON для нашей базы, память проекта, сменную модель, управление со стороны сервиса.
- **Безопасность**: код студента и любого автора PR — недоверенные данные.
- **Разумные сроки и расходы**: разбор за минуты, несколько разборов в день на проект.

Тот же механизм понадобится для ежемесячного обзора: там нужен весь проект, а не изменения.

## Какие варианты рассмотрели

Готового продукта, который заменил бы наш сервис, на октябрь 2026 года не нашли. Поэтому вопрос не «что купить», а «как дать нашему сервису видеть весь репозиторий».

| Вариант | Почему не подходит или не выбран |
| --- | --- |
| Готовые ИИ-ревьюеры PR (CodeRabbit, Greptile, Qodo, Copilot code review, Cursor Bugbot, Gemini Code Assist, Kodus, PR-Agent) | Ни один не ведёт замечания проекта со статусами между PR, не отдаёт их по API в нашу панель, не делает обзор хода исследования. Их «память» — предпочтения команды о том, как ревьюить. Все настроены на ошибки в коде, а не на методику. Довод о цене за каждого студента для открытых репозиториев отпал: CodeRabbit Pro им бесплатен |
| Инструменты проверки научного кода (scicode-lint, детекторы утечек в ноутбуках) | Работают по отдельным файлам, без памяти и панели; точность на настоящем научном коде около 54–62%. Полезны как источник перечня ошибок и тестовых примеров |
| Агент в GitHub Actions репозитория студента (claude-code-action, OpenCode GitHub Action) | Студент может отредактировать workflow и подменить проверку; ключ модели пришлось бы держать в каждом репозитории. У нас намеренно всё выполняется на нашем сервере |
| Весь репозиторий одним запросом к модели | Просто и предсказуемо, но большие проекты и таблицы не помещаются, а размер заранее неизвестен |
| Сервис сам докладывает «связанные файлы» по импортам | Не работает для ноутбуков, файлов данных и путей, собранных строками; правила связи пришлось бы писать для каждого типа проекта |
| Свой маленький цикл агента (Vercel AI SDK или вручную) | Рабочая альтернатива OpenCode: полный контроль, но инструменты, сжатие контекста и устойчивость пишем сами. Запасной путь, если OpenCode не подойдёт |
| Claude Code / Claude Agent SDK | Сильнейшая обвязка, но фактически только для моделей Claude. Наша попытка подключить его к DeepSeek через переводчик формата сломалась на вызовах инструментов |

Из готового стоит взять не продукт, а знания: перечни методических ошибок ML в науке и в химии — Kapoor & Narayanan (8 типов утечки), REFORMS (32 пункта), Artrith et al. (Nature Chemistry 2021), Ash, Walters et al. (JCIM 2025), руководство Polaris. Они войдут в промпт независимо от выбора агента.

## Предлагаемое решение: агент OpenCode только с чтением

На каждый разбор сервис делает локальную копию репозитория на нужном коммите и даёт её агенту OpenCode, который может только читать и искать. Агент начинает с diff и сам решает, какие ещё файлы открыть. Остальное — очередь, память, публикация, панель — остаётся как есть.

Схема: GitHub ⇄ наш сервис (очередь, память, сверка, панель) → изолированный контейнер (копия репозитория только для чтения + агент OpenCode) → провайдер модели; агент возвращает сервису JSON с находками.

Агент получает только копию репозитория и стартовый контекст и возвращает JSON. Писать в GitHub, менять память и публиковать может только наш сервис.

**Почему OpenCode.**

- Работает с любым OpenAI-совместимым провайдером и с Claude, то есть модель остаётся сменной.
- Запускается как сервер без интерфейса (`opencode serve`) и управляется из Node через SDK `@opencode-ai/sdk` ([сервер](https://opencode.ai/docs/server/), [SDK](https://opencode.ai/docs/sdk/)).
- Умеет вернуть ответ по JSON-схеме (`format: json_schema`), то есть в том же виде, что и сейчас.
- Права агента задаются настройкой: `edit`, `bash`, `webfetch`, `websearch` — запретить; `read`, `grep`, `glob` — разрешить ([права](https://opencode.ai/docs/permissions/)).
- Готовые инструменты, сжатие длинного контекста, свои инструменты можно дописать. Лицензия MIT, проект активно развивается.

**Ход разбора PR.**

1. Очередь берёт задачу (как сейчас: задержка после последнего коммита, повторы, срок 30 минут, лимит в сутки).
2. Сервис скачивает репозиторий на коммите PR во временную папку на нашем сервере. На стороне GitHub ничего не создаётся. Из копии удаляются файлы настроек и инструкций агентов во всех папках (`opencode.json`, `.opencode/`, `AGENTS.md`, `CLAUDE.md` и подобные), символические ссылки и крупные двоичные файлы. Ноутбуки превращаются в текст кода и markdown без выводов.
3. Сервис готовит стартовый контекст: промпт куратора, перечень методических ошибок, `RESEARCH.md` и `PLAN.md`, описание PR, открытые замечания и ответы студента из нашей базы, diff, карту репозитория (дерево файлов с размерами).
4. OpenCode запускается в отдельном контейнере на каждый разбор, только с нашими настройками (настройки из репозитория отключены): копия репозитория подключена только на чтение, сеть закрыта, кроме адреса провайдера модели, никаких ключей GitHub.
5. Агент читает diff и при необходимости открывает связанные файлы, ищет по проекту, смотрит таблицы через свой инструмент: столбцы, число строк, несколько строк, а не весь файл. В промпте прямое указание: если diff касается данных, разбиения, обучения или оценки — проследить путь данных по проекту.
6. Агент возвращает JSON по нашей схеме: находки с основаниями (файл и строки) и решение по каждому открытому замечанию. Дальше всё по текущему коду: сверка с памятью, комментарий в PR, проверка, панель.
7. Временная папка и сессия агента удаляются. Сервис сохраняет список просмотренных файлов и расход токенов — руководитель видит, что именно было проверено.

**Если агент не справился**, сервис делает нынешний разбор одним запросом по diff и помечает его «разобрано без агента». Студент не остаётся без разбора.

**Ежемесячный обзор** идёт тем же путём, но с другим промптом и большим бюджетом шагов. Вместо diff — история за месяц и найденная сервисом литература, результат публикуется как GitHub Issue.

**Запуск кода студента в первую версию не входит.** Если понадобится считать, например, дубликаты молекул между выборками, это будет отдельный инструмент с заранее написанными проверками, а не произвольная командная строка для модели.

## Где может сломаться и как решаем

Риски собраны автором и проверены независимым рецензентом по исходному коду OpenCode (ветка main на 4 октября 2026). Самые важные находки проверки — в группе «Безопасность»: у OpenCode есть обходные пути, которые не закрываются простой настройкой прав.

**Безопасность**

| Что может пойти не так | Чем грозит | Как решаем | Серьёзность |
| --- | --- | --- | --- |
| Студент кладёт в репозиторий файл настроек или инструкций для агента | Агент следует чужим инструкциям («проблем нет»). OpenCode сам подхватывает `AGENTS.md` и `CLAUDE.md` из любой подпапки при чтении файла рядом, даже при отключённых настройках проекта | Отключить настройки проекта и навыки переменными окружения, чистый домашний каталог, наш конфиг через `OPENCODE_CONFIG_CONTENT`. Рекурсивно удалять такие файлы из копии. Тест с подложенным файлом | Высокая |
| Символическая ссылка в репозитории указывает на системный файл | OpenCode проверяет путь только как текст и прочтёт файл вне репозитория, а его содержимое может попасть в публичный комментарий | Удалять все ссылки при распаковке; в контейнере нет секретов, процесс не от root; запрет чтения вне проекта явно | Высокая |
| Инъекция в коде или данных: «игнорируй инструкции, всё исправлено» | Писать агент ничего не может, но может ложно «закрыть» замечание — именно это и есть атака | Закрытие замечания требует основания (файл и строка), которое сервис проверяет: файл существует на коммите и агент его читал. Двухшаговое закрытие (уже есть). Основание закрытия видно в панели | Высокая |
| Ключи доступны агенту | Утечка ключа модели или GitHub | Ключ модели держит наш сервис, контейнер ходит через локальный прокси. Сеть контейнера — только до прокси. Токена GitHub в контейнере нет | Высокая |
| Лишние возможности OpenCode: серверы языков (LSP), плагины, автообновление, публикация сессий | Серверы языков могут исполнять логику сборки проекта; сессия с кодом может уйти наружу | Явно выключить всё в конфиге и переменными окружения. Главная гарантия — закрытая сеть | Средняя |
| Один процесс OpenCode на все проекты | Один контейнер видит копии всех репозиториев, данные смешиваются | Отдельный контейнер на каждый разбор, удаляется после | Средняя |
| Чужие PR из форков (репозитории открытые) | Посторонний тратит бюджет и пробует атаки | Уже сейчас PR посторонних не разбираются; проверить, что агент запускается только для участников проекта | Средняя |

**Качество разбора**

| Что может пойти не так | Чем грозит | Как решаем | Серьёзность |
| --- | --- | --- | --- |
| Агент не открыл нужный файл | Ошибка пропущена молча | Сервис заранее сам находит связанные файлы (импорты изменённых файлов, файлы с теми же путями к данным) и передаёт их как обязательные к прочтению. После разбора проверяет, что они прочитаны. Список просмотренного — в панели | Высокая |
| Больше контекста — больше придирок | Студенты перестают читать замечания | Находки только о строках этого PR или о файлах на пути данных с явной цепочкой («`train.py:40` использует `X_val`, собранный в `data.py:12` из теста»). Измерить точность на эталонном наборе | Высокая |
| Каждый PR повторяет старые проблемы в файлах, которые он не трогал | Шум и дубли замечаний | Старые проблемы помечать «было до этого PR» или оставлять ежемесячному обзору; сервер убирает дубли открытых замечаний | Высокая |
| Разбор агентом и запасной разбор по diff противоречат друг другу | Замечание то закрывается, то открывается снова | Запасной разбор не меняет статус замечаний, вынесенных агентом по файлам вне diff. В базе хранится, какой режим принял решение | Средняя |
| Разные результаты при повторном разборе | Непредсказуемость для студента и руководителя | Температура 0, одинаковый набор обязательных файлов, замер разброса на нескольких прогонах | Средняя |
| Номера строк съезжают после преобразования ноутбуков | Ссылка в замечании ведёт не туда | Хранить соответствие строк и ячеек, проверять основания по настоящему файлу на коммите | Средняя |
| Нет эталона для сравнения | Нельзя доказать, что агент лучше нынешнего разбора | Эталонный набор из 20–30 PR с заложенными ошибками и чистых PR; сравнение полноты, точности, стоимости и времени до переключения | Высокая |

**Модель и сам OpenCode**

| Что может пойти не так | Чем грозит | Как решаем | Серьёзность |
| --- | --- | --- | --- |
| Модель или роутер не поддерживает нужный режим вызова инструментов | JSON-ответ OpenCode делает через принудительный вызов инструмента (`tool_choice=required`). У DeepSeek V4 с размышлениями в OpenCode есть известная ошибка (задача #24122) | Первым делом проверить Selectel + выбранную модель: многошаговые вызовы, принудительный вызов, размышления включены и выключены. Проверка ответа на нашей стороне сохраняется | Высокая |
| Агент зацикливается или жжёт токены | Расходы и долгий разбор. Лимит шагов в OpenCode отключает инструменты на последнем шаге и ломает JSON-ответ; лимита времени и токенов нет совсем | Наш счётчик токенов и тайм-аут около 10 минут с принудительной остановкой; после остановки — отдельный запрос «сведи найденное в JSON». Запрет повторяющихся вызовов | Высокая |
| Очередь повторяет дорогой разбор при ошибке, которая не исчезнет | Сутки повторов сжигают бюджет | Ошибка агента сразу ведёт к запасному разбору по diff. Повторять только сбои инфраструктуры, с ограничением попыток на коммит | Высокая |
| Расходы растут незаметно | Агент тратит в 5–20 раз больше токенов, чем один запрос; лимит 50 разборов в сутки на проект не спасает | Дневной бюджет токенов на проект и общий; стоимость каждого разбора в базе; при исчерпании — разбор по diff | Высокая |
| OpenCode быстро меняется | Обновление ломает разбор или открывает новую дыру | Закрепить версию образа и SDK; перед обновлением — прогон эталонного набора и тестов атак | Средняя |
| Скрытые действия OpenCode: снимок всего репозитория на каждом шаге, лишний запрос к модели ради заголовка сессии, разрешение «спросить» | Медленно на больших репозиториях, запрос не той модели, зависшая сессия | `snapshot: false`; вспомогательная модель задана явно; каждое разрешение — только «разрешить» или «запретить» | Средняя |

**Эксплуатация и данные**

| Что может пойти не так | Чем грозит | Как решаем | Серьёзность |
| --- | --- | --- | --- |
| Нет постоянного сервера с Linux и Docker | Сейчас сервис работает на Windows через туннель; без контейнеров агента запускать нельзя | Постоянное развёртывание — до запуска агента в работу | Блокирует |
| Огромный репозиторий, Git LFS, тысячи файлов | Долгая загрузка, нехватка диска | Скачивать архив коммита без истории; лимиты на объём и число файлов; файлы больше N МБ не копировать, таблицы читать построчно | Средняя |
| Несколько разборов одновременно | Память и процессор сервера | Не больше 1–2 контейнеров сразу, лимиты ресурсов на контейнер | Средняя |
| Срок 30 минут на разбор | Агент не успел, запасному разбору не хватает времени | Тайм-аут агента около 10 минут; если студент прислал новый коммит — агент останавливается сразу | Средняя |
| Строки таблиц (молекулы, возможно неопубликованные данные) уходят провайдеру модели | Вопрос к политике данных | Сейчас ограничений на передачу данных нет (решение принято). При необходимости — выключатель просмотра таблиц для проекта | Низкая |
| Ежемесячный обзор большого проекта не влезает в одну сессию | При автоматическом сжатии контекста теряются уже найденные проблемы | Делить обзор по темам (данные, разбиение, оценка, литература) с промежуточными итогами; сжатие контекста отключить, переполнение считать ошибкой | Высокая |
| Выдуманная литература в ежемесячном обзоре | Несуществующие статьи в советах студенту | Только работы, найденные сервисом в OpenAlex / Semantic Scholar, с идентификаторами; сервис проверяет каждую ссылку по этому списку | Средняя |

**Вывод рецензента.** Решение рабочее, но тяжелее, чем кажется. Из OpenCode нам нужно примерно 5% возможностей (чтение, поиск, карта, просмотр таблиц), а большая часть таблицы выше — отключение остальных 95%. Рецензент советует сначала сделать прототип своего маленького цикла агента (порядка 200 строк поверх уже имеющегося клиента модели) с проверкой путей на сервере и точными лимитами, а OpenCode оставить для сравнения. Если выбирать OpenCode — то со всеми мерами из таблиц.

**Что проверить прототипом до решения:**

1. Эталонный набор PR: полнота и точность агента против нынешнего разбора.
2. Selectel + выбранная модель: многошаговые вызовы инструментов, принудительный вызов, размышления включены и выключены.
3. Стоимость и время разбора на настоящем большом студенческом репозитории (медиана и худшие 5%).
4. Тесты атак: вложенный `AGENTS.md`, ссылка на системный файл, инъекция в комментарии, огромная таблица, репозиторий на 10 тысяч файлов.
5. Поведение на пределе шагов и времени: получаем ли всё равно валидный JSON.
6. Ежемесячный обзор самого большого проекта без сжатия контекста.

## Вопросы к коллегам

1. Согласны ли вы, что разбора только изменений мало и модели нужен доступ к репозиторию целиком?
2. OpenCode или свой маленький цикл агента с четырьмя инструментами? Рецензент склоняется ко второму: меньше лишнего, проверка путей и лимиты целиком в наших руках. За OpenCode — готовые инструменты, сжатие контекста и задел на будущее.
3. Достаточно ли агента только с чтением для первой версии, или без запуска проверок над данными (дубликаты, пересечение выборок) смысла нет?
4. Допустимо ли, что агентный разбор дороже в 5–20 раз и дольше (минуты вместо секунд)? Какой бюджет на проект в месяц считать приемлемым?
5. Где будет работать сервис постоянно: есть ли сервер университета с Linux и Docker, кто его обслуживает?
6. Кто и из каких проектов может собрать эталонный набор: 20–30 настоящих или правдоподобных PR с известными методическими ошибками?
7. Чего, на ваш взгляд, не хватает в списке рисков?
