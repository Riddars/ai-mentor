# Простой первый разбор и PR: конкретный план v2

Заменён [финальным планом v3](план%20—%20простой%20разбор%20v3.md):
большой PR теперь делится на части; новой кнопки повтора не будет.

22 ноября 2026. План, не реализован. Заменяет предыдущий план контекста карты и PR.
Новая граница: PR не разбивается на пакеты. Он получает полный текстовый diff;
дополнительный репозиторный инструмент — только чтение файла целиком.

## 0. Восстановление с точки зрения сотрудника (уточнение 22 ноября)

Проект/PR не требует повторного добавления, пустого коммита или нового PR
из-за сбоя сервиса. У пользователя всегда видны состояние, причина и следующий шаг.
Нельзя гарантировать полный разбор произвольного PR, превышающего реальное
окно модели, одновременно сохраняя требование одного полного diff.

| Ситуация | Автоматическое поведение | Что видит сотрудник |
| --- | --- | --- |
| Таймаут, 429/5xx, кратковременная сеть | Ограниченный fallback/отложенные повторы с сохранением расхода; без нескольких наложенных retry-циклов | «Повторяем разбор после временного сбоя», время следующей попытки |
| Ответ сохранён, GitHub недоступен | Повторяется только доставка через outbox | «Разбор готов, ожидается публикация» |
| Дневной бюджет исчерпан | Задание ожидает доступности бюджета; не исчезает после retryWindow технических ошибок | «В очереди, продолжится после восстановления бюджета» |
| Полный diff или необходимый целый файл не помещается | Используется заранее разрешённый профиль модели с подходящим окном, если он настроен и укладывается в бюджет; иначе сохранённый блокер `needs_capacity` | «Нужна настройка сервиса; менять код не требуется», конкретная причина |
| Отказ чтения не мешает доказанным выводам | Сохраняются проверенные находки и отдельные непроверенные вопросы; существенная ограниченность не скрыта за успехом | «Разбор с ограничениями», перечень недоступных материалов |
| Появился новый коммит | Ожидающее исследование заменяется последней версией, опубликованная история сохраняется | Какая версия сейчас проверяется |

`needs_capacity` не повторяет тот же платный запрос бесконечно. В панели руководителя/
администратора есть очередь требующих настройки заданий с объёмом входа, причиной
и необходимой ёмкостью. После изменения подходящей конфигурации перепроверяем
блокер и автоматически ставим актуальное задание в очередь. Изменение состояния
и fingerprint блокера сохраняются в SQLite; нет новой задачи на каждом sync.
При недоступности обоих провайдеров после окна повторов остаётся явная задача
восстановления, с редкими health-probes/проверкой конфигурации, а не обещание
бесконечных платных LLM-повторов. Постоянная ошибка схемы требует исправления
сервиса; повтор после исправления версии pipeline, не по таймеру того же запроса.

В коде уже есть GitHub `check_run.rerequested` и `source=rerun`;
доступность штатного Re-run конкретному студенту пока не проверена.
Первая приёмочная проверка — реальный участник с правами студента в тестовом repo.
Для понятного восстановления добавляем к ограниченному/неуспешному check кнопку
«Повторить разбор» через `requested_action`, если её доступность нужным ролям
подтвердится. Руководитель сохраняет нынешнюю кнопку панели.
Не вводим новую систему учётных записей студентов в веб-панели ради этой кнопки.
Если требуемой роли GitHub кнопку не показывает, альтернативой будет явная
команда в комментарии PR с проверкой пользователя и тех же прав на проект.

Оба GitHub события ведут в ОДНУ функцию восстановления: проверка подписи,
принадлежности check нашему App/repo/PR, полномочий отправителя и текущего head;
одна активная задача; ограничение частоты; сохранение общего расхода.
Кнопка не обходит дневной/общий бюджет и не снимает физический предел окна.
При неизменившемся блокере размера возвращает его описание без платного вызова.
Повтор технически успешного ревью и восстановление неуспешного — разные действия:
последнее продолжает существующую цепочку задания, не обнуляет его allowance.

Изменения: `worker.ts` (классификация/продолжение), `store.ts` и миграция
SQLite (причина/следующая попытка/fingerprint), `checks.ts` и webhook route
(состояния/кнопка), панель проекта (ожидания/административная очередь).
Проверяем весь цикл с правами сотрудника, а не только вызовом функции тестом.

Качество `complete/limited/not_reviewed`, восстановление
`retryable/blocked/terminal` и доставка `pending/delivered` — раздельные поля.
Нельзя просто использовать нынешний outcome `partial`: worker может снова
запустить модель для уже опубликованного частичного результата. Завершённый
ограниченный отчёт сохраняется/публикуется один раз; следующая попытка возможна
по причине восстановления, изменению условий или явному разрешённому запросу.
Нажатие не создаёт новый бюджет для той же цепочки: после его исчерпания
нужен административно разрешённый дополнительный бюджет, учтённый отдельно.

## 1. Подготовка и измерение

Новый `lib/curator/context-size.ts`: считает полный сериализованный запрос,
включая системные инструкции, имена файлов, JSON/служебные обёртки, историю
и описание инструмента. Для доступного соответствующего токенизатора — подсчёт,
иначе явно помеченная консервативная оценка с запасом и обработка отказа API.
Нет универсального точного коэффициента символов в токены.
Окно берём из проверенной конфигурации конкретной модели/провайдера;
текущее экспериментальное значение 128000 не означает поддержку миллиона.

Предлагаемые начальные настройки (настраиваемые, проверяются тестами):
- резерв для итогового ответа — 8000 токенов;
- дополнительный запас окна при оценке — 15%; это запас, не гарантия точности;
- отдельного фиксированного ограничения в 40000 токенов на PR-файл нет:
  предел определяется реальным свободным окном и бюджетом на завершение;
- фиксированный предел в 8 чтений не вводится; остановка по общему бюджету,
  времени и отсутствию прогресса. Повторные одинаковые запросы не создают
  копий файла; три последовательных повтора одного уже выполненного запроса
  без новых материалов требуют завершения
  с явной причиной, а не ложного полного результата;
- общий расход: отдельные настройки карты и PR, при первоначальном внедрении
  не увеличиваем автоматически текущие бюджеты проекта/дня/задания.

Каждый запрос одновременно проверяет своё окно и оставшийся общий бюджет.
Текущий `ExecutionBudget` используется всеми фазами, включая fallback и JSON repair.
До дополнительного чтения резервируем ещё один запрос со всем уже накопленным
контекстом для вывода, один запрос независимой проверки по полному diff и уже
выданным целым файлам, ответы этих фаз и ограниченное исправление формата:
маленький output reserve сам по себе этого не обеспечивает.
Перед большой картой оцениваем ВСЕ части, повторяемые инструкции, ответы и сборку.
Если не хватает общего бюджета — `budget_insufficient` до платного запуска.
Более миллиона входных токенов нельзя целиком прочитать в бюджете 950 тысяч.

## 2. Первый разбор: какие сообщения уходят модели

Новый `lib/curator/repository-inventory.ts`: файлы закреплённого SHA,
политика исключения, хеши, размеры, причина каждого пропуска. Порядок — по пути.
Сохраняем существующие исключения данных/служебных/двоичных файлов;
безопасные метаданные таблиц и шаблоны настроек — отдельное уточнение политики.
Секреты из `.env.example` нельзя считать безопасными только по имени.
Код и Markdown из notebook передаются без сохранённых outputs, с явной отметкой.

Сообщение system: назначение задачи, недоверенность файлов, правила четырёх
разделов карты, JSON-схема ответа, запрет выдумывать исключённое содержимое.
Сообщение user: repo + SHA, список исключений (при большом списке — ограниченный
обзор и ссылка на локальный полный манифест, которую модель не обязана прочитать),
потом `=== FILE "путь" ===`, полный текст, `=== END FILE ===`.

Если всё помещается — существующий `initial-map.ts`, один основной запрос.
Если нет — новый `map-pipeline.ts`:
1. Последовательно набирает целые файлы до безопасного размера запроса.
2. Следующий файл начинает новую часть. Семантического деления/AST нет.
3. Слишком большой одиночный файл делится на помеченные диапазоны только
   для первоначальной карты. Нет тихого пропуска его конца.
   Если даже одна строка больше окна — используем точные диапазоны символов
   с сохранением полного покрытия, не разрезая UTF-8 посередине символа.
4. Каждая часть получает ЧИСТЫЙ контекст: общие правила, repo/SHA, только
   назначенные файлы/диапазоны и компактные общие сведения, если они вмещаются.
   Возвращает описание назначения, роли файлов, входы/выходы, названные внешние
   зависимости, ссылки на источники и неопределённости. Источники не заменяем
   машинно угаданным графом зависимостей.
5. Финальный чистый запрос получает все описания с их файлами и составляет
   общую карту. Если описания не помещаются — объединение несколькими уровнями.
   Противоречия/неясные межчастевые связи сохраняются как неопределённости,
   а не устраняются догадками. Это карта, не доказательство корректности кода.
6. Подробные результаты частей сохраняются отдельно от коротких notes
   (нынешний лимит 6000 символов). Проверяем длину до записи, не теряем конец.

Проверка покрытия программная: все допущенные файлы/диапазоны назначены
и получили валидные ответы. Она не доказывает точность описания моделью.
Защитные лимиты архивов/распаковки остаются; при неполной копии нет успеха.

## 3. PR: полный diff и одно средство чтения

Новый `lib/curator/pr-full-diff.ts` получает точные head и base, определяет
merge-base и полный diff до head, включая добавленные/удалённые строки,
переименования и все проверяемые текстовые файлы. Отсутствие GitHub patch
не означает отсутствие изменений: восстанавливаем diff локально по git-объектам.
Учитываем fork, пагинацию, недоступную историю и смену SHA.
Архив только head этого не обеспечивает.
Git используется без external diff/textconv, hooks и smudge/clean-фильтров:
читаем объекты закреплённых SHA без исполнения кода, сборок и установки зависимостей.

В этом режиме не действуют старые ограничения отображения diff в 50000 символов,
300 файлов и подавление больших JSON/CSV/lock-файлов. Полный текстовый diff
передаётся, если помещается. Бинарным изменениям соответствует путь/тип/статус,
а не фиктивный текстовый diff. Чувствительное содержимое защищаем до отправки;
любое исключение/маскирование явно помечает покрытие как ограниченное.
Пользователь видит, что именно было недоступно модели.

Если полный diff вместе с обязательными инструкциями и резервом не помещается:
`diff_too_large`, без платного вызова, без скрытого разбиения и без перехода
к старому обрезанному diff. В сообщении — доступное окно и оценка нужного размера.

Новый режим `REVIEW_MODE=full-diff`, новый `lib/agent/pr-full-diff-agent.mts`.
Используем существующий Pi/транспорт, но отдельные инструкции и набор инструментов;
старые `read_file` с диапазонами, search, table tools и research ledger не подключаем.

Начальный контекст:
- system: правила ревью, схема ответа, допустимое чтение и работа с неопределённостью;
- user: repo, закреплённые base/merge-base/head, описание PR, короткая карта проекта
  с SHA/отметкой её актуальности, прежние замечания и ответы сотрудника,
  затем ПОЛНЫЙ diff. При сокращении сопутствующих материалов это явно отмечено;
  не закрываем замечания, чьи необходимые основания не были представлены.
- Исходный diff и выданные файлы не выбрасываются из истории и не заменяются
  саммари во время этого PR-разбора.

Единственный инструмент: `read_file({path, revision: "head" | "base"})`.
`base` здесь означает закреплённый merge-base; по умолчанию `head`.
Ответ при успехе: путь, фактический SHA, ПОЛНОЕ содержимое с номерами строк.
Номера строк и обёртки входят в расчёт размера.
Работа только внутри репозитория, без перехода по symlink наружу, команд оболочки
и произвольной сети. Политика защиты секретов обязательна.

Файл выдаётся, только если он текстовый, разрешённый,
помещается ВМЕСТЕ с текущим контекстом и оставляет общий бюджет на вывод.
Отказ содержит причину: отсутствует, запрещён, нетекстовый, слишком большой,
не помещается в окно, нет бюджета. Части файла вместо целого не выдаём.
После отказа или исчерпания доступного бюджета модель должна завершить вывод по
доступным данным, явно указав, что не удалось проверить. Нельзя превращать
неподтверждённое подозрение в установленную ошибку.
Повторное чтение того же path+SHA возвращает указатель на уже выданное
содержимое в истории; повтор не расходует ещё раз место на копию файла.

## 4. Проверка и сохранение результата PR

Ответ модели: summary, кандидаты новых замечаний с источниками, предложения
по статусам известных замечаний, непроверенные вопросы и причины ограничений.
Новые замечания явно проходят `verifyFindings`/его адаптер с общим бюджетом
и исходниками точных ревизий; простой старый diff-путь этого сейчас не делает.
Старый verifier с адресными выдержками напрямую не используем: новый получает
в одном независимом запросе кандидаты, полный diff и уже выданные целые файлы,
без рассуждений исследующего агента и без собственного чтения отрывков.
Если новых кандидатов нет, этот дополнительный запрос не нужен.
Он не считается полноценным повторным ревью. Проверку принадлежности ошибки новым изменениям
делаем по diff; ссылка на неизменённый связанный код допустима как основание.

Если независимая проверка не состоялась (`checked=false`), кандидаты сохраняются
как непроверенные; не выдаём их за подтверждённые и не публикуем как ошибки.
Сверку прежних замечаний применяем один раз. Отсутствие упоминания не равно
исправлению. При неполном существенном контексте старые замечания не закрываем.
Для comment-trigger сохраняем нынешнее ограничение: новые замечания не создаются.
Сохраняем pending до merge, авторство ручных notes, stale-head gate и outbox.
Неполнота/отказ чтения отражаются в истории/check-run; `ok` не означает
«все вопросы проверены», для незавершённой проверки отдельный статус/причина.

## 5. Устойчивость без лишней инфраструктуры

В SQLite — манифест, завершённые части карты, зафиксированные запросы чтения,
результаты, расход, версии схем/промптов и причины остановки. Новые методы
`store.ts`, добавочная миграция `lib/db/index.ts`; существующий outbox используем.
Нет векторной базы, AST-индекса, командной оркестрации и межпроектного LLM-кеша.
Начальная параллельность один. Перезапуск продолжает задание того же SHA,
не отправляет снова завершённые части карты и не обнуляет накопленный расход.
Время активной попытки и общий срок жизни задания различаются в worker.
Для PR сохраняем упорядоченные assistant/tool-call/tool-result сообщения с ID
и содержимым выданных файлов либо восстанавливаем эквивалентный контекст
из закреплённых объектов. Одних путей недостаточно: ответ «уже выдано»
допустим только при наличии полного файла в восстановленной истории.

Selectel основной, Provod резервный при техническом сбое. Для резервной модели
снова проверяем весь запрос. Если окно меньше — не обрезаем PR и файлы,
фиксируем недоступность fallback. Не запускаем автоматически прежний агент
как третий способ повторно исследовать всё.
Для карты можно уменьшить незавершённую часть при ошибке окна.
Для PR после ошибки окна отклоняем новое чтение и пробуем завершить только
с ранее допустимым контекстом; если и он не помещается — явное незавершение.
Исправление JSON — максимум две короткие попытки по ответу/ошибке схемы,
без повторной отправки всех исходников. Технические повторы ограничены
политикой транспорта и общим бюджетом; не наслаиваем несколько циклов retries.

## 6. Порядок реализации и доказательства

1. Отдельная ветка от текущей версии, настройки/подсчёт/манифест.
2. Карта: один запрос либо последовательные части, сборка, сохранение и resume.
3. PR: получение полного diff, отдельный runtime с одним инструментом,
   подключение проверки/фиксации через адаптер в `review.ts`.
4. Регрессионные тесты, сравнение результатов, затем решение о включении.
   Старый PR-режим остаётся доступным до приёмки; runtime нового режима
   не переключается в него молча. Сервер не меняем в рамках подготовки плана.

Офлайн-проверки: границы окна/файла/бюджета, >1 млн токенов искусственного ввода,
