# План: подготовленный контекст для карты проекта и ревью PR

Заменён 22 ноября 2026: [актуальный простой план v3](план%20—%20простой%20разбор%20v3.md).
Ниже сохранена историческая версия; актуальные правила описаны в v3.

Дата: 21 ноября 2026. Статус: план после независимой проверки; реализация не начата.
Основа: ветка `codex/initial-map-snapshot`, успешный локальный запуск MedChemJudge
`run-C9qapd`: 38 файлов, один запрос, 45 214 входных и выходных токенов.
Это проверка построения карты, а не качества поиска ошибок в PR.

## Цель и границы

Программа готовит ограниченные по размеру материалы и контролирует выполнение;
модель описывает проект или ищет ошибки в конкретных изменениях.
Не вводим новый агентный фреймворк, обязательный AST-парсер, векторную базу,
LLM-планировщик или свободный цикл исследования репозитория.
Первый этап не меняет действующее ревью PR; затем новый PR-путь включается отдельно.
Публикация, проверка актуальности коммита, ответы сотрудника, ручные заметки
руководителя и жизненный цикл замечаний должны сохранять действующие правила.

## Этап 1. Общая подготовка материалов

Новые `lib/curator/repository-inventory.ts` и `lib/curator/context-packets.ts`:

- Манифест по точному коммиту: путь, хеш содержимого, размер, тип,
  решение включить/исключить и причина. Читаем файлы последовательно;
  не строим одну гигантскую строку перед принятием решения о разбиении.
- Единственная политика отбора для обоих вариантов карты. Шаблоны `.env.example`
  рассматриваются отдельно от настоящих секретов; одного имени недостаточно
  для гарантии отсутствия секретов. Защиту содержимого применяем до отправки.
- Для файлов данных — ограниченное описание формата/схемы, если его можно
  безопасно получить без полной загрузки значений. Для CSV/TSV заголовок и
  достоверные метаданные, без вымышленных точных размеров или числа строк.
  Неподдерживаемые форматы явно перечисляются. Это важно для репозиториев,
  состоящих преимущественно из данных. Не отправляем всю таблицу вместо кода.
- Для notebook сохраняем код и Markdown; пропуск outputs явно отражается.
  Нетекстовые файлы не считаются проверенными по содержимому.
- Контекст измеряется на полном сформированном сообщении, включая инструкции,
  метаданные и резерв ответа; используется подходящий токенизатор, где доступен,
  иначе оценка с запасом, помеченная как оценка. Ограничения моделей задаются
  явно, для fallback проверяются повторно. Это отдельный лимит от общего расхода.
- Большие файлы разбиваются на диапазоны строк со стабильными ID; длинная
  одиночная строка обрабатывается отдельным явно помеченным фрагментом.
  Полезное содержимое нельзя молча отрезать из-за 2 MB или 2 млн символов.
- Существующие защитные пределы скачивания/распаковки сохраняются. Если они
  сработали, результат содержит `incomplete_snapshot`, а не полное покрытие.

## Этап 2. Карта проекта

`lib/curator/initial-map.ts` остаётся быстрым путём одного запроса.
Новый `lib/curator/map-pipeline.ts` выбирает его, если весь подготовленный вход
помещается. Иначе:

1. Детерминированно группирует файлы по папкам/пакетам и размеру.
   Зависимости учитываются только там, где их удаётся надёжно извлечь;
   для неизвестных языков работает группировка по путям и размерам.
2. Каждый пакет получает ограниченный общий контекст, свои исходники целиком
   либо назначенные диапазоны и инструкцию `prompts/map-part.md`.
   Полный индекс огромного репозитория не повторяется в каждом запросе.
3. Модель без инструментов возвращает MiniMap: назначение, роли файлов,
   точки входа, входы/выходы, внешние связи, источники и неопределённости.
   Программа проверяет схему и существование указанных путей/диапазонов.
4. Запрос по `prompts/map-merge.md` объединяет MiniMap в общую карту.
   Если они вместе не помещаются, объединение выполняется деревом уровней.
   Связи между пакетами не объявляются доказанными только по сходству описаний;
   при необходимости отдельный ограниченный запрос получает исходники связи.
5. Все MiniMap сохраняются отдельно. Короткая публичная карта и текущие notes
   не заменяют их: в store сейчас действует предел 6000 символов.
   Превышение формата обрабатываем до сохранения, без тихого усечения.
6. Итог считается полным только при успешной обработке всех назначенных
   диапазонов и сборке карты. Покрытие означает передачу материалов и получение
   валидного ответа, а не доказательство отсутствия ошибок в понимании.

Изменения входа: `overview.ts`, snapshot-ветка `lib/agent/run.ts`.
Меняем только путь первоначальной карты; ручной поиск ошибок и остальные
обзоры не переключаем автоматически. Выбор пути сохраняется в задании,
чтобы возобновление не зависело от случайного появления заметок в процессе.

## Бюджет, восстановление и хранение

- Общий `ExecutionBudget` покрывает чтение моделью каждого пакета, общие
  материалы, объединение, проверку, исправление формата и обращения к fallback.
- До первого платного запроса строится план с оценкой расхода и резервами.
  Миллион исходных токенов нельзя полностью прочитать при общем бюджете 950 тыс.
  Для такого задания нужен больший бюджет либо явный отказ до начала расходов.
  Разделение контекста само по себе не уменьшает суммарный объём чтения.
- В SQLite сохраняются пакет, входной хеш, версии схемы/промпта, выбранная
  модель, ответ, статус, зависимости и расход. Начало вызова фиксируется
  до обращения к провайдеру. Неизвестная стоимость после сбоя не обнуляется.
- На первом этапе повторно используем результаты внутри того же задания
  и коммита. Межпроектный/межзаданный LLM-кеш откладываем.
- Worker возобновляет незавершённые пакеты, не пересчитывает готовые и не
  обнуляет общий бюджет. При возобновлении создаётся deadline активной попытки,
  ограниченный оставшимся максимальным сроком жизни задания. Истечение попытки
  допускает продолжение по правилам очереди; истечение срока жизни задания
  завершает его. Ни одно продолжение не сбрасывает накопленный расход.
- Начальная параллельность — один запрос. Затем её можно увеличить отдельно,
  только с атомарным резервированием бюджета и защитой от двойного выполнения.
- Selectel основной, Provod резервный при технической ошибке.
  Ошибка размера вызывает пересборку меньшего пакета, а не повтор того же входа.
  На неверный JSON допускаются максимум две короткие попытки исправления
  без повторного анализа всех исходников. Неразрешённая ошибка сохраняется
  как конкретная причина, результат не объявляется успешным.

Общий расход задания, время активной попытки и максимальный срок жизни задания
хранятся раздельно. Продолжение после простоя не получает истёкший deadline
попытки и не обнуляет общий расход. Ошибки конфигурации, неподдерживаемого
размера и нехватки бюджета не запускают повтор того же плана.
Причины остановки включают `budget_insufficient`, `context_too_large`,
`incomplete_snapshot`, `invalid_format`, `provider_timeout`,
`verification_pending`, `superseded`; они отображаются в истории и check-run,
а не только во внутренних логах. Названия и отображение согласуются с текущими
enum до реализации, без успешного статуса для незавершённой проверки.

Для хранения потребуется миграция `lib/db/index.ts`, методы `store.ts` и
изменения `worker.ts`; существующие события не используем как единственное
хранилище MiniMap. Ключ пакета включает commit, pipeline version, вход и
все зависимости; повторные завершения идемпотентны.

## Этап 3. Отдельный эксперимент PR

Новый `lib/curator/pr-pipeline.ts`; `REVIEW_MODE=packets` в `lib/config.ts`.
По умолчанию сохраняем текущий режим. В `review.ts` новый путь возвращает
проверенный результат в существующий механизм фиксации и публикации.

1. В `context.ts` отделяем получение исходных материалов от ограниченного
   текстового представления. Получаем полные base/head и изменения: отсутствие
   GitHub patch и предел 300 файлов не могут означать, что изменения отсутствуют.
   Для крупных/неполных ответов строим diff по локальным git-объектам точных SHA;
   если это невозможно, статус неполного входа вместо ложного успеха.
   Фиксируем head и base, diff строим от их merge-base, сверяем с семантикой
   GitHub PR; учитываем fork и недоступную историю. Архива одного head мало.
2. Пакет содержит карту как справку, описание PR, diff назначенных участков,
   небольшие изменённые файлы целиком либо окружающие диапазоны больших,
   доступные связанные конфигурации/определения/тесты. Полный репозиторий
   в каждый PR не отправляем. Нет обязательного AST: точнее извлечь функцию
   можно позднее; первоначальный fallback — явные диапазоны строк.
3. Каждый проверяемый участок diff назначается одному пакету; связанный код
   может повторяться. Удаления, переименования и ссылки base/head различаются.
4. `prompts/pr-packet.md` возвращает кандидаты замечаний и конкретный запрос
   недостающих путей/диапазонов. Программа разрешает только чтение внутри
   закреплённого репозитория, применяет политику секретов и общий бюджет.
   Максимум два раунда дополнения на пакет, без свободного агентного цикла.
   Неотвеченный существенный вопрос отражается в неполноте, не исчезает.
5. Замечания объединяются по проверяемым признакам (место, причина), затем
   проходят отдельную проверку по реальным исходникам. Одного совпадения
   строк или ID для доказательства ошибки недостаточно. Дополнительный
   этап проверяет межпакетные связи там, где есть затрагивающие их изменения.
6. Старые замечания сверяются один раз отдельным общим шагом. Не разрешаем
   каждому пакету самостоятельно закрывать одни и те же замечания. Сохраняем
   ответы сотрудника, отклонённые замечания и правила подтверждения исправлений.
7. `verifyFindings` вызывается явно в новом пути с общим бюджетом.
   Сейчас diff-путь его не вызывает, а agent-путь сохраняет замечания при
   `checked=false`. Новый путь различает подтверждённые замечания и непроверенные
   кандидаты. Неподтверждённые не публикуются как установленные ошибки.
8. До полной обработки назначенных изменений не вызываем обычную успешную
   reconciliation. Черновик и пробелы сохраняются, старые замечания автоматически
   не закрываются. Итоговый отчёт собирается программой, без обязательного
   отдельного LLM-компоновщика. Актуальность head проверяется перед фиксацией.

## Этап 4. Приёмка до включения

Офлайн:
- Проверка покрытия пакетов, диапазонов, исключений и бюджета на искусственном
  проекте >1 млн токенов, включая один большой файл и очень длинную строку.
- Неизвестный язык, проект только с данными, notebook, переименования/удаления,
  большие структурированные файлы, отсутствующий patch, PR >300 файлов.
- Неверный JSON, таймаут/429/5xx, fallback с меньшим контекстом, рестарт между
  ответом модели и checkpoint, повторное выполнение, смена SHA и ручные заметки.
- Прежние `test:reviews`, `test:reliability`, миграции, TypeScript, lint и build.

Реальные локальные проверки выполняются после согласования реализации и
бюджета, с отдельной тестовой базой и подменой GitHub-записи:
- Повтор первого разбора MedChemJudge из чистой базы без ручных перезапусков.
- Заранее выбранные одинаковые PR/SHA на старом и новом пути: небольшой,
  связанный через несколько файлов и большой. Включить известные реальные
  ошибки и корректные изменения, чтобы видеть и пропуски, и ложные замечания.
- Для проекта >1 млн входных токенов платный тест требует соответствующего
  бюджета; офлайн-мок не выдаётся за реальный успешный анализ.

Приёмка: полное учётное покрытие, нет необоснованного закрытия замечаний,
нет потери известных существенных ошибок без объяснения, нет прироста ложных
замечаний на выбранных примерах, понятны все расходы/повторы/пробелы.
Малый набор тестов не доказывает превосходство на любых репозиториях.
Отдельно проверяем реальную доставку в GitHub и UI на тестовом проекте перед
производственным включением. Локальная подмена публикации этого не доказывает.

Порядок поставки: небольшие отдельные коммиты — подготовка материалов;
большая карта и восстановление; экспериментальный PR; проверки и сравнение.
Откат переключает новый режим, но не удаляет сохранённые анализы.
Миграция добавляет таблицы, старые записи и действующий путь не переписываются.
