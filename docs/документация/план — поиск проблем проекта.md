# Поиск проблем всего проекта после карты

Статус: план проверен субагентом-судьёй 22.11.2026 (PASS с уточнениями, включёнными ниже). Реализация не начата. Оценка плана не является проверкой реализации.

## Поведение

После успешного сохранения карты при первом подключении или ручном полном обзоре автоматически ставится отдельное задание поиска проблем. Карта остаётся доступной независимо от результата поиска. Автоматический запуск не распространяется задним числом на все существующие проекты.

Кнопка «Проверить проект на ошибки» повторяет только поиск для версии, описанной сохранённой картой. Если карты нет или её версия уже не соответствует основной ветке, панель предлагает сначала обновить карту. Самостоятельно строить карту в ответ на нажатие этой кнопки не нужно.

В первой версии поиск добавляет только новые подтверждённые замечания. Существующие статусы не меняет: не закрывает, не снимает и не переоткрывает замечания. Исправления в PR обрабатываются по прежним правилам.

## Этап 1. Исходники и контекст

- Переиспользовать `repositoryInventory`, `snapshot-policy`, `context-parts`, `context-size`. Не менять правила исключения файлов и не собирать искусственный PR на весь проект.
- Карта и поиск закреплены за одним SHA. В отдельном задании повторно получить копию именно этого SHA: временный каталог карты может уже отсутствовать. Зафиксировать версию правил, преобразования и хеши материалов для воспроизводимости.
- Сохранить ссылки на задание и анализ карты, используемый текст карты и исходный снимок контекста поиска. Текст, добавленный человеком, сохраняет действующие правила защиты от перезаписи.
- До поиска передать карту, версию кода, действующие сведения о требованиях из заметок руководителя, RESEARCH.md, PLAN.md и других материалов. Не вводить вымышленную отдельную систему требований. Код и репозиторные документы являются данными, а не командами модели.
- Отдельно собрать полные доступные замечания основной ветки/проекта: ID, статус, описание, доказательства, места, рекомендации, способ проверки, причины и авторов снятия. Включить ожидающие замечания проекта, но не считать проблемы незамерженных чужих веток проблемами основной ветки. Для контекста истории учитывать и закрытые записи, чтобы отличать известную историю от новой проблемы.
- Не расширять существующие краткие сборщики PR без необходимости: у поиска будет отдельный сборщик полной истории.

## Этап 2. Поиск без инструментов

- Добавить `prompts/project-audit.md` и `lib/curator/project-audit-pipeline.ts`. Использовать обычный `chat`, без Pi/tools и без выполнения кода репозитория.
- Запрос: системные правила поиска; карта и требования; известные замечания; затем блоки «путь файла — содержимое». Результат использует текущие поля замечаний: важность, область, описание, доказательство, влияние, рекомендация, проверка и места в коде. Для кандидатов добавить служебные ID источников.
- Если всё помещается, сделать один поисковый запрос. Если нет, использовать существующее детерминированное разбиение файлов/текста и измерение всего запроса с резервом под ответ. Записывать покрытие и исключения; не утверждать, что изучены исключённые данные или все возможные межфайловые связи.
- Обычно все замечания передаются полностью до поиска. При большой истории до поиска передать компактный индекс всех известных замечаний; после поиска сравнить кандидатов с полной историей пакетами. Не обрезать историю молча. Если даже индекс не помещается, явно фиксировать ограничение контекста поиска; полную пакетную сверку всё равно завершить до принятия новых замечаний. Незавершённая сверка означает незавершённую проверку, а не отсутствие проблем.
- Сохранять ответы частей и кандидатов с хешами запросов в существующие SQLite checkpoints. Объединять кандидатов, а не заменять исходники пересказами до поиска.

## Этап 3. Проверка и сохранение

- Переиспользовать формат и подход к валидации доказательств PR, но добавить `project-audit-verify`: связь с diff не требуется. Проверять пути и цитаты по исходникам закреплённой версии с учётом преобразований notebook и остальных представлений.
- Старый `verifyFindings` при сбое способен оставлять непроверенные находки: напрямую такой результат не применять. До успешной независимой проверки кандидат остаётся в checkpoint. Подтверждённые, опровергнутые и неразрешённые кандидаты различаются явно.
- Убирать точные дубли по устойчивому отпечатку, остальные сравнивать по причине и месту с полной историей и между частями. Одного совпадения названия недостаточно. Неопределённые кандидаты не принимать автоматически. Стопроцентную семантическую дедупликацию не обещать.
- Совпадение с закрытым замечанием само по себе не подавляет кандидата: если проблема доказанно присутствует в проверяемом SHA, оформить новую находку со ссылкой на прежнюю историю как возможную регрессию; статус старой записи не менять. При недостаточных основаниях оставить кандидата неразрешённым.
- Перед сохранением повторно сверить актуальную историю и версию основной ветки. Изменения преподавателя/PR во время анализа учитывать повторной сверкой сохранённых кандидатов, без повторения поиска. Проверку версии истории и вставку выполнять атомарно; повторный запуск не дублирует принятую запись.
- Если основная ветка ушла с SHA карты, сохранить отчёт с пометкой старой версии, но не добавлять кандидатов как актуальные замечания. Для нового поиска требуется карта новой версии.
- При вставке явно гарантировать `scope=project`. Допустимо использовать служебную запись обзора PR №0, существующий формат и `applyReconciliation`, но только с новыми прошедшими сверку находками и без любых изменений старых статусов. Проверить назначение scope отдельным тестом.

## Этап 4. Очередь и панель

- Добавить отдельный `project_audit` в типы заданий/анализов и явные ветки worker для запуска, бюджетов, ошибок, восстановления и завершения. Не допускать попадания задания в обработчик комментария PR.
- Постановку автоматического поиска связать уникальным ключом с заданием карты и выполнить в транзакции сохранения успешной карты. Публикация карты в GitHub не должна блокировать поиск. Перезапуск процесса не теряет и не удваивает продолжение.
- Переиспользовать ограничения, учёт расходов, резервирование, Selectel/Provod и причины ожидания pipeline; отдельные задания не означают обход дневного бюджета. Проверить очистку проекта, очередь и блокировки параллельных заданий проекта.
- Добавить защищённый action и кнопку «Проверить проект на ошибки» для тех же ролей руководителя, которые могут запускать обзор. Показывать отдельно состояние карты и поиска, SHA, результат, ограничения и понятную причину ожидания/ошибки. Успешный поиск без замечаний отличается от сбоя.
- Поиск не публикует issue, check или комментарий GitHub и не меняет содержимое публикации карты. Его project-замечания доступны последующим PR по обычным правилам: это не обещание вечной скрытости от студентов.

## Этап 5. Проверки и включение

- Офлайн: карта → один поиск, crash windows транзакции, отдельная кнопка, закреплённый SHA, изменившаяся ветка, большие файлы/история, покрытие частей, существующие/снятые/закрытые/ожидающие замечания, branch-only, дубли и параллельные решения руководителя/PR.
- Офлайн: ссылки и notebook, неверный формат и repair, отказ независимой проверки, fallback, дневной бюджет, восстановление без повторного поиска, миграции при необходимости, удаление проекта, отсутствие любых GitHub-публикаций поиска, регрессия PR.
- Внедрять по этапам; после каждого — проверка субагентом-судьёй. Сначала за флагом, без массовых запусков. Новый kind хранится в TEXT, пересоздавать таблицу только ради него не требуется; миграция нужна для уникальной связи/метаданных, если выбранная схема их требует.
- Финальный платный тест — только после предупреждения пользователя о цели и критериях. Сценарий: чистое подключение проблемного репозитория → карта → поиск → замечания в панели без ручного вмешательства, с корректными расходами, без дублей и GitHub-публикаций поиска. Затем отдельное решение о push/deploy.

## Ограничения

Дополнительный поиск повторно отправляет исходники модели; проверка кандидатов тоже расходует токены. Общее число вызовов заранее не фиксируется: оно зависит от размера проекта, истории, кандидатов и повторов. Не обещаем обнаружить все ошибки или стопроцентно исключить смысловые дубли. Стабильность означает сохранение прогресса, контролируемые повторы, прозрачные причины сбоев и отсутствие ложного сообщения об успешной проверке.
