# Обратная связь по подключению проектов — 2026-11-05

Статус: замечания будущих пользователей и предложения к обсуждению, **не принятые решения**.
После показа сервиса людям, которые будут создавать репозитории, возникли четыре темы:
приватность, переезд готового проекта, более мягкое подключение и выбор модели. Перед
расширением использования стоит дать сценарий нескольким волонтёрам или студентам и
понаблюдать, где они застревают.

## Приватный репозиторий

Технически GitHub App может читать приватный репозиторий, если приложение установлено в
организации и этому репозиторию предоставлен доступ. Код уже получает токен установки и
читает репозиторий через него (`lib/github/auth.ts`, `lib/github/setup.ts`). Ограничение
нынешнего сценария другое: обязательный статус `AI Curator` и защита основной ветки через
GitHub ruleset. По документации GitHub правила для приватных репозиториев организации
доступны на GitHub Team/Enterprise, а на GitHub Free for organizations — только для публичных.
Поэтому текущая панель предлагает публичный репозиторий и помечает приватный как неподготовленный.

Нужно решить, какой режим обещать пользователю:

- Полный: приватный репозиторий, GitHub App и обязательная проверка слияния; сначала
  подтвердить подходящий тариф и права в целевой организации.
- Пробный: приватный репозиторий с установленным приложением, разборы и комментарии к PR,
  но без гарантии, что PR нельзя слить до проверки. Такой режим потребует отдельной индикации
  в панели и проверки всего пути на тестовом приватном репозитории. Нельзя называть его
  эквивалентом полного режима.

Отдельно подтвердить с владельцами проектов, допустима ли отправка содержимого приватного
репозитория во внешний API модели. Старое решение о допустимости передачи данных принималось
для исходного сценария и не заменяет обсуждения новой категории проектов.

## Переезд проекта с историей

Создание из шаблона подходит новому проекту: файлы копируются, но прежняя история коммитов
не переносится. Для существующего репозитория есть два основных пути:

1. **Transfer ownership** в GitHub — предпочтительно, когда владелец исходной и целевой
   организаций может согласовать передачу. Сохраняются Git-история, ветки и связанная
   история GitHub, включая issues и pull requests. Нужны права администратора исходного
   репозитория, право создать репозиторий в целевой организации и разрешение её политики.
   После переноса проверить доступ GitHub App, участников и правила ветки.
2. **Новая копия через `git clone --mirror` / `git push --mirror`** — когда передать владение
   нельзя. Переносятся Git-ветки, теги и коммиты; история issues/PR, настройки доступа и
   правила GitHub таким способом не копируются. Git LFS переносится отдельно. Команды
   выполнять только в специально созданном пустом целевом репозитории и после сверки
   источника и назначения: `push --mirror` перезаписывает ссылки целевого репозитория.

Fork сохраняет историю коммитов, но оставляет связь с исходным проектом и может зависеть от
политик организаций; не считать его универсальным способом независимого переезда. Если
репозиторий уже находится в доступной организации и перенос не нужен, можно просто
подключить существующий `owner/repo`, установив GitHub App и проверив настройки.

## Более мягкое подключение

Сейчас панель ведёт в основном по пути «создать из шаблона в указанной организации →
подключить → настроить ruleset → пригласить студентов». При этом поле `owner/repo` уже
позволяет указать существующий репозиторий. Предлагается явно разделить стартовые пути:
«новый из шаблона», «подключить существующий», «перенести из другой организации».
После подключения показывать проверяемые шаги: доступ приложения, видимость и доступный
режим проверок, основная ветка, правила слияния, участники. Не заставлять копировать файлы
вручную и не изменять историю репозитория автоматически.

## Выбор модели

Сейчас модель и провайдер выбираются для всего сервиса через `LLM_PROVIDER` / `LLM_MODEL`,
есть резервная модель; выбора по проекту или пользователю нет. Можно обсудить ограниченный
список моделей **для руководителя проекта**, но сначала нужны сравнение качества на одном
наборе PR, стоимость и лимиты, совместимость с агентными инструментами и понятная запись
использованной модели в каждом разборе. Свободный выбор студента может менять стоимость и
сопоставимость проверок, поэтому его не предлагается вводить первым шагом. Пока это вопрос
для решения, не обещанная возможность.

## Проверка с пользователями

Провести короткий пилот с несколькими волонтёрами/студентами под наблюдением: новый проект
из шаблона, подключение существующего публичного репозитория с несколькими ветками и PR,
перенос тестового репозитория между организациями, а приватный сценарий — после выбора
режима и проверки тарифа. Попросить участников самим пройти подключение, открыть PR,
посмотреть результат и назвать непонятные шаги. Зафиксировать время, ошибки и нужные
права, затем уточнить интерфейс. Не переносить реальные исследования ради пилота.
