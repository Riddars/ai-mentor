# Надёжность агентного обзора — план изменений

Дата: 2026-11-21. Статус: согласован пользователем; локальная реализация и бесплатные проверки завершены, идёт пробный разбор настоящей моделью.

План подготовлен по независимым предложениям специалистов по контексту и надёжности. Его предмет — автоматическое первое подключение проекта, полезность проверки, объяснимость остановок и полный учёт ресурсов. Изменения находятся в локальной ветке `codex/overview-runtime-reliability`. На сервер пока не выложены. Чистая приёмка через пользовательскую форму пока не выполнена.

## Цель и критерий успеха

Руководитель создаёт или переносит репозиторий, подключает его обычной формой и получает содержательный обзор без ручных повторов, изменения настроек и помощи разработчика. Временные сбои обрабатывает сам сервис в пределах общего бюджета. Если завершение невозможно, руководитель видит конкретную причину, проверенные части и оставшиеся вопросы.

Полный обзор означает проверку существенных цепочек проекта и оснований выводов. Прочитать каждый файл недостаточно и не обязательно. Нельзя объявлять обзор полным только потому, что модель выдала корректный JSON или сама сообщила об успехе.

Универсальность означает возможность исследовать разные репозитории. Не вводим фиксированных агентов «по химии», обязательной структуры папок или единого списка проверок для всех языков. Действующие научные критерии и правила находок сохраняются там, где применимы.

## Основания

Чистая приёмка MedChemJudge-test-20261120 выполнена через обычную форму под учётной записью руководителя центра. После подключения вмешательств не было. Коммит — 07522cb77069e8c4b0d70046c38ab1a9683a8828; проект 8, задача 19, разбор 21.

- Получен частичный обзор за одну попытку. Описание и опубликованный issue не появились.
- Учтено 614185 токенов: 404325 в основных запросах и 209860 в неотображённых в трассе запросах сжатия.
- Сделано 60 обращений к инструментам. README запрошен одинаковым вызовом девять раз.
- Модель на шаге 16 сообщила о повреждении заметок, затем повторила чтение. Конкретное содержимое промежуточных сводок не сохранено, поэтому точная причинная связь не установлена.
- Итоговый текст противоречит журналу фактических чтений.

Предыдущий успешный обзор исходного MedChemJudge получен после вмешательств. Он не заменяет приёмку первого подключения. Новое повышение лимитов не является основным исправлением.

## Подтверждённые дефекты

1. `lib/agent/agent.mts` принимает сводку по длине и наличию текста, без проверки сохранности состояния. Сводка, рабочие заметки и результат завершения перезаписывают одно поле `log.notes`. Одинаковая память может попадать в запрос несколько раз.
2. Журнал фактического чтения содержит пути и короткие фрагменты, но не надёжное покрытие диапазонов и представлений файла. Он не является основанием утверждать, что файл полностью проверен.
3. Финализация создаёт новый system prompt с упрощёнными правилами. Исходные научные критерии и правила прежних находок оказываются внутри пользовательских данных вместо действующих инструкций.
4. Обычный JSON без `finish_overview` может получить полный статус. Сам `finish_overview` допускает завершение по пустому списку вопросов и одному просмотренному файлу.
5. Не сохраняется объективная причина финализации. Разные ограничения сводятся к общему частичному результату. Журнал не содержит всех фактически отправленных запросов и сводок.
6. Учёт и восстановление не полностью охватывают исключения процесса, отказ резервного провайдера, пустые и обрезанные ответы. Общий расход может быть приписан последнему провайдеру. Остаток токенов и времени в успешном fallback уже учитывается, но остальные ветви и фазы требуют единого контракта.
7. Резерв на проверку результата не равен техническому ограничению этой проверки. Доставка обзора может пересобирать текст из текущих заметок вместо сохранённого снимка.

Обычное сжатие не теряет ведущий system message из-за протокола установленной pi. Это проверено отдельно. Не исправляем неподтверждённый дефект библиотеки.

## Принятая архитектура

Сохраняем приложение, SQLite, очередь, pi и инструменты чтения. Новый фреймворк, внешняя очередь, графовая база и обязательная система субагентов не нужны.

Разделяем пять видов информации:

- исходные инструкции и идентификатор коммита;
- факты выполненных чтений, которыми управляет код;
- небольшой адаптивный список существенных вопросов и их состояние;
- выводы модели и ссылки на доказательства;
- сокращённое описание старого диалога для экономии контекста.

Сжатие не может удалять детерминированные факты, менять исходные правила или подменять подтверждённые заметки проекта. Не вводим обязательную таксономию вопросов и подробное обоснование каждого обычного чтения.

## Этап 0. Воспроизводимость и регрессии

Сначала записываем все модельные обращения, включая исследование, сжатие, итог, исправление JSON и проверку находок. Для каждого нужны назначение, провайдер, модель, начало и конец, результат, usage и версия контекста.

Сохраняем версии сводок и возможность восстановить фактически отправленный контекст. Большие результаты инструментов храним один раз; запрос содержит ссылки и хеши. Доступ и хранение ограничиваются существующей областью проекта и настраиваемыми сроками/объёмом. Ключи и credentials в трассу не попадают.

Для остановки сохраняем основную причину и предшествовавшие события. В частности: завершено, токены, инструменты, объём выдачи, время, сетевой сбой, HTTP-ошибка, неверный формат, отсутствие продвижения, неполная копия, отмена, новый коммит, сбой процесса.

Минимальная реализация — добавочные записи попыток/запросов и структурированных событий в SQLite с использованием существующего checkpoint. Окончательное число таблиц определяется схемой, отдельный сервис не вводится.

**Готово, когда** каждый запрос виден, расход по фазам сходится с итогом, а остановка объясняется сохранённым событием. Добавлены тесты, воспроизводящие потерю правил и ложное полное завершение.

## Этап 1. Корректность завершения и сохранение правил

Фаза составления отчёта наследует исходные содержательные правила. Инструменты чтения исключаются без потери научных критериев, правил прежних находок и запрета неподтверждённых утверждений.

Полнота вычисляется по состоянию исследования. Основные применимые вопросы должны быть проверены, несущественность исключённых вопросов объяснена, основания связаны с реальными материалами. Существенные открытые вопросы дают частичный результат. Синтаксическая корректность ответа не заменяет эту проверку.

Для overview вводим явную проверку схемы без молчаливого удаления некорректных находок. Совместимость действующего PR-парсера сохраняем отдельно. Восстановление формата не меняет содержание замечаний и доказательства.

**Готово, когда** JSON без подтверждённого завершения не становится полным обзором; один прочитанный README не считается достаточным охватом; финальные инструкции сохраняют правила reconciliation. Проверены обе ветви — естественный ответ и принудительное формирование отчёта.

## Этап 2. Общие ресурсы и восстановление

Вводим единый контекст бюджета задачи, общий для очереди, процессов и всех фаз: deadline, токены, обращения к инструментам и объём выдачи. 950000 токенов — общий предел задачи, включая сжатие, исправление формата, проверку, резервного провайдера и автоматические продолжения. До запроса резервируем его вход и максимальный выход, оставляя ресурс для итогового отчёта и необходимых проверок.

Показанные провайдером токены, оценка и неизвестный расход незавершённого запроса хранятся раздельно. Учитываем особенности adapter для input/cache read/cache write/reasoning без двойного подсчёта. Отсутствующий usage не считается автоматически нулевым. Лимит по символам не выдаём за точный токенизатор.

Переход на резерв обрабатывает возвращённую ошибку и исключение процесса, сохраняет уже известный расход основного, использует остаток ресурсов и checkpoint. Запросы каждого провайдера учитываются отдельно. Исправление JSON и доставка не запускают чтение репозитория заново.

Автоматическое продолжение разрешается внутри исходной задачи только с сохранённым состоянием и проверяемым продвижением. Оно не получает новый полный бюджет и не начинает исследование заново. При отсутствии продвижения продолжение останавливается.

Разделяем повторы анализа и доставки. Конкретная ошибка определяет допустимый повтор; число повторов не должно перемножаться между слоями. Неизвестный расход после обрыва остаётся явно неизвестным с консервативным резервом.

**Готово, когда** ошибки основного и резервного маршрута, пустой/обрезанный ответ, таймаут и перезапуск не теряют учёт и объяснение. Все ограничения передаются в verifier и repair. Публикационный повтор не вызывает модель.

## Этап 3. Память и продвижение исследования

Разделяем авторские рабочие заметки, автоматическую сводку и сведения о завершении. Вводим неизменяемые результаты чтения с коммитом, путём, представлением, диапазоном/селектором, усечением и идентификатором содержимого.

Повторное чтение разрешено для сопоставления и контрпроверки. Для уже покрытого диапазона агент получает краткое напоминание и доступ к оригиналу. Повтор без новой причины не должен снова увеличивать контекст тем же большим фрагментом. Перестановка параметров не создаёт фиктивно новое чтение.

Список вопросов адаптируется по карте и документам проекта. Программа хранит, какие вопросы проверены, какие заблокированы и какие неприменимы. Известный дефект проекта может стать находкой, а отсутствие файла — подтверждённым ограничением; их нельзя смешивать с ещё не выполненной проверкой.

Контекст собирается из исходных правил, задачи и SHA, состояния, точных важных оснований и небольшого хвоста полных обменов с инструментами. Сводка добавляется один раз.

Сжимается только старый диалог при существенном приросте контекста. Сводка имеет проверяемую структуру, ссылки на материалы и открытые вопросы. При провале проверки сохраняем предыдущую рабочую память. Не повторяем бесконечно дорогое сжатие одного участка.

Продвижение оценивается по новым материалам и завершённым проверкам, а не только по четырём одинаковым пакетам вызовов. При отсутствии продвижения допустима одна направленная коррекция; затем сохраняется конкретный частичный результат с причиной.

**Готово, когда** несколько последовательных сжатий не теряют проверенные факты, диапазоны и вопросы; разрешены осмысленные перепроверки; чередование одинаковых чтений не образует бесконечного цикла; итог не объявляет непрочитанным фактически прочитанное.

## Этап 4. Очередь, доставка и понятная панель

Разделяем состояние очереди, качество результата и доставку. Закончившаяся задача может иметь частичный результат, и это показывается явно.

Полный принятый результат, разрешённые изменения находок, версия заметок и снимок публикации сохраняются согласованно. Повтор доставки использует сохранённый текст и стабильный ключ публикации. При ручной правке заметок атомарно сохраняем новую версию и вытесняем ожидающую публикацию прежней версии заметок. Устаревший текст не отправляется. Это не откатывает принятые изменения находок и SHA памяти.

Частичный обзор не закрывает находки, не заменяет подтверждённое описание и не продвигает memory SHA. Проверка фактов, принятие локального обзора и успешная публикация в GitHub отображаются раздельно.

На странице достаточно показать причину остановки, проверенные части/пробелы, расход по фазам и провайдерам, использованные ограничения, повторные чтения и состояние доставки. Например: «Частичный обзор. Лимит инструментов 60/60. Токены 614185/950000».

**Готово, когда** потеря ответа после принятого GitHub POST не создаёт второй issue; повтор отправляет ту же версию; частичный текст не подписан как опубликованный обзор.

## Этап 5. Проверки качества и чистая приёмка

Сначала бесплатные тесты с управляемыми ответами:

- несколько сжатий, повреждённая сводка, сохранение инструкций и доказательств;
- отсутствие finish, существенные открытые вопросы, неполные verdicts;
- повторные и чередующиеся чтения, другие диапазоны, корректные контрпроверки;
- HTTP/network/empty/length/invalid JSON/unknown usage и отказ резервного процесса;
- cache breakdown, общий бюджет и deadline, сумма всех фаз;
- сбой сохранения, перезапуск, потерянный ответ GitHub, конкурентная ручная правка;
- сохранение существующих публичных/приватных PR, комментариев, слияния и паузы.

Для содержательной оценки нужен фиксированный набор с известными ошибками и корректными примерами. Включаем научный ML, обычное приложение, Unity-подобный проект, данные без кода и крупные структурированные файлы. Оцениваем пропущенные и ложные замечания, полезность описания и основания выводов. Работающая очередь сама по себе не доказывает качество ревью.

Затем чистое подключение приватной копии MedChemJudge на том же SHA через обычную форму, с пустой памятью и заранее закреплёнными настройками. После подключения разрешены только наблюдение и автоматические действия сервиса. Ручной retry, правка кода или конфигурации завершают тест как неуспешный.

Успех требует полезного полного обзора, подтверждённого охвата, корректных заметок и memory SHA, одной публикации в GitHub, сходящегося расхода и соблюдения ограничений. Отдельно проверяем роль supervisor: прошлый тест выполнен под head и не доказывает все права обычного руководителя проекта.

Лимит 950000 не увеличиваем во время сравнения. Он не является целевым нормальным расходом. Предлагаемый объём живой приёмки: один первый запуск MedChemJudge; только после его успеха — ещё две независимые копии MedChemJudge и один небольшой публичный проект. Плановый потолок серии — четыре задачи по 950000 токенов, суммарно 3,8 млн, включая все внутренние фазы и повторы. Это верхняя граница конфигурации, а не целевой расход или расчёт списаний в рублях. Количество и бюджет согласуются вместе с планом до запуска. При неожиданном частичном результате платная серия останавливается для диагностики. Долю успешных первых подключений измеряем по всем запускам, а не по одному выбранному успеху.

## Совместимость и выкатка

Изменения состояния и управления исследованием сначала включаем только для новых полных обзоров. Общие исправления провайдеров, parser и учёта отдельно проходят существующие PR-тесты. Действующие решения о совещательности куратора и поведении verifier при отказе не меняем молча.

Миграция SQLite добавочная. Старые результаты сохраняют legacy totals и неизвестную детализацию; распределение по провайдерам задним числом не выдумываем. Старые checkpoint и pending publications остаются читаемыми.

Перед выкаткой нужны резервная копия и проверка восстановления на копии. Используем закреплённый коммит и флаг нового режима полных обзоров. При регрессии сохраняем диагностику, отключаем новый режим и возвращаем проверенный код. Старую копию БД поверх новых пользовательских действий не восстанавливаем.

## Что не включаем в первый этап

- Обязательные субагенты для каждого репозитория и новый агентный фреймворк.
- Отдельную внешнюю базу памяти, очередь и мониторинговый сервис.
- Очередное увеличение ограничений без измерений.
- Возврат денежной отчётности без проверенных тарифов: сначала прозрачный учёт токенов, кэша и провайдеров.
- Обещание отсутствия любых ошибок. Критерии — полезность, самостоятельное завершение проверенных сценариев, ограниченный расход и объяснимая обработка сбоев.

## Источники и дальнейшее решение

Основные изменения затрагивают `lib/agent/{agent,tools,run,protocol,child,transcript}`, `lib/curator/{overview,worker,store,overview-draft,verify}`, адаптер LLM и страницы анализа. Используем существующие selftests и добавляем регрессии к конкретным найденным дефектам.

Подходы к контексту сверены с материалом Anthropic: https://www.anthropic.com/research/effective-context-engineering-for-ai-agents. Это ориентир для проектирования, а не доказательство качества нашей реализации.

До начала реализации пользователь согласует этот план. После этого выполняем этапы последовательно; успешное прохождение одного этапа не подменяет итоговую приёмку первого подключения.

## Реализация 2026-11-21

В новом режиме старый диалог сокращается детерминированно: сохраняются IDs и диапазоны чтений, вопросы, авторские заметки и хвост полных обменов. Отдельная модель для сжатия не вызывается. Это исключает расходы на повторное пересказывание одной истории и перезапись заметок автоматической сводкой.

Прошли `npm run test:reliability`, `npm run lint`, `npm run build`, а также проверки прежних PR, миграций, пауз и доставки. Синтетические Unity/CSV-примеры проверяют универсальность механизма, но не доказывают качество выводов живой модели. Входной бюджет оценивается по длине текста; фактический расход и неизвестные запросы хранятся отдельно. Без точного токенизатора оценка не гарантирует отсутствие единичного превышения фактического расхода.

Запущен первый локальный пробный обзор MedChemJudge в пустой изолированной базе через обычную очередь. Это ещё не приёмка пользовательской формы и реальной публикации GitHub. Платная серия останавливается при первом неожиданном частичном результате для диагностики.

Первый локальный платный прогон `run-Knu54P` завершился частично: 880983 токена, 60 инструментов, причина `tool_limit`, вопросы исследования не сохранялись. Код и настройки во время прогона не менялись. Приёмка не пройдена, последующие запуски серии остановлены. После диагностики добавлен обязательный переход к сохранению вопросов после первых четырёх чтений и резерв последних восьми действий для фиксации оснований и finish_overview. Бесплатный `test:reliability` после правки прошёл; живой результат этой правки ещё не подтверждён.
