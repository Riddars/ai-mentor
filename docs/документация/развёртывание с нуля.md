# Развёртывание с нуля

Обновлено: 2026-10-12. Черновик для обсуждения: как поднять сервис в рабочем режиме на сервере
ИТМО с полного нуля — организация GitHub, приложение, шаблон, сервер, настройки, проверка.
Проверен двумя субагентами (сверка с кодом; сверка с документацией GitHub, Next.js, Node,
nginx, certbot); вживую на сервере не прогонялся. Места, которые зависят от сервера и ещё не
известны, — в разделе «Что узнать у ИТМО». Локальный запуск для разработки — `запуск.md`.

## Как всё связано

```
студент ──push/PR──▶ GitHub (организация, репозиторий проекта, правило ветки)
                        │  событие (вебхук, HTTPS POST, подпись HMAC)
                        ▼
              https://<домен>/api/github/webhook
                        │  nginx (TLS) → Next.js на 127.0.0.1:3000
                        ▼
                 сервис «ИИ-куратор» ──▶ api.github.com (ключ приложения: читать PR,
                   │   │                 ставить проверку, писать комментарий)
                   │   └──────────────▶ ИИ-роутер Selectel (разбор моделью)
                   │
                   ├─ SQLite: память проектов, очередь разборов, учётки панели
                   ├─ раз в 5 минут ──▶ CronBox (сигнал «жив»)
                   └─ панель руководителя: https://<домен>/ (логин и пароль)
```

Что от чего зависит:

- **GitHub App** — «личность» сервиса в GitHub. Через него GitHub шлёт события (вебхук) и через
  него сервис действует в репозиториях. У приложения три секрета: ID, закрытый ключ `.pem`, секрет
  вебхука. Все три — в настройках сервиса.
- **Правило ветки** в каждом репозитории требует проверку `AI Curator` — без её завершения PR не
  слить. Проверку ставит только наш сервис. Значит: сервис лежит → новые PR не сливаются. После
  подъёма сверка с GitHub (при старте и затем раз в 10 минут) ставит в очередь разбор открытых PR
  и отмечает закрытые. Ответы студентов в комментариях, пришедшие за время простоя, теряются —
  их можно повторить кнопкой **Redeliver** в Recent Deliveries приложения (доступно 3 дня).
- **Проект в панели** — сервис разбирает только подключённые репозитории. Правило ветки без
  подключения в панели = PR заблокирован навсегда. Поэтому правило и подключение — вместе.
- **Публичность** — на бесплатном плане GitHub обязательные проверки работают только в публичных
  репозиториях. Все репозитории проектов публичные. Правила для всей организации на Free
  недоступны (только Enterprise), поэтому правило заводится в каждом репозитории.

## 0. Что нужно заранее

| Что | Зачем | Кто даёт |
|---|---|---|
| Сервер Linux (2 ядра, 4 ГБ памяти, 20 ГБ диска — с запасом; `/tmp` — не маленький tmpfs) | сервис, база, копии репозиториев для агента (архив до 300 МБ) | ИТМО |
| Доменное имя, указывающее на сервер | адрес вебхука и панели | ИТМО |
| Входящие из интернета: 443 (вебхук, панель) и 80 (выпуск и продление сертификата Let's Encrypt) | GitHub должен достучаться до вебхука, руководители — до панели | ИТМО |
| Исходящий HTTPS к `api.github.com`, `github.com`, `codeload.github.com`, `api.selectel.ru`, `api.cronbox.ru`, `registry.npmjs.org`, `deb.nodesource.com`, `acme-v02.api.letsencrypt.org`, зеркалам Ubuntu | работа сервиса, установка, сертификат | ИТМО |
| TLS-сертификат (Let's Encrypt или университетский) | HTTPS; без него не работает вход в панель | ИТМО / мы |
| Аккаунт GitHub ответственного сотрудника | владелец организации и приложения | центр |
| Ключ ИИ-роутера Selectel, оплаченный баланс | разбор моделью | центр (бюджет не решён) |
| Аккаунт CronBox | оповещение о сбоях | мы |

## 1. Организация GitHub

Делает владелец (ответственный сотрудник), в веб-интерфейсе GitHub.

1. github.com → «+» → **New organization** → план **Free**. Имя — например, `itmo-chem-ml`
   (вопрос: новая организация для прода или `RiddarsCorp` — см. «Что решить нам»).
2. **Settings → Member privileges**:
   - Base permissions: **Read**;
   - Repository creation: снять Public и Private — участники не создают репозитории;
   - Repository visibility change и Repository deletion and transfer: запретить участникам
     (оставить только владельцам).
3. Пригласить второго владельца — чтобы организация не зависела от одного человека.

## 2. Шаблон репозитория

1. В организации: **New repository** → `project-template`, **Public**.
2. Файлы — как в `RiddarsCorp/project-template`: `RESEARCH.md`, `PLAN.md`, `README.md`,
   `.github/PULL_REQUEST_TEMPLATE.md` (проще всего скопировать содержимое оттуда).
3. **Settings → General → Template repository** — включить.

## 3. GitHub App

Лучше создавать, когда сервер уже отвечает по `https://<домен>`: при создании GitHub шлёт
тестовое событие `ping`, и по нему сразу видно, доходят ли события. Приложение принадлежит
организации, не личному аккаунту.

1. Организация → **Settings → Developer settings → GitHub Apps → New GitHub App**.
2. Поля:
   - **GitHub App name**: `AI Curator` (имя уникально на всём GitHub; если занято —
     `AI Curator ITMO`). Имя проверки в PR от имени приложения не зависит — она всегда
     называется `AI Curator`.
   - **Homepage URL**: `https://<домен>` (или ссылка на репозиторий сервиса).
   - **Callback URL**, **Request user authorization**, **Device flow**: не нужны.
   - **Webhook → Active**: включено.
   - **Webhook URL**: `https://<домен>/api/github/webhook`.
   - **Webhook secret**: длинная случайная строка (`openssl rand -hex 32`). Её же — в
     `GITHUB_WEBHOOK_SECRET` на сервере.
   - **SSL verification**: включено.
3. **Permissions → Repository permissions**:
   - Checks: **Read and write** — ставить и завершать проверку `AI Curator`;
   - Contents: **Read-only** — читать файлы и архив коммита;
   - Issues: **Read-only** — нужно для подписки на событие Issue comment (ответы студентов);
   - Metadata: **Read-only** (обязательно, ставится само; его же хватает, чтобы читать права
     участника и правила веток);
   - Pull requests: **Read and write** — читать PR и публиковать комментарий;
   - позже: Issues **Read and write** (ежемесячный обзор, этап 4).
4. **Subscribe to events**: **Pull request**, **Issue comment**. События **Check run** по
   документации GitHub приходят приложению с Checks: write автоматически — они нужны кнопке
   **Re-run** у проверки `AI Curator` (кнопка «Re-run all checks» сервисом не обрабатывается).
   На тестовом приложении Re-run вживую не проверялся.
5. **Where can this GitHub App be installed?** — **Only on this account**.
6. **Create GitHub App**. На странице приложения:
   - записать **App ID** → `GITHUB_APP_ID`;
   - **Private keys → Generate a private key** — скачается `.pem`; перенести на сервер (см. 4.3),
     с компьютера удалить.
7. Слева **Install App** → организация → **All repositories** → Install.

Если приложение уже есть (тестовое в `RiddarsCorp`), для перехода на сервер достаточно поменять в
его настройках Webhook URL со smee на `https://<домен>/api/github/webhook`. Нового `ping` при
этом не будет — проверять по реальному событию PR.

## 4. Сервер

Команды — для Ubuntu 24.04 (вопрос к ИТМО, какая система). Строки с `sudo` выполняет
администратор; всё, что внутри каталога сервиса (клон, установка, сборка, настройки), — от
системного пользователя `curator` через `sudo -u curator -H …`, чтобы файлы принадлежали ему.

### 4.1. Система, Node.js, пользователь

```bash
sudo apt update && sudo apt install -y git nginx
# Node.js 24 (встроенный node:sqlite без флагов)
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt install -y nodejs
node -v   # v24.x

sudo useradd --system --create-home --home-dir /opt/ai-curator --shell /usr/sbin/nologin curator
sudo install -d -o curator -g curator -m 755 /var/lib/ai-curator
sudo install -d -o curator -g curator -m 700 /opt/ai-curator/secrets
```

### 4.2. Код

```bash
sudo -u curator -H git clone https://github.com/Riddars/ai-mentor.git /opt/ai-curator/app
cd /opt/ai-curator/app
sudo -u curator -H npm ci   # со всеми зависимостями: агент запускается через tsx из devDependencies
```

Нельзя `npm ci --omit=dev` и нельзя сборку `output: standalone`: агент запускается отдельным
процессом из исходника `lib/agent/child.mts` через `tsx`.

### 4.3. Настройки

Закрытый ключ приложения: скопировать с компьютера (`scp app.pem <сервер>:/tmp/`), затем

```bash
sudo install -o curator -g curator -m 600 /tmp/app.pem /opt/ai-curator/secrets/app.pem
sudo rm /tmp/app.pem
```

Файл настроек создать от имени `curator` (не копировать `.env.local.example` целиком: там
значения для локальной разработки — `LLM_PROVIDER=provod`, `SMEE_URL`, режим заглушки):

```bash
sudo -u curator -H nano /opt/ai-curator/app/.env.local
sudo chmod 600 /opt/ai-curator/app/.env.local
```

Next.js читает `.env.local` и в рабочем режиме. Содержимое:

```bash
# GitHub App
GITHUB_APP_ID=<App ID>
GITHUB_APP_PRIVATE_KEY_PATH=/opt/ai-curator/secrets/app.pem
GITHUB_WEBHOOK_SECRET=<тот же, что в приложении>

# Разбор
CURATOR_REVIEWER=llm
SIM_ADMIN_TOKEN=<случайная строка>   # обязателен даже при llm (см. ниже)
REVIEW_MODE=diff                     # agent — после решения о включении агента

# Модель
LLM_PROVIDER=selectel
LLM_MODEL=deepseek/deepseek-v4-pro
LLM_REASONING=off
SELECTEL_API_KEY=<ключ>
LLM_PRICES=selectel:deepseek/deepseek-v4-pro=21.672/43.345

# База — вне каталога с кодом, чтобы обновление кода её не трогало
DATABASE_PATH=/var/lib/ai-curator/curator.db

# Панель
AUTH_SECRET=<openssl rand -hex 32>
HEAD_LOGIN=<логин руководителя центра>
HEAD_PASSWORD=<временный пароль, убрать после первого входа>
# ALLOW_DEV_SEED не задавать: демо-данные на рабочем сервере не нужны

# Оповещение о сбоях
HEARTBEAT_URL=<адрес монитора CronBox>
```

Лимиты очереди и бюджеты токенов (`REVIEW_*`, `TOKENS_PER_*`, `AGENT_*`) по умолчанию — значения
в коде (перечислены в `.env.local.example`); менять, когда будет решён бюджет.

**Ловушка:** если не хватает обязательной переменной (`GITHUB_APP_ID`, `GITHUB_WEBHOOK_SECRET`,
`SIM_ADMIN_TOKEN`, `CURATOR_REVIEWER`, `LLM_PROVIDER`) или не читается `.pem`, сервис всё равно
поднимается и `/api/health` отвечает «ok», но очередь не запускается, а вебхук отвечает 500.
`/api/health` проверяет только, что процесс жив. Поэтому после старта — смотреть журнал (4.4).

### 4.4. Сборка и служба

```bash
cd /opt/ai-curator/app && sudo -u curator -H npm run build
```

`/etc/systemd/system/ai-curator.service`:

```ini
[Unit]
Description=AI Curator
After=network-online.target
Wants=network-online.target

[Service]
User=curator
WorkingDirectory=/opt/ai-curator/app
Environment=NODE_ENV=production
ExecStart=/opt/ai-curator/app/node_modules/.bin/next start -H 127.0.0.1 -p 3000
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ai-curator
# через несколько секунд:
curl http://127.0.0.1:3000/api/health      # {"status":"ok"}
journalctl -u ai-curator -n 50             # не должно быть "service not configured" и "[queue] not started"
```

При старте база создаётся и обновляется сама; обработчик очереди запускается вместе с сервисом.
Копии репозиториев агента — `/tmp/curator-agent-*`; оставшиеся после аварийной остановки
удаляются при следующем старте.

### 4.5. nginx и HTTPS

Порядок важен: блок 443 ссылается на файлы сертификата, а их до выпуска нет — `nginx -t`
упадёт. Поэтому сначала только порт 80, затем сертификат, затем итоговый конфиг.

Шаг 1 — `/etc/nginx/sites-available/ai-curator`:

```nginx
server {
    listen 80;
    server_name <домен>;
    location / { proxy_pass http://127.0.0.1:3000; }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/ai-curator /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
sudo apt install -y certbot python3-certbot-nginx
sudo certbot certonly --nginx -d <домен>   # продление certbot настраивает сам
```

Если сертификат даёт ИТМО — этот шаг пропустить и вписать их файлы в шаг 2.

Шаг 2 — итоговый `/etc/nginx/sites-available/ai-curator`:

```nginx
server {
    listen 80;
    server_name <домен>;
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    server_name <домен>;
    ssl_certificate     /etc/letsencrypt/live/<домен>/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/<домен>/privkey.pem;

    client_max_body_size 25m;   # события GitHub — до 25 МБ

    # служебные адреса для разработки снаружи не нужны
    location ~ ^/api/(simulate|dev)/ { return 404; }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        # только адрес клиента: по нему считаются неудачные попытки входа
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
curl https://<домен>/api/health
```

Вход в панель в рабочем режиме ставит cookie только по HTTPS — без сертификата войти нельзя.

Брандмауэр: снаружи открыты только 80 и 443; порт 3000 — только локально. Если ИТМО пускает
входящие только с разрешённых адресов, адреса вебхуков GitHub — в `https://api.github.com/meta`
(поле `hooks`). Но такой белый список закроет и панель для руководителей, и проверку Let's
Encrypt — тогда сертификат от ИТМО, а панель — через сеть университета.

Если исходящий доступ только через прокси: сервису нужны `HTTPS_PROXY` и `NODE_USE_ENV_PROXY=1`
(в `Environment=` службы); процессу агента код эти переменные сейчас не передаёт — нужна
доработка.

### 4.6. Копии базы

Сервис сам раз в сутки кладёт копию базы в `/var/lib/ai-curator/backups/` (7 последних, дата в
имени — по UTC). Это тот же диск — от его отказа не спасает. Нужна ежедневная копия на другую
машину, например из crontab пользователя `curator` (нужен его SSH-ключ на принимающей машине):

```bash
30 3 * * * rsync -a /var/lib/ai-curator/backups/ <куда>:/backups/ai-curator/
```

Куда копировать — вопрос к ИТМО.

### 4.7. Оповещение

В CronBox — монитор `AI Curator` (интервал 1 час на бесплатном тарифе), его адрес — в
`HEARTBEAT_URL`. Подробно — `запуск.md`, «Оповещение о сбоях». После развёртывания добавить
внешний опрос `https://<домен>/api/health` — он ловит случай «сервис жив, но недоступен снаружи».

## 5. Первый вход и учётки

1. `https://<домен>` → вход `HEAD_LOGIN` / `HEAD_PASSWORD` — учётка руководителя центра
   создаётся при первом входе в пустую базу.
2. Сменить пароль в «Управлении», убрать `HEAD_PASSWORD` из `.env.local`.
3. Завести учётки руководителей проектов («Управление» → учётки). Демо-учёток на новой базе нет.

## 6. Подключение проекта (на каждый проект)

Порядок важен: правило ветки и подключение в панели — в один заход.

1. Организация → **New repository** → **Repository template**: `project-template` → имя
   проекта → **Public** → Create.
2. Команда проекта: организация → **Teams → New team** (`proj-<имя>`) → добавить студентов →
   в репозитории **Settings → Collaborators and teams → Add teams** → роль **Write** (не Admin).
   Студенты должны быть участниками организации (приглашение через **People → Invite**).
3. Правило ветки: репозиторий → **Settings → Rules → Rulesets → New branch ruleset**:
   - Name: `main-protection`; Enforcement: **Active**; Bypass list — пусто;
   - Target branches: **Include default branch**;
   - **Restrict deletions** и **Block force pushes** — включены (по умолчанию);
   - **Require a pull request before merging** — включить, одобрений: 0;
   - **Require status checks to pass** — включить → Add checks → `AI Curator`, источник пока
     **any source**;
   - Create.
4. Панель → «Управление» → проекты → добавить `<организация>/<репозиторий>`, назначить
   руководителя.
5. Первый PR (владелец или студент: заполненные `RESEARCH.md`, `PLAN.md`) → в PR появляется
   проверка `AI Curator` «в работе», через минуту — комментарий куратора, проверка завершена.
6. Привязать проверку к приложению: правило `main-protection` → у проверки `AI Curator`
   выбрать источником наше приложение (имя из раздела 3). GitHub предлагает приложение только
   после того, как оно хоть раз поставило проверку в этом репозитории — поэтому после шага 5.
   До этой привязки статус с именем `AI Curator` может выставить любой участник с правом Write;
   шаги 3–6 делать в один заход. Если приложение не предлагается — задать его `integration_id`
   через REST API rulesets **[проверить]** на тестовом репозитории.

## 7. Проверка после развёртывания

1. `https://<домен>/api/health` → `{"status":"ok"}`, в `journalctl -u ai-curator` нет
   `service not configured`.
2. Приложение → **Advanced → Recent Deliveries**: событие `ping` — ответ 200. Если ping ушёл до
   запуска сервера — **Redeliver** (доступно 3 дня).
3. Тестовый репозиторий по разделу 6, PR с заведомой ошибкой (утечка данных) → замечание в
   комментарии, разбор виден в панели, расход — на странице «Расход».
4. CronBox: «Последний пинг» обновляется.
5. `sudo systemctl restart ai-curator` во время разбора → разбор выполнится после перезапуска.

## 8. Обновление сервиса

Установка и сборка ломают работающий сервис (`npm ci` удаляет `node_modules`, сборка
перезаписывает `.next`), поэтому сначала остановить. Простой — время установки и сборки
(минуты); открытые PR подберёт сверка при старте.

```bash
sudo systemctl stop ai-curator
cd /var/lib/ai-curator
# база в режиме WAL: копировать не файлом, а через VACUUM INTO (свежие записи могут быть в -wal)
sudo -u curator node -e "new (require('node:sqlite').DatabaseSync)('curator.db').exec(\"VACUUM INTO 'backups/before-update-$(date +%F).db'\")"
cd /opt/ai-curator/app
sudo -u curator -H git pull
sudo -u curator -H npm ci
sudo -u curator -H npm run build
sudo systemctl start ai-curator
journalctl -u ai-curator -n 50
```

Миграции базы выполняются при старте сами. Копии `before-update-*` не попадают под
автоматическую ротацию — удалять вручную. Ответы студентов, пришедшие за время простоя, —
Redeliver в Recent Deliveries.

## Что узнать у ИТМО

1. Будет ли сервер (ВМ), кто выдаёт и обслуживает, какая система.
2. Доменное имя и кто выпускает сертификат.
3. Открыты ли входящие 443 и 80 из интернета (GitHub шлёт события со своих адресов, руководители
   заходят в панель из любой сети) — или только из сети университета.
4. Есть ли исходящий доступ к GitHub, Selectel, CronBox, npm — или только через прокси.
5. Куда копировать резервные копии базы.
6. Допустимо ли передавать код и данные студентов внешнему провайдеру модели (Selectel) — по
   нашим решениям ограничений нет, но для университетского сервера стоит подтвердить.
