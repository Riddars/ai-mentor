# Как именно работает модуль разбиения контекста

22 ноября 2026. Спецификация к плану v3; код ещё не реализован.
Проверена субагентом; уточнения о покрытии, идентификаторах, метаданных diff
и завершении повторной упаковки включены.

## Назначение и граница универсальности

Это обычный TypeScript-модуль `lib/curator/context-parts.ts`, а не модель
и не новый агентный фреймворк. Он не пытается понять предметную область,
программный язык или архитектуру. Получает подготовленные текстовые единицы
и собирает последовательность входных запросов допустимого размера.
Полезен для Python, Unity/C#, сайта, документации и других текстовых материалов.
Бинарные файлы, неизвестные кодировки, испорченные архивы и превышение защитных
лимитов — явные отдельные случаи, а не обещание прочитать произвольные байты.
Полнота передачи текста не доказывает полноту понимания моделью.

## Входы: четыре конкретных объекта

1. `ModelLimits`: provider/model, окно контекста, максимальный ответ,
   выбранный метод подсчёта, запас оценки и резерв дополнительного чтения PR.
2. `TaskTemplate`: функция построения реальных system/user/tools/history
   сообщений по списку единиц. Каждая попытка размера строит тот же запрос,
   который затем будет отправлен; отдельного приближённого формата упаковки нет.
3. `SourceUnit[]`: упорядоченные ссылки на содержимое с путём, SHA, хешем,
   идентификатором диапазона, видом материала и метаданными координат.
   Текст хранится на диске/в ограниченных буферах, весь репозиторий не склеивается
   в оперативной памяти. Скачивание/распаковка имеют самостоятельные пределы.
   Стабильный ID определяется источником и диапазоном, а не номером части.
   Перепаковка меняет назначение, но не идентичность исходного материала.
   Ключ единицы включает revision+path+kind+range+hash; ключ части — её
   содержимое и версию плана. Порядковый номер только для отображения;
   готовые результаты при перепаковке незавершённого не переименовываются.
4. `TaskBudget`: оставшийся общий расход/время, завершённые части,
   зарезервированные будущие объединение, вывод и проверки.

Пример единиц карты: README целиком; main.cs целиком; notebook code+Markdown.
Пример единиц PR: полный diff файла; если его пришлось разделить — hunk
с исходными координатами; если hunk слишком большой — его точный фрагмент.
Общий упаковщик не парсит языки. Адаптер карты и адаптер diff отдельно знают,
как разделить свою единицу, не потеряв содержимое и сведения об источнике.

## Измерение

Байты служат для защиты памяти/загрузки; токены — для допуска к модели;
общий расход токенов — для ограничения ВСЕГО задания. Это разные проверки.

`fits(units)` строит сообщения через TaskTemplate и измеряет весь вход:
инструкции, содержимое, пути, манифест, описание инструментов и историю.
К ним прибавляются зарезервированный ответ и запас. Если вход уже накоплен
при read_file, измеряется именно накопленный запрос, а не только новый файл.

Подходящий токенизатор считает текст соответствующим способом; особенности
служебной сериализации/обёрток API учитываются отдельно. Совпадение названия
модели и библиотеки само по себе не доказывает точность подсчёта всего запроса.
Если точный метод не подтверждён — счётчик помечается estimated; коэффициент
символов в токены не выдаётся за универсальную формулу. На первом этапе можно
использовать имеющуюся оценку только с запасом и механизмом уменьшения запроса.
Известный endpoint подсчёта провайдера можно подключить, если он действительно
доступен; наличие такого endpoint заранее не предполагаем.

Пример для понимания, не настройка производства: при окне128000 из него
оставлены8000 на ответ,8000 запаса и12000 на обёртки/общие материалы;
около100000 остаётся на содержимое. На практике измеряется собранный запрос,
а не простая сумма независимых подсчётов: токенизация границ может отличаться.

## Алгоритм: последовательная упаковка

1. Закрепить версии, отсортировать пути, создать исходный манифест и правила
   исключения; выбрать настройки конкретной модели.
2. Проверить, помещаются ли сами обязательные инструкции/метаданные/резерв
   без исходников. Если нет — ошибка конфигурации, а не дробление кода бесконечно.
3. Текущая часть пуста. Взять следующую единицу и построить запрос
   `текущая часть + следующая единица`.
4. Если запрос помещается — добавить единицу и перейти к следующей.
5. Если не помещается и текущая часть непуста — зафиксировать текущую часть;
   ту же не добавленную единицу повторно проверить в НОВОЙ пустой части.
6. Если даже одна единица не помещается в пустой запрос — её адаптер делит
   на меньшие единицы. Подставить их на то же место очереди и повторить шаг3.
7. По окончании сохранить последнюю непустую часть. Пронумеровать части,
   построить конечные сообщения и проверить размер повторно: изменение
   номеров/заголовков/манифеста само могло увеличить запрос. При необходимости
   переупаковать; финальная проверка всегда на реально отправляемом формате.
   Для служебных полей резервируем заранее ограниченную ширину; если refit
   всё же нужен, он уменьшает части, имеет конечный предел попыток и выдаёт
   ошибку конфигурации вместо цикла без прогресса.
8. Проверить покрытие, оценить общий план с резервами и сохранить его до
   первого модельного запроса. Перед каждым последующим вызовом — новый admission.

Пример при условной вместимости100000 токенов содержимого:
A=60000, B=50000, C=20000. Получатся часть1:A и часть2:B+C.
Порядок сохраняется. Значение файлов и язык программирования на это не влияют.

Не требуется искать самый плотный набор и переставлять файлы — предсказуемость
важнее экономии нескольких пустующих процентов окна. Измерение ограничено
размером текущей части; промежуточные результаты подсчёта можно кешировать
по входному хешу и версии счётчика. Не пересчитываем весь репозиторий на каждом
добавленном файле; финальное fits всё равно проверяет полный запрос.
Подсчёт всего текущего сообщения при множестве крошечных файлов может иметь
квадратичную стоимость внутри части; линейной сложности не обещаем.
Замеряем этот случай отдельно, при необходимости используем блочное добавление
и кеш кандидатов, сохраняя обязательную финальную проверку полного сообщения.

## Деление слишком большой единицы

Карта: целый файл → диапазоны строк → если одна строка огромна, диапазоны
символов. Сохраняем исходный путь, SHA, начальную/конечную позицию и хеш.
Декодирование не меняет содержание и не режет UTF-8 посередине символа.
Канонические диапазоны — полуоткрытые [from,to) в UTF-8 байтах текстового
представления, границы только между полными Unicode-символами. Номера строк
для показа считаются отдельно с единицы; UTF-16 индексы JavaScript не выдаём
за эти байтовые позиции. Не нормализуем CRLF/BOM/Unicode незаметно.
Последняя неполная строка сохраняется, финальный перенос не добавляется.

PR: diff файла → hunks → диапазоны строк внутри hunk → фрагмент одной
гигантской строки. Сохраняем старые/новые номера и смещения, знаки добавления/
удаления, метаданные rename. Фрагмент не выдаётся за применимый git patch.
Повторённые заголовки/контекст — обёртка, исходные изменения считаются отдельно.

Делим детерминированно примерно пополам на допустимых границах, затем каждый
полученный фрагмент снова проверяем через fits. Не предполагаем, что половина
символов означает ровно половину токенов. Каждый шаг уменьшает исходный
диапазон; если уже один символ с обязательными метаданными не помещается —
явный `unsupported_unit/configuration_error`, без бесконечного цикла.
Инструмент read_file НЕ использует это деление: только целый файл или отказ.

## Проверка отсутствия потерь

Для каждого допущенного источника диапазоны частей должны в совокупности
давать исходное содержимое без пробелов; сверяем позиции и хеши.
Для notebook и других явно преобразованных материалов это содержимое
утверждённого текстового представления, а не побайтовое равенство исходному
JSON с исключёнными outputs. Сохраняем отдельно хеш оригинала, версию
преобразования и хеш представления. Обычный текст не нормализуем незаметно:
CRLF, отсутствие финального переноса и Unicode учитываются в проверках.
Для PR проверяем принадлежность изменённых единиц исходному diff,
координаты и ровно одно основное назначение каждой единицы.
Манифест включает и изменения без текстовых строк: rename/mode-only,
symlink, submodule/gitlink, LFS-указатель, бинарные изменения. Реальное содержимое
внешнего submodule/LFS не считаем прочитанным по его указателю; не загружаем
его автоматически. Сохраняем маркер отсутствия финального перевода строки.
Для PR восстанавливаем канонический манифест diff и метаданные, а не пытаемся
применить фрагмент гигантской строки как самостоятельный patch.
Повторный соседний контекст допускается отдельно и не маскирует пропуски.
Все исключения имеют причины. Приёмка включает восстановление исходного
содержимого из назначенных единиц и сравнение с оригиналом.
Валидный ответ части означает обработку назначенного запроса, но не является
доказательством, что модель прочитала/поняла каждый символ.

## Если расчёт не совпал с API или условия изменились

- При явном отказе API по размеру не повторяем тот же запрос: увеличиваем
  запас и переупаковываем только незавершённые исходные единицы меньше.
  Сохраняем дерево замен плана, готовые ответы и учтённый расход.
- Ограничиваем число перестроений (например, максимум3 на цепочку
  неподтверждённого admission), затем требуем проверки настройки счётчика/окна.
  Это защита от постоянной ошибки конфигурации, не предел количества файлов.
- Таймаут/429/5xx не считаем доказательством слишком большого контекста:
  используем политику технических повторов, не бессмысленное дробление.
- Для fallback проверяем его окно; если меньше — отдельный обновлённый план
  незавершённых частей. Не смешиваем артефакты разных коммитов.
- После получения ответа сверяем провайдерский usage с оценкой, записываем
  расхождение в диагностику; расход не переписываем задним числом в ноль.
- Для PR read_file, не поместившегося в историю, возвращаем отказ; историю
  не обрезаем и не теряем выданные файлы. Проверки/сведение следуют плану v3.

## Что доказываем тестами

Одинаковое поведение на текстовых файлах разных расширений и языков;
кириллица/CJK/emoji/экранирование; CRLF/LF и отсутствие завершающего переноса;
много маленьких файлов; огромный файл и одиночная строка; путь с необычными
символами; заголовки, меняющие размер после нумерации; точное покрытие,
детерминированность и завершение алгоритма; diff add/delete/rename;
неизвестный токенизатор, отказ API и ограниченное переупаковывание;
неполная загрузка, рестарт и расход бюджета. Проверки свойств дополняются
реальным MedChemJudge и фиксированными PR, а не заменяют оценку качества модели.

Гарантия инженерного алгоритма: нет зависимости от конкретного языка проекта,
нет тихой потери допущенного текста, есть конечное поведение и явные отказы.
Не гарантируем обработку любых байтов, любой величины входа за фиксированные
время/деньги или отсутствие ошибок модели. Это отдельные ограничения системы.
