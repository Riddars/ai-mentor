# Панель руководителя (этап 5)

Обновлено: 2026-09-27.

Рабочий документ по пятому этапу — веб-панели наблюдения за проектами. Читать вместе с
разделом 7 `детализированная концепция.md` (замысел) и `принятые решения.md` (почему так).

## Зачем и для кого

Панель — часть того же приложения на Next.js. Она ничего не анализирует сама: показывает
то, что накопил куратор (память этапа 3), и даёт руководителю центра управлять проектами и
учётными записями.

**Руководитель проекта** (2–5 студентов) приходит с вопросами: *что куратор нашёл у моего
студента и что обсудить; согласен ли я с тем, что модель сняла по объяснению студента;
студент вообще работает?* Он действует по пунктам — по замечаниям и pull request'ам, — а
не по агрегатам.

**Руководитель центра** (~30 проектов, несколько руководителей): *где проблемы; у кого
проекты без руководителя; куратор работает — разборы не падают, PR не висят
заблокированными?* Плюс администрирование.

Обеим ролям — **один интерфейс, ограниченный областью видимости**. Разница: охват
(все / свои), столбец «Руководитель» и фильтр по нему, раздел «Управление» (только центр).
Студенты панелью не пользуются — они работают через GitHub.

*(Предположение о режиме использования — не из документов; уточнится на практике.)*

## Принципы

1. **Списки и таблицы, а не дашборд.** Единица работы — замечание, PR, проект. Сортируемые
   таблицы с фактами; никаких «оценок внимания» с порогами. Приоритет — сортировкой по
   фактам, решение — за человеком. Это вариант раздела 7 концепции «показывать
   фактические данные без собственной оценки».
2. **Новое важнее накопленного.** Повторно открытые находки — первыми; снятые по объяснению
   студента — отдельной секцией: там модель приняла решение, которое человек проверяет.
3. **Здоровье сервиса видно на месте** — честно: видны только сбои, дошедшие до записи
   разбора (`error`, `parse_error`); падение до записи (нет токена GitHub, сервис лежал)
   следа не оставляет. «Слияние заблокировано» показывается только там, где это правда:
   у открытого PR, чей последний разбор *по коммиту* упал (check-run остался
   `action_required`); сбой сверки по комментарию check-run не создаёт и подписывается иначе.
4. **Ничего не выдумывать за данные.** Показываем только то, что реально пишет куратор
   (вебхук / `review.ts`). Этап исследования, регулярность коммитов, дата ежемесячного
   обзора — данных нет, столбцов нет.
5. **Страница показывает данные, а не объясняет себя.** Никаких подзаголовков-пояснений,
   текстовых стрелок и сырых кодов; пустые необязательные секции не показываются; графиков
   нет. Если элемент без пояснения непонятен — меняется элемент, а не дописывается текст.

### На что опираемся

- **GitHub Security Overview** — таблица репозиториев со счётчиками алертов по серьёзности и
  фильтрами — образец экрана центра.
- **GitHub Pull Requests + Checks** — список PR со статусом проверки — образец списка PR.
- **Sentry Issues** — жизненный цикл `unresolved / resolved / ignored / regressed` — прямой
  аналог наших `open / closed / dismissed / reopened`.
- **Dependabot / Snyk** — «dismissed with reason», авто-«fixed» при новом коммите — наши
  `dismissed` / `closed`; **SonarQube** — фокус на новом коде.

### Чего сознательно не показываем

KPI-плитки; графики распределений по областям и серьёзности; «нагрузку руководителей» (это
назначения — видны в управлении и в столбце «Руководитель»); «статус внимания»/светофор и
сигналы с порогами. Первая версия панели всё это содержала и была отвергнута как надуманная.
Во второй версии отвергнуты итог под таблицей проектов, мини-полоска «разборы по неделям»,
столбец «Исход последнего» и таблица pull request'ов на странице проекта — они не отвечали на
вопрос руководителя. Активность студентов по отдельности не показываем: важен проект.

## Роли и вход

- **`head` — руководитель центра.** Видит все проекты, единственный администратор
  (`/admin`). Учётку `head` нельзя отключить или удалить; второго `head` не бывает.
- **`supervisor` — руководитель проекта.** Видит только назначенные проекты; чужой проект
  и досье — 404; `/admin` — редирект на главную.

Вход: подписанный токен (HMAC по `AUTH_SECRET`) в httpOnly-cookie на 30 дней; пароли —
только хэшем (PBKDF2). Без `AUTH_SECRET` панель открыта в разработке (вы — `head`) и
закрыта в production. Первый `head` создаётся из `HEAD_LOGIN` / `HEAD_PASSWORD` при пустой
таблице. Пароли меняет только руководитель центра; страницы «Аккаунт» нет. Смена пароля и
отключение учётки завершают все её открытые сессии: токен несёт `session_version`
пользователя, при несовпадении `getViewer` его отвергает (миграция `user_version 5`).
Сброс пароля самого `head` — вручную в БД (см. «Не решено» в `состояние работ.md`).

Файлы: `lib/auth.ts` (только криптография токена — без БД, чтобы `proxy.ts` оставался
дешёвым), `lib/users.ts` (пользователи в SQLite), `proxy.ts` (ворота: без токена → `/login`,
API → 401; `/admin` — только `head`; без cookie доступны вебхук, `/api/health`,
`/api/simulate/*` со своим токеном и `/api/dev/seed` со своей проверкой), `app/actions/auth.ts`.

## Экраны

### Проекты (`/`)

Одна таблица. Столбцы:

- **Проект** — название, `owner/repo` (ссылка на GitHub), бейджи: «пауза»; «слияние
  заблокировано» (есть открытый PR, чей последний разбор по коммиту упал) или «сбой
  разбора» (последний разбор проекта — `error` / `parse_error`). Бейдж сбоя — только когда
  он есть.
- **Руководитель** — только центру; «не назначен» выделено.
- **Участники** — логины GitHub.
- **Замечания** — число открытых; красное, если среди них есть критичные. Замечания из PR,
  закрытых без слияния, не считаются.
- **Последняя активность** — дата последнего обновления PR или разбора.

Сортировка по клику на заголовок (серверная, `?sort=&dir=`; неизвестное значение → по
умолчанию); стрелка — только у активного столбца. По умолчанию: критичные открытые ↓ → все
открытые ↓ → самое старое критичное раньше → давно не активные раньше. Фильтры через URL: у
центра — по руководителю и «без руководителя» (для роли `supervisor` параметр
игнорируется); у обеих — «показать на паузе» (по умолчанию скрыты).

### Проект (`/projects/[id]`)

Хлебные крошки `Проекты / Название`. Шапка: название, статус, ссылка на репозиторий,
участники, руководители (центру), последняя активность. Секции:

1. **Открытые замечания** — `reopened` первыми, затем серьёзность, затем свежесть. Строка:
   суть; ниже `область · с {дата}` (для `reopened` — дата последнего переоткрытия из
   истории); справа — бейдж серьёзности и, если статус не `open`, бейдж статуса.
2. **Закрытые замечания** — сворачиваемый блок, только если есть: сначала «Сняты по
   объяснению студента» (выделены — это решение модели, его проверяет человек), затем
   «Исправлены»; у каждого — причина.
3. **В pull request'ах, закрытых без слияния** — сворачиваемый блок, только если есть; вне
   счётчиков.
4. **История разборов** — сворачиваемый блок: `дата · PR #N · новый коммит | ответ
   студента`, бейдж сбоя, резюме; строка ведёт на страницу разбора.

Статус `pending` — «исправлено, ждёт слияния»: модель сказала «исправлено» по diff PR, а
окончательное закрытие ждёт слияния этого PR в основную ветку. В списке открытых — с бейджем;
в счётчиках проекта остаётся открытым (код ещё не в основной ветке).

### Досье замечания (`/projects/[id]/findings/[fid]`)

Хлебные крошки `Проекты / Проект / Замечание`. Серьёзность, область, статус, суть, PR (с
состоянием), дата. Далее — только заполненные поля: **Что не так** (`description`),
**Почему это важно** (`impact`), **Основания** (список мест: файл и строки, документ и
раздел, набор данных, иное — файлы и документы ссылкой на GitHub на коммит последнего
разбора; затем подтверждающий фрагмент), **Что сделать**, ответы студента **в этом pull
request** (ответы хранятся на уровне PR, а не находки — так их пишет `review.ts`). Справа —
история статуса (статус, PR со ссылкой на разбор, дата, причина, логин человека, если
решал человек) и блок **«Решение руководителя»**: закрыть открытое замечание как ложное или
вернуть закрытое в открытые, с обязательной причиной (доступно руководителю проекта по своим
проектам и руководителю центра). Если замечание исправлено в другом PR, в шапке —
«исправлено в PR #N» (и «ждёт слияния», пока PR не слит); если снято в другом PR — «снято в
PR #N». Подсветка кода (Shiki) — позже, когда будут
храниться реальные фрагменты.

### Разбор (`/projects/[id]/analyses/[aid]`)

Хлебные крошки `Проекты / Проект / Разбор`. Дата, бейдж сбоя, PR, что запустило (новый
коммит / ответ студента), коммит, провайдер и модель, резюме. **Комментарий в pull
request** — опубликованный текст, отрисованный как Markdown. **Изменения по замечаниям** —
новые и сменившие статус находки со ссылками на досье и причиной; у находок из других PR —
«найдено в PR #N». **Что получила модель** — изменённые файлы (с пометкой, если diff
обрезан), найден ли `RESEARCH.md`, число открытых замечаний проекта и ответов студента.
**Ответ модели как есть** — свёрнутый блок с сырым ответом (с миграции `user_version 7`). Разборы до миграции `user_version 6` комментария и материалов
не имеют — эти блоки у них не показываются.

### Структура замечания

Одинакова для любого вида проверки (код, данные, методология, научная часть):

| Поле | Хранение | Содержание |
|---|---|---|
| Суть | `title` | одна фраза простым языком |
| Область | `area` | `code` код · `data` данные · `methodology` методология · `reproducibility` воспроизводимость · `problem` постановка задачи · `reasoning` научная логика · `novelty` новизна и контекст · `plan` расхождение с планом |
| Серьёзность | `severity` | `critical` критично · `important` важно · `info` к сведению |
| Что не так | `description` | подробнее, 2–4 предложения |
| Почему важно | `impact` | влияние на результаты и выводы |
| Основания | `locations` (JSON), `evidence` | 0..N мест `{kind: file / document / data / other, target, detail}` + фрагмент |
| Что сделать | `recommendation` | |

Типы и списки — `lib/curator/finding.ts` (без обращения к БД, годится для клиентского кода),
подписи — `lib/format.ts`. Та же структура в комментарии, который куратор публикует в PR.
При разборе PR модель видит только diff и `RESEARCH.md`, поэтому `novelty` и часть
`reasoning` будут редки — их основной источник — ежемесячный обзор (этап 4).

### Управление (`/admin`, только `head`)

Списки проектов и учётных записей с формами добавления; каждая запись — карточка.

- **Проект** (`/admin/projects/[id]`): название — всегда; `owner` / `repo` — только пока по
  проекту не было PR (иначе события GitHub потеряют связь); руководители — назначить /
  снять; пауза / возобновление; **удаление** с вводом `owner/repo` — каскадно (история →
  ответы → находки → разборы → PR → участники → назначения → проект). Удалённый проект не
  подключается заново автоматически; завершённые проекты — на паузу.
- **Учётная запись** (`/admin/users/[id]`): логин (уникальность без учёта регистра), имя,
  новый пароль, включить / отключить, удаление с вводом логина (снимает назначения).
  Для `head` — только логин, имя и пароль.

Статусы проекта: **`active` | `paused`**. Пауза отключает разбор (см. «Куратор» ниже);
накопленные замечания сохраняются. Что делать с ними при возобновлении — не решено.

## Что панель требует от куратора

Три правки вебхука сделаны при этапе 5 (см. `принятые решения.md`):

- разбираются только проекты, подключённые в управлении: незнакомый репозиторий вебхук
  игнорирует целиком (без check-run);
- пауза: разбор не выполняется, обязательная проверка сразу завершается `success` с текстом
  «Проект на паузе — разбор не выполняется», комментарий не публикуется;
- закрытие PR (`pull_request.closed`) записывает состояние `merged` / `closed`, открытие и
  новые коммиты — `open` (в обоих режимах ревьюера); сверка по комментарию берёт настоящее
  состояние PR из GitHub и не «открывает» слитый PR; сбой во время разбора по комментарию
  пишется в `analyses` как `error` (сбой до разбора — нет, см. `сценарии/04`); при ответе
  500 запись о доставке снимается, чтобы ручная повторная доставка не считалась дубликатом.

Для страницы разбора (2026-09-27): `analyses.materials` пишется при каждом разборе моделью,
`analyses.comment` — после успешной публикации комментария в PR (для сверки по ответу
студента — только если комментарий публиковался). Сверка идёт по открытым находкам всего
проекта, поэтому разбор одного PR может закрыть находку другого (см. `принятые решения.md`).

## Стек и код

- Next.js 16 (App Router, server components, server actions; middleware называется
  `proxy.ts`), TypeScript, Tailwind CSS 4, свои примитивы в `components/ui/` (без
  shadcn/cva), Inter из `@fontsource-variable/inter`.
- Весь SQL — в `lib/db/index.ts` и `lib/curator/store.ts`; область видимости руководителя
  выражена одним подзапросом (`scope()`), поэтому чужие данные в агрегаты не попадают.
- Хлебные крошки — `components/Breadcrumbs.tsx`; сворачиваемые блоки — `components/ui/Collapsible.tsx`
  (нативный `details`, без клиентского кода); Markdown — `components/Markdown.tsx`
  (`react-markdown`).
- Формы админки — `components/admin/*` (`useActionState`), действия — `app/actions/admin.ts`;
  каждое действие начинается с `requireHead()`.
- Схема: `users` (с `session_version`), `project_supervisors` (many-to-many),
  `projects.status`; миграции: `user_version 4` переводит бывший `archived` в `paused`,
  `user_version 5` добавляет `session_version`, `user_version 6` — структура замечания
  (`area`, `description`, `locations` вместо `category`, `file`, `lines`; серьёзность
  `critical/important/info`) и `analyses.comment` / `analyses.materials`, `user_version 7` —
  `projects.github_repo_id`, `pull_requests.head_sha`, `findings.resolved_by_pr_id`,
  `finding_status_history.actor`, `analyses.raw_response`.

## Как запускать

1. `.env.local`: `AUTH_SECRET` (любая длинная строка), `HEAD_LOGIN` / `HEAD_PASSWORD`;
   при необходимости `DATABASE_PATH` (по умолчанию `./data/curator.db`). Полный конфиг
   GitHub для панели не нужен.
2. `npm run dev`.
3. Демо-данные: `POST /api/dev/seed` — открыт в разработке; вне её нужен `ALLOW_DEV_SEED=1`
   **и** вход под `head`. Пересеивание чистое — демо-проекты пересоздаются заново, даты
   привязаны к «сегодня».
4. `/login`. Демо-учётки: `head` / `head` (или из env), `supervisor1..3` / пароль = логин.

Демо покрывает: критичная утечка через два файла открыта 20 дней при свежих коммитах; PR
слит с открытым критичным замечанием; исправлено; снято по объяснению; `reopened`; PR закрыт
без слияния; застой 40 дней; `error` (слияние заблокировано) и `parse_error`; проект без
руководителя; проект на паузе; замечание, поднятое в слитом PR и исправленное следующим PR
(`reaction-yield`). Замечания всех восьми областей, в том числе без привязки к
коду (научная логика, постановка задачи, расхождение с планом, новизна); у разборов —
опубликованный комментарий и материалы.

Если `HEAD_LOGIN` задан, а база не пуста (например, демо залито раньше первого входа),
учётка `head` из env не создаётся — см. «Не решено» в `состояние работ.md`.

## Состояние

Вторая версия — переработка от задачи руководителя после отклонения дашборда. Прошла
независимую ревизию субагентом (28 замечаний; важные исправлены: состояние PR при
комментарии, честная пометка «слияние заблокировано», дата повторного открытия, отзыв
сессий). Проверено локально: сборка, линт, миграции (свежая база, v3 → v5), роли и область
видимости (в том числе игнор `?supervisor=` у руководителя), сортировка/фильтры, все
действия управления через формы (уникальность, отказ переименования при наличии PR,
подтверждение удаления, каскад без нарушений внешних ключей, защита `head` от поддельного
POST, вход новым паролем, отзыв сессий при смене пароля и отключении), вебхук подписанными
запросами (подпись, ворота, `closed`, пауза, регистронезависимый поиск). Вживую на GitHub
правки вебхука ещё не гонялись.

Третья итерация (2026-09-27) — по замечаниям пользователя к интерфейсу: чистка от пояснений
и лишних блоков, универсальная структура замечания, история разборов со страницей разбора,
закрытие находки следующим PR.
Проверено: `tsc`, линт, сборка; миграция v5 → v6 на рабочей базе (перенос `file/lines` в
`locations`, перекодировка серьёзности); демо в новой структуре. Страницы под ролями в
