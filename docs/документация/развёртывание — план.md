# Развёртывание: план упрощения и автоматизации

Обновлено: 2026-10-12. Цель — чтобы выкатка на сервер ИТМО сводилась к «заполнить файл
настроек и запустить один скрипт», обновление — к одной команде с откатом, сервис сам
поднимался после сбоев и перезагрузки, а подключение проекта в GitHub не требовало десятка
ручных шагов. Основа — `развёртывание с нуля.md` (ручная процедура, проверена двумя
субагентами). Предложение составлено субагентом и проверено субагентом-критиком; его поправки
учтены ниже.

## Где остановились (2026-10-12)

План утверждён пользователем; ни одна фаза ещё не начата. Следующая — фаза 0 (эксперимент на
`RiddarsCorp/test`, согласие получено). Правки документов 1–3 из раздела «Правки документов»
внесены.

Порядок работы: одна фаза — одна сессия. В конце фазы: проверки (tsc, линт, сборка,
самопроверки), судья-субагент по изменённому коду (кроме фазы 0), исправление его замечаний,
пометки в `сценарии/`, `состояние работ.md`, этот раздел «Где остановились» (что сделано, что
проверено, что осталось, что узнали нового), коммит и push.

## Что сознательно не делаем

- **Docker / compose** — сервис и так один процесс плюс файл SQLite; Docker не убирает ни
  прокси, ни systemd, ни шаги в GitHub, а доступ к Docker Hub из России нестабилен.
- **Автодеплой из GitHub Actions** — нужен входящий SSH на сервер университета и ключ от
  сервера в GitHub. Обновление — вручную одной командой.
- **Создание проектов из панели через приложение** — приложению понадобились бы права
  Administration: write и Members: write на всю организацию; утечка ключа позволила бы удалить
  все репозитории. Вместо этого — скрипт под учёткой администратора (фаза 5).

## Фаза 0. Эксперимент: привязка проверки к приложению через API

Создать на `RiddarsCorp/test` правило ветки через REST (`POST /repos/{o}/{r}/rulesets`) с
`required_status_checks: [{context: "AI Curator", integration_id: <App ID>}]` и проверить, примет
ли GitHub привязку к приложению, которое ещё не ставило проверку в этом репозитории (в
интерфейсе такое ограничение есть). Затем удалить или вернуть правило.

От результата зависят: шаг 6.6 в `развёртывание с нуля.md` (окно, когда любой участник может
выставить себе «успех») и фаза 5. Время — 30 минут. Нужно согласие пользователя (меняет
настройки репозитория на GitHub).

## Фаза 1. Мелкие правки кода, без которых дальше нельзя (полдня)

1. **Тайм-аут запросов к GitHub** — `AbortSignal.timeout(30_000)` в `githubRequest`
   (`lib/github/api.ts`). Сейчас одно зависшее соединение держит такт обработчика до 5 минут.
2. **`SIM_ADMIN_TOKEN` необязателен при `CURATOR_REVIEWER=llm`** (`lib/config.ts`): нужен только
   заглушке `/api/simulate/conclude`.
3. **Копия базы перед обновлением** — через `VACUUM INTO`, не копированием файла (база в режиме
   WAL). В `развёртывание с нуля.md` уже исправлено.

Готово, когда: tsc, линт, самопроверки; сервис без `SIM_ADMIN_TOKEN` в режиме llm стартует.

## Фаза 2. Честный `/api/health` и автоперезапуск (полдня)

1. `/api/health` отвечает 503 с машинными кодами проблем, 200 — если всё в порядке:
   - `config` — `getConfig()` бросает (нет переменной, не читается `.pem`);
   - `db` — не выполняется `SELECT 1`;
   - `worker_stalled` — обработчик при `CURATOR_REVIEWER=llm` не запущен или такт занят дольше
     15 минут (признак — время начала текущего такта, не время последнего: сверка с GitHub на
     десятках проектов законно идёт минутами); первые 60 секунд после старта не проверяется;
   - `disk` — свободно меньше 1 ГБ (`fs.statfsSync`).
   Наружу — только коды, без текстов ошибок (адрес открыт без входа). Ошибки модели в health не
   входят: их ловит сигнал CronBox.
2. Таймер systemd `ai-curator-health` раз в 2 минуты: `curl -m 10`; при двух неудачах подряд с
   кодом `worker_stalled` или без ответа — `systemctl try-restart` (не запускает остановленную
   службу во время обновления). При `config` не перезапускает — бесполезно.
3. В службе: `StartLimitIntervalSec=0` в `[Unit]` (systemd не сдаётся после серии падений),
   `TimeoutStopSec=30`; журнал — отдельный `/etc/systemd/journald.conf.d/ai-curator.conf` с
   `SystemMaxUse=500M`.

Готово, когда: health отдаёт 503 при сломанной настройке и при искусственно зависшем такте,
200 в норме; самопроверка на эти случаи.

## Фаза 3. Установка и обновление одной командой (1–1,5 дня)

`deploy/` в репозитории:

- **`install.sh`** (от root, повторный запуск безопасен): Node 24 (NodeSource), Caddy, git,
  пользователь `curator`, каталоги `/var/lib/ai-curator` и `/etc/ai-curator`, брандмауэр (ufw:
  22, 80, 443), swap 2 ГБ, если памяти меньше 8 ГБ (сборка рядом с работающей службой может
  съесть память); пишет службу, таймер, Caddyfile из шаблонов; генерирует `AUTH_SECRET`, только
  если его ещё нет (иначе всех выкинет из панели); проверяет, что `DATABASE_PATH` абсолютный;
  затем вызывает `update.sh`. Параметр прокси для apt, npm и git — если у ИТМО прокси.
- **`update.sh`** (обновление с откатом): новая версия собирается в
  `/opt/ai-curator/releases/<время>` (`git clone --depth 1`, `npm ci --prefer-offline`, сборка),
  пока старая работает; затем остановка, копия базы через `VACUUM INTO`, переключение ссылки
  `/opt/ai-curator/current`, запуск, ожидание до 60 секунд ответа health (HTTP и база). Не
  поднялось — ссылка возвращается на прежнюю версию; копия базы восстанавливается, только если
  новая версия успела сменить `user_version` (иначе новые данные не теряются). Хранить 3
  версии и 5 копий базы.
- **Настройки** — `/etc/ai-curator/curator.env` (`root:curator`, 640) через `EnvironmentFile`,
  ключ — `/etc/ai-curator/app.pem`. В шаблоне — без комментариев в конце строк: systemd считает
  их частью значения.
- **Caddy вместо nginx и certbot** — сам выпускает и продлевает сертификат:
  ```
  <домен> {
    request_body { max_size 25MB }
    @dev path /api/simulate/* /api/dev/*
    respond @dev 404
    reverse_proxy 127.0.0.1:3000
  }
  ```
  Caddy сам ставит `X-Forwarded-For` и не доверяет присланному клиентом. Сертификат ИТМО —
  строкой `tls <cert> <key>`. Если Caddy недоступен в зеркалах ИТМО — ветка скрипта с nginx и
  certbot по `развёртывание с нуля.md`.

Готово, когда: на чистой ВМ Ubuntu 24.04 (любой — до сервера ИТМО) `install.sh` поднимает
сервис по HTTPS; `update.sh` обновляет; сломанная сборка не трогает работающую версию;
неподнявшаяся версия откатывается. `развёртывание с нуля.md` переписан под скрипты.

## Фаза 4. Проверка подключения проекта в панели (полдня)

Уже принятое решение (`сценарии/01`), не реализовано. При подключении проекта и на его странице
панель проверяет через API и показывает предупреждение (не блокирует):

- приложение установлено на репозиторий (`GET /repos/{o}/{r}/installation`);
- репозиторий публичный (на бесплатном плане обязательные проверки работают только в
  публичных);
- есть правило ветки с обязательной проверкой `AI Curator`, привязанной к нашему приложению
  (`GET /repos/{o}/{r}/rules/branches/{ветка}`).

Новых прав не нужно — хватает Metadata: read.

## Фаза 5. Скрипт создания проекта (полдня)

`scripts/new-project.sh` под учёткой администратора (его `gh`, scope `admin:org`; права
приложения не расширяются): репозиторий из шаблона, команда `proj-<имя>` с правом Write,
приглашение студентов; затем пауза «подключите проект в панели» и только после подтверждения —
правило ветки (иначе PR будут заблокированы навсегда). Тело правила — по итогам фазы 0.
Требует согласия на правку принятого решения «автоматизации создания репозиториев нет» (см.
ниже).

## Фаза 6. Автоповтор пропущенных событий (полдня, низкий приоритет)

При старте и раз в 10 минут: список доставок приложения (`GET /app/hook/deliveries`, JWT
приложения), группировка по `guid`, повтор (`POST …/deliveries/{id}/attempts`) групп без
успешной доставки, окно — с прошлого запуска, не больше 3 суток, не больше 3 попыток на
`guid`. Спасает ответы студентов, пришедшие за время простоя (открытые PR и так подбирает
сверка). Меняет решение «GitHub сам не повторяет — повтор вручную».

## Фаза 7. Регистрация приложения — отложено

Приложение создаётся один-два раза за всё время; манифест с локальным сервером избыточен. Если
понадобится — файл манифеста в репозитории и одна команда обмена кода на ключи. Пока — ручная
форма из `развёртывание с нуля.md`, раздел 3.
