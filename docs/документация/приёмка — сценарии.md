# Приёмка: сценарии студента и руководителя

Обновлено: 2026-10-16.

Как сервис ведёт себя в типичных ситуациях первых недель работы: что делает человек, чего мы
ожидаем и что происходит на самом деле. Нужен, чтобы на вопрос «а почему так?» был ответ, и как
план живой проверки в `ai-chem-curator/test`. Пометки: **[по коду]** — так следует из кода, вживую
не проверено; **[вживую]** — проверено, с датой; **[пробел]** — поведение неудобное или
непонятное, нужно решение.

Исходная точка во всех сценариях: руководитель завёл репозиторий через мастер в панели
(шаблон, правило ветки, студент приглашён), первичный обзор уже прошёл — у проекта два
замечания «не заполнены RESEARCH.md / PLAN.md».

## Студент

### 1. Переносит уже начатый проект — первый PR

**Действия.** Клонирует репозиторий проекта, копирует в него свои файлы (код, ноутбуки, данные),
по возможности заполняет `RESEARCH.md` и `PLAN.md`, коммитит в новую ветку, открывает PR.

**Ожидаем.**
- В PR сразу появляется проверка «AI Curator — в работе», через 1–3 минуты — комментарий
  куратора; слить PR можно после завершения проверки.
- Если документы заполнены — замечания о пустых документах помечены «исправлено, закроется после
  слияния». Если нет — остаются.
- Замечания по коду — только существенные методические.
- После слияния: исправленное закрыто, замечания по коду стали замечаниями проекта, заметки о
  проекте описывают его устройство.

**Что происходит.** **[по коду]**
- Агент получает копию репозитория на коммите PR и описание изменений; при большом PR часть
  файлов в описание не влезает (лимит 50 000 символов, порядок: код → документы → ноутбуки →
  данные), это отмечается в комментарии «проверено N из M», но агент может открыть любой файл
  сам. Файлы больше 50 МБ в копию не попадают.
- Все замечания по новому коду — «в ветке PR» до слияния, после слияния — замечания проекта.
- Заметки о проекте обновятся при слиянии, если разбор предложил новые.

**[пробел]**
- **Прямой push в `main` отклоняется** («Changes must be made through a pull request»). Студент,
  не знающий про PR, упрётся в ошибку git. Нужна памятка.
- **Старая история git не переносится** простым способом: PR между репозиториями с разной
  историей GitHub не создаёт, переписать `main` правило не даёт. Варианты: перенос файлами без
  истории (рекомендуем) или руководитель создаёт репозиторий не из шаблона, а импортом старого
  (GitHub → Import repository) и затем добавляет файлы шаблона и правило — мастер этого не
  умеет.
- Первый PR со всем проектом — самый дорогой разбор (≈1–2 ₽) и самый длинный комментарий.

### 2. Не заполнил план, дописал отдельным PR

**Ожидаем.** В первом PR замечание «PLAN.md не заполнен» остаётся открытым. Во втором PR, который
меняет `PLAN.md`, — «исправлено, закроется после слияния», после слияния закрыто.

**Что происходит.** **[по коду]** Так и есть: закрыть замечание можно, только если PR меняет
файл, на который оно ссылается. Если в плане описано не то, что в коде, — замечание «план»
серьёзности «к сведению».

### 3. Не следует шаблону

**Варианты:** удалил или переименовал `RESEARCH.md` / `PLAN.md`; всё описал в `README.md` или в
ноутбуке; положил PDF.

**Ожидаем.** Куратор просит заполнить описание, но не повторяет одно и то же в каждом PR.

**Что происходит.** **[по коду]**
- Удаление файла не считается исправлением: замечание остаётся открытым с причиной «код удалён,
  проблема не исправлена».
- Модели передаются только `RESEARCH.md` и `PLAN.md`; `README.md` и ноутбуки агент может прочитать
  сам, но замечание о незаполненном описании от этого не закроется. PDF агент не читает.
- Новое замечание о том же не заводится, пока открыто прежнее.

**[пробел]** Имена `RESEARCH.md` и `PLAN.md` обязательны — это нигде не написано студенту.

### 4. Особенности работы с GitHub

| Ситуация | Что происходит **[по коду]** |
|---|---|
| Несколько коммитов подряд | Разбирается только последний; проверки прежних завершаются «Заменён новым коммитом». |
| PR-черновик | Проверка сразу «успех» с пометкой «Черновик — разбор после перевода в «готов к ревью»»; разбор — после Ready for review. |
| Хочет слить сразу | Нельзя, пока идёт проверка (1–3 минуты); через 30 минут без разбора проверка завершается «не разобрано», слияние разрешается, разбор будет позже. |
| Загрузка файлов через веб GitHub | Коммит в `main` недоступен — GitHub сам предлагает создать ветку и PR; дальше как обычно. |
| Colab | Ноутбук читается как ячейки кода и текста, без выводов и картинок. Абсолютные пути Colab (`/content/...`) — возможное замечание о воспроизводимости. |

### 5. Спорит с замечанием, игнорирует, исправляет позже

**Ожидаем.** Объяснение в комментарии к PR рассматривается; убедительное снимает замечание, слабое
— нет, с объяснением почему. Слияние без исправления не мешает работе, замечание остаётся.
Исправление в любом следующем PR закрывает замечание.

**Что происходит.** **[по коду]**
- Комментарий участника проекта → сверка по объяснению (по diff, без агента), короткий ответ
  в PR; если открытых замечаний нет — модель не вызывается.
- Снятое замечание больше не поднимается без новых оснований; руководитель видит снятые
  отдельно и может вернуть.
- Объяснить замечание из полного обзора можно в комментарии к любому открытому PR.

**[пробел]** Комментарии руководителя в PR тоже считаются «ответами студента», если у него есть
право записи.

## Руководитель проекта

### 6. Работа в панели

| Ситуация | Ожидаем | Что происходит |
|---|---|---|
| Создал проект | Понятные шаги | Мастер «Новый проект» + «Подготовка репозитория» **[вживую 2026-10-16]**. |
| Сразу после создания | Пусто, ждём студента | Два замечания о пустых документах от первичного обзора, одно «критично» **[вживую 2026-10-16]**. **[пробел]** Предложено ставить их «к сведению» — не решено. |
| Пригласил студента | Студент в участниках | Появляется, когда принял приглашение (событие `member`) **[по коду]**; запасной путь — страница проекта в «Управлении» **[вживую 2026-10-16]**. |
| Замечание неверное | Закрыть | В досье «Закрыть как ложное» с причиной; модель его больше не вернёт **[по коду]**. |
| Заметки о проекте неточны | Исправить | «О проекте» → «Изменить»; issue обзора обновляется; обзор сохраняет формулировки руководителя, если код им не противоречит **[по коду]**. |
| Летняя пауза | Ничего не блокируется | PR не разбираются, проверка сразу «успех» с пометкой; комментарии не сохраняются; при возобновлении — полный обзор **[по коду]**. |
| Студент ушёл | Убрать | Удалить из репозитория в GitHub — уходит из участников; его замечания остаются **[по коду]**. |
| Проект закончен | Убрать из панели | Пауза и архивирование репозитория в GitHub (руководитель центра). **[пробел]** Если **удалить** проект в панели, а правило ветки в репозитории оставить, новые PR там заблокированы навсегда — куратор их больше не видит. |
| Хочет знать о новых замечаниях | Уведомление | Нет: только панель. Сводки руководителю нет **[нет]**. Студент получает уведомления GitHub о комментариях в своих PR. |

## Сервис

### 7. Сервис недоступен

**Ожидаем.** Работа студентов не останавливается надолго.

**Что происходит.** **[по коду]**
- Событие PR пришло, пока сервис лежал, — проверки нет вовсе, PR ждёт её («Expected — waiting
  for status»), слить нельзя. После запуска сверка (сразу и раз в 10 минут) подберёт открытые PR
  и разберёт.
- Разбор поставлен, но модель или GitHub сбоят — повторы; через 30 минут проверка «не
  разобрано», слияние разрешено.
- Комментарии студентов за время простоя теряются (повтор — вручную, Redeliver в приложении).
- Через час молчания приходит письмо от CronBox.

**[пробел]** Студент видит только «ожидает проверку» без объяснения; нужна памятка.

### 8. Расход и лимиты

- Разбор PR агентом ≈0,5–2 ₽, полный обзор ≈0,5–5 ₽ (2026-10-16, Selectel DeepSeek V4 Pro).
- Не больше 50 разборов в сутки и 1 млн токенов на проект; сверх — «не разобрано, лимит», разбор
  на следующие сутки. Обзор ждёт места в бюджете на весь прогон (600 тыс. токенов).

## Что ждут люди и где это расходится с системой

Взгляд «со стороны» (субагент в роли студента и руководителя, не видевших системы, 2026-10-16).
Главные расхождения — **[пробел]**, по каждому нужно решение или памятка:

1. **Данные.** Закрытых данных в проектах нет, большие данные в репозиторий не кладут (решение
   пользователя, 2026-10-16). Данных вне репозитория куратор не видит — знает о них только из
   «Данных» в `RESEARCH.md`.
2. **Перенос проекта.** Изменения — только через PR, push в `main` запрещён правилом намеренно;
   студенту нужна строка в памятке, иначе он упрётся в ошибку git на английском. Историю
   коммитов перенести можно: старый репозиторий вторым источником, слияние в новую ветку с
   `--allow-unrelated-histories`, PR. Веб-загрузка — не больше 25 МБ на файл и 100 файлов за раз.
   `.gitignore` в шаблон не добавляем — студенты настраивают сами (решение пользователя).
3. **Серая кнопка Merge 1–3 минуты.** У проверки теперь текст «Куратор проверяет изменения —
   обычно 1–3 минуты» прямо рядом с кнопкой **[по коду]**.
4. **Issue «Обзор проекта»** — только суть проекта, без замечаний; замечания, в том числе из
   обзора, — в конце каждого комментария куратора к PR («Ещё открыто в проекте») **[по коду]**.
5. **«Критично» на пустом проекте** подрывает доверие к меткам (уже в п. 6, не решено).
6. **Руководитель не знает GitHub-ник студента**; приглашение живёт 7 дней и часто уходит в спам.
7. **Уведомления:** студенты отключат письма GitHub о комментариях бота; руководителю сервис не
   пишет вообще — о сбое и о «слито с открытым критичным» он узнаёт только из панели.
8. **Шаблон обязателен?** Имена `RESEARCH.md` / `PLAN.md` нигде не объяснены; PDF куратор не
   читает, ноутбуки читает без выводов ячеек.
9. **Удаление проекта в панели** при оставленном правиле ветки блокирует PR навсегда.
10. **Сбой сервиса** выглядит для студента как «куратор меня блокирует», хотя обещали, что не
    блокирует.

**Вопросы, которые точно зададут:** данные в публичном репозитории; перенос с историей и почему
не работает push в `main`; почему Merge серая; что делать, если сервис лежит; обязательны ли
замечания; куда девать большие данные; почему «критично» на пустом проекте; обязателен ли
шаблон и читает ли куратор ноутбуки и PDF; обновляется ли обзор и закрываются ли замечания сами;
что с проектом при паузе, удалении, уходе студента.

**Нужны памятки** — студенту (перенос по шагам, PR вместо push, ожидание проверки, как спорить с
замечанием, что выкладывать, что делать при сбое) и руководителю (создание проекта и ники
студентов, что значат статусы и серьёзность, «критично» на старте, пауза и удаление). Где их
держать (README шаблона, страница в панели, отдельный документ) — не решено.
