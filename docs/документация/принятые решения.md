# Принятые решения

Зачем этот файл: чтобы новый участник не предлагал заново то, что уже рассмотрели и
отклонили, и не переигрывал решения, у которых есть причина.

Обновлено: 2026-09-27. Внешние факты проверялись 2026-08-23.

## Зафиксировано в детализированной концепции

Эти решения описаны в `детализированная концепция.md`. Здесь — только причина, по которой
выбрано именно так.

**Одно веб-приложение, а не набор сервисов.** Приём событий GitHub, анализ, память,
расписание и панель руководителя живут в одном развёрнутом приложении. Масштаб задачи —
несколько десятков проектов и несколько человек, смотрящих результат.

**Размещение на сервере университета.** Приложению нужен постоянный адрес, доступный извне:
GitHub должен доставлять на него события.

**Блокировка слияния через обязательную проверку от GitHub App.** Проверку выставляет
зарегистрированное приложение центра, указанное в настройках ветки как доверенный источник
статуса. Обычную отметку о прохождении проверки может отправить любой участник с правом
записи — отметку от приложения подделать нельзя. Отсюда же требование: студенты не должны
иметь административных прав на репозиторий.

**Отсутствие ответа не разрешает слияние.** Если сервис недоступен, pull request остаётся
заблокированным; предусмотрено ручное снятие блокировки ответственным сотрудником. Уточнено
2026-09-27: не дольше 30 минут — затем проверка завершается с пометкой «не разобрано» (см.
«Сценарии работы» ниже).

**Находки не блокируют слияние — куратор совещательный.** Разбор публикует замечания
комментарием, но всегда завершает обязательную проверку успехом: даже при найденных
методических проблемах слияние остаётся разрешённым. Решение по каждому замечанию — за
студентом и научным руководителем; система — первая линия проверки, а не запрет. Блокировка
остаётся только при недоступности сервиса (см. пункт выше).

**Повторный разбор без изучения проекта с нуля.** Каждый новый коммит запускает проверку
заново: разбирается итоговый diff PR относительно основной ветки (не только последний
коммит — модель видит итоговое состояние PR), с опорой на сохранённый контекст — открытые
находки проекта и ответы студента. Это сокращает и время ответа, и расходы.

**Память системы — на сервере, а не в репозитории студента.** Иначе студент может
отредактировать историю собственных ошибок.

**SQLite для структурированных данных, файлы — для объёмных текстов.** SQLite — это один
файл на сервере: не нужен отдельный сервер базы данных, резервная копия делается
копированием файла. При этом состояние проекта изменяется из нескольких мест сразу —
обработчик событий GitHub, ежемесячный обзор и регулярный сбор статистики работают по
разным расписаниям, — а обычные файлы при одновременной записи молча теряют изменения.

**Next.js и TypeScript, интерфейс на Tailwind CSS.** Панель руководителя — часть того же
приложения. Набор компонентов — собственные лёгкие примитивы (`components/ui/`); готовая
библиотека (shadcn и подобные) не понадобилась.

**Ежемесячный обзор публикуется отдельным GitHub Issue.** Обычные задачи проще
автоматизировать, у них есть метки и понятное состояние «открыто — закрыто».

## Решено в обсуждении, но в концепцию ещё не внесено

Требует подтверждения при следующем обновлении документов.

**Репозитории проектов — открытые (публичные).** Это не косметика, а условие
работоспособности: на бесплатном плане GitHub защита ветки с обязательными проверками
доступна только в открытых репозиториях. Размещение в открытом доступе признано допустимым.
Важно: ранний документ `docs/видение/концепция.md` говорит о закрытых репозиториях — там это устарело.

**Платный план GitHub не покупаем, бесплатный доступ по программе GitHub Education
недоступен.** Из этого и следует решение об открытых репозиториях.

**Ограничений на передачу данных во внешний API языковой модели нет** — передавать можно
любые данные проекта. (Внешний сервис — тот, что настроен провайдером; сейчас provod.ai,
ранее предполагался Anthropic.)

**Провайдер языковой модели не зафиксирован; держим его сменным.** Конкретные модели ещё не
выбраны, поэтому привязываться к одному провайдеру нельзя: переход на Claude (Anthropic)
должен оставаться возможным в любой момент. Сейчас подключён provod.ai — российский
OpenAI-совместимый шлюз (ключ `sk_...`, оплата в рублях). Вызов модели изолирован в слое
`lib/llm/`, а разбор pull request от провайдера не зависит, поэтому смена провайдера — это
добавление одного адаптера, а не переделка. Более того, provod уже отдаёт модели Claude
напрямую по той же OpenAI-совместимой схеме, так что переход на Claude через provod возможен
вообще без нового адаптера — сменой `LLM_MODEL`. Важно: `детализированная концепция.md`
(разделы 8–9) пока называет провайдером Anthropic жёстко — формулировку нужно смягчить до
«провайдер не зафиксирован».

## Память проекта (этап 3)

Решено при реализации этапа 3.

**Оценка уверенности модели не хранится.** Механизм признан предварительной гипотезой, от
которой отказались: находка получает область и серьёзность, но не «уверенность». Раздел 4
`детализированная концепция.md` приведён в соответствие (поле убрано из модели данных). Если
понадобится — вернём отдельной колонкой через миграцию.

**Сопоставление находок между прогонами делает сама модель.** При каждом разборе в промпт
кладутся открытые находки всего проекта (с номером PR, где каждая поднята) и ответы
студента в этом PR; модель возвращает актуальный статус (open / closed / dismissed /
reopened) по прошлым находкам и список новых. Эвристическое сопоставление по «отпечатку»
(категория + файл + заголовок) отвергнуто как хрупкое: переформулировка или сдвиг строк
ломают совпадение.

**Находка принадлежит проекту, а не PR** (2026-09-27). Раньше модель видела только находки
разбираемого PR, и исправление в следующем PR не распознавалось: находка из слитого PR
оставалась открытой навсегда. Теперь находка из любого PR проекта может быть закрыта
(`closed`) или снята (`dismissed`) разбором другого PR. Правила: находки этого PR модель
сверяет все; находки других PR упоминает, только если изменения или ответ студента их
касаются, и закрывает, только если исправление видно в изменениях; не затронутые остаются
как есть. Находка остаётся привязанной к PR, где её нашли; в каком PR она исправлена, видно
по истории статуса (разбор → PR). Находки PR, закрытых без слияния, другим PR не передаются —
этот код не попал в основную ветку. Цена — промпт растёт на список открытых находок проекта
(при масштабе в десятки находок несущественно).

**Объяснения студента разбирает модель.** Ответ студента (комментарий в PR) сохраняется и
передаётся модели; она сама решает, снимает ли объяснение замечание (→ dismissed). Ответ без
нового коммита обрабатывается через событие `issue_comment` и сверку на текущем head PR, без
создания нового check-run (проверка уже завершена, слияние разрешено — куратор совещательный).

**Хранилище — встроенный `node:sqlite`.** Ноль внешних зависимостей (Node 22+). Драйвер
помечен experimental, поэтому изолирован в `lib/db/`; замена — одна правка. Объёмные тексты
находок пока хранятся инлайн в SQLite, не отдельными файлами (масштаб мал; концепция это
допускает формулировкой «могут храниться отдельными файлами»).

## Панель руководителя (этап 5)

Подробности — `панель руководителя.md`.

**Две роли: `head` (руководитель центра) и `supervisor` (руководитель проекта).** Студенты
панелью не пользуются — они работают через GitHub. `head` видит все проекты и управляет
учётками и подключением; `supervisor` видит только назначенные ему проекты. Обеим ролям —
один и тот же интерфейс, ограниченный областью видимости, а не разные наборы виджетов.

**Вход — подписанный токен в httpOnly-cookie, пользователи в SQLite.** Пароли только хэшем
(PBKDF2). Без `AUTH_SECRET` панель открыта в разработке и закрыта в production (фейл-закрыто).
Первый `head` создаётся из `HEAD_LOGIN` / `HEAD_PASSWORD` при пустой базе.

**Таблицы с фактами вместо дашборда и «статуса внимания»** (2026-09-14). Первая версия
панели с KPI-плитками, графиками распределений, блоками «Требуют внимания» и «Нагрузка
руководителей» и трёхцветным статусом с порогами отвергнута пользователем как надуманная.
Из двух вариантов раздела 7 концепции выбран «показывать фактические данные без собственной
оценки»: одна сортируемая таблица проектов, страница проекта из списков, досье. Приоритет —
сортировкой по фактам (критичные открытые → все открытые → давность → последняя
активность), решение — за человеком. Графиков нет; Recharts из раздела 8 отложен, пока нет
вопроса, на который отвечал бы график.

**Интерфейс показывает данные, а не объясняет себя** (2026-09-27). Никаких подзаголовков-
пояснений, текстовых стрелок и сырых кодов (`ok`); пустые необязательные секции не
показываются. Главная: «Замечания» — одно число открытых (красное, если есть критичные),
«Последняя активность» — дата; сбой разбора — бейдж у проекта только когда он есть. Убраны
итог под таблицей, «серьёзные / всего», «серьёзных с …», мини-полоска «разборы по неделям»,
столбец «Исход последнего» и таблица pull request'ов на странице проекта: они не отвечали на
вопрос руководителя. Активность считается по проекту, а не по студентам. Закрытые замечания
(снятые по объяснению и исправленные) и история разборов — сворачиваемые блоки; у каждого
разбора есть своя страница.

**Универсальное замечание** (2026-09-27). Куратор проверяет не только код, но и данные,
методологию, научную логику, постановку задачи и соответствие плану, поэтому замечание
устроено одинаково для любого вида: суть (`title`), область (`area`), серьёзность, что не
так (`description`), почему важно (`impact`), основания (`locations` + `evidence`), что
сделать (`recommendation`). Область — фиксированный список вместо свободной категории от
модели: код · данные · методология · воспроизводимость · постановка задачи · научная
логика · новизна и контекст · расхождение с планом. Серьёзность — три уровня: критично
(может исказить выводы) · важно · к сведению. Основания — список любой длины (файл со
строками, документ и раздел, набор данных, иное) вместо единственного «файл:строки»:
проблема может проходить через несколько файлов или не иметь места в коде вовсе. Миграция
`user_version 6` переносит старые `file`/`lines` в `locations` и перекодирует
`high/medium/low` → `critical/important/info`.

**Разбор хранит опубликованный комментарий и материалы** (2026-09-27). В `analyses`
сохраняются текст, реально опубликованный в PR (`comment`), и что получила модель
(`materials`: изменённые файлы, найден ли `RESEARCH.md`, был ли diff обрезан, число прошлых
находок и ответов студента). Так руководитель может открыть любой разбор и увидеть, на чём
основан вывод. Markdown комментария отображается через `react-markdown`.

**Состояние проекта — `status`: `active` | `paused`; удаление — настоящее.** `archived`
убран (2026-09-14): по сути дублировал паузу. Миграция `user_version 4` переводит бывшие
`archived` в `paused`. Удаление проекта — каскадное (PR, разборы, находки, история, ответы,
участники, назначения) с подтверждением вводом `owner/repo`; для завершённых проектов — пауза.
Переключатель паузы живёт в `/admin`, а не на главном экране — управление в одном месте.
Ранее: `status` заменил булев `connected` из схемы этапа 3 (миграция `user_version 3`).

**Полный CRUD в управлении; пароли меняет только руководитель центра.** Проекты: добавить,
переименовать (owner/repo — только пока не было PR, иначе рвётся связь с вебхуком), пауза,
удалить. Учётки: создать, изменить логин/имя, задать пароль, включить/отключить, удалить
(снимает назначения). Учётку `head` нельзя отключить или удалить; второго `head` не бывает.
Страницы «Аккаунт» нет. Смена пароля и отключение учётки отзывают все её сессии: токен
несёт `session_version` пользователя, несовпадение — отказ (миграция `user_version 5`).

**Замечания в PR, закрытых без слияния, не считаются открытыми.** Код не попал в основную
ветку; статус находки не меняем, но из счётчиков проекта исключаем и на странице проекта
показываем отдельной секцией.

## Куратор: правки при этапе 5

Три изменения поведения вебхука, без которых панель показывала бы неправду (2026-09-14).

**Разбираются только проекты, подключённые в управлении.** Раньше любой репозиторий с
установленным приложением создавался в памяти при первом PR; удалённый в панели проект
воскресал бы с чистой историей и без руководителя. Теперь незнакомый репозиторий вебхук
игнорирует целиком (без check-run — защита ветки для него не настраивается). Подключение
репозитория в `/admin` — обязательный шаг.

**Пауза отключает разбор.** Раньше пауза была лишь пометкой. Теперь PR проекта на паузе не
разбираются; чтобы пауза не блокировала слияние, обязательная проверка сразу завершается
`success` с пояснением «Проект на паузе — разбор не выполняется», комментарий не
публикуется. Что делать с накопленными замечаниями при возобновлении — не решено.

**Вебхук записывает состояние PR** (`pull_request.closed` → `merged` / `closed`; открытие и
новые коммиты → `open`). Без этого все PR в памяти оставались «open», и сценарий раздела 6
(«слияние без реакции на существенную находку») был неотличим от живого PR. Сверка по
комментарию берёт настоящее состояние PR из GitHub, поэтому ответ студента к слитому PR не
«открывает» его обратно. Сбой во время разбора по комментарию пишется в `analyses` как
`error` (без check-run — слияние он не блокирует); сбой до разбора (получение PR, токен) не
записывается — см. `сценарии/04 куратор изнутри.md`. При ответе 500 запись о доставке
снимается, чтобы ручная повторная доставка (GitHub сам неудачные доставки не повторяет) не
считалась дубликатом.

## Сценарии работы (2026-09-27)

Приняты по итогам разбора сценариев (`сценарии/`) и независимой проверки субагентами. В коде
пока не реализованы.

**Ответ студента — только от участников проекта.** Принимаются комментарии участников
проекта; остальные пропускаются до сохранения и до обращения к модели. Уточнено на живой
проверке 2026-09-27: участник проекта — у кого право записи в репозиторий или выше (спрашивается у GitHub, кэш
10 минут); признак события `author_association` (владелец, участник организации, соавтор)
принимается как быстрый путь. Одного признака мало: членство в организации по
умолчанию скрыто, и тогда GitHub помечает участника в событиях как постороннего. Причина: репозитории публичные, и без фильтра любой посторонний может
снимать замечания и тратить деньги на модель. Отдельный список участников в панели не
нужен. Комментарии руководителей учитываются как ответы — их слово весомо. PR от
посторонних (из fork) не разбираются: проверка сразу завершается успехом.

**Замечание закрывается в два шага.** Исправление видно в PR → `pending` («исправлено, ждёт
слияния»); слияние в основную ветку → `closed`; PR закрыт без слияния → обратно `open`. PR в
неосновные ветки разбираются, но закрывает только слияние в основную. Причина: раньше
замечание закрывалось навсегда PR'ом, который потом не слили. Статус «Ожидает проверки» из
концепции получает этот смысл.

**Долгий сбой не блокирует слияние бесконечно.** Сервис сам периодически повторяет разбор
открытых PR без завершённой проверки. Если разобрать не удалось за 30 минут — проверка
завершается успехом с пометкой «не разобрано» в PR и панели, разбор остаётся в очереди.
Смягчает решение «отсутствие ответа не разрешает слияние» (см. выше): короткий сбой
по-прежнему блокирует, длительный — нет. Причина: иначе перед защитами правило ветки будут
отключать вручную и забывать включить. Обход правила — никому. Кнопка «перезапустить
разбор» в панели.

**Модель не меняет серьёзность и суть замечания после создания** — только статус и
причину; остальные поля обновляются только непустыми значениями. Причина: понижение
серьёзности по просьбе студента или ошибка модели в номере замечания незаметно меняли
картину для руководителя.

**Руководитель может сам менять статус замечания** — «вернуть в открытые», «закрыть как
ложное», с обязательным комментарием; руководитель проекта — по своим проектам,
руководитель центра — по всем; в истории — как решение человека. Главная защита от ошибок
модели и перебора объяснений студентом.

**Черновые PR не разбираются** — проверка сразу завершается успехом; разбор при переходе в
«готов к ревью». **Расходы:** разбор с задержкой после последнего коммита, только последний
коммит; по комментарию — только если есть открытые замечания; не больше 50 запросов в сутки
на проект — сверх лимита проверка сразу завершается «не разобрано — лимит», а разбор
выполняется на следующие сутки.

**Полный текст замечаний публикуется в PR**; после защиты не удаляется — код и так публичен,
студенту нужны детали. **Секреты:** своей защиты не делаем, включаем сканирование секретов
GitHub; вернуться, если секреты начнут попадать в репозитории.

**При возобновлении после паузы и при подключении проекта — внеочередной обзор проекта
целиком** (механизм ежемесячного обзора, этап 4). **Завершённый проект** — пауза в панели и
архивирование репозитория; открытые замечания остаются как история.

**Вопросы второго порядка** (2026-09-27, подробности — в `сценарии/`):

- Студенты не создают репозитории в организации; права — через команду проекта с `write`,
  `admin` — никогда. Структуры каталогов и автоматических проверок в шаблоне нет.
- Автоматизации создания репозиториев нет; вместо неё при подключении проекта панель через
  API проверяет установку приложения, правило ветки и привязку проверки к приложению.
- Модели передаются `PLAN.md` и описание PR; `README.md` и сообщения коммитов — нет.
  Картинки не передаются даже мультимодальной модели.
- Хранится сырой ответ модели каждого разбора (для споров); полный промпт — нет.
- Сверка по комментарию только меняет статусы, новые замечания не заводит. Об отклонённом
  объяснении и новых замечаниях студенту сообщается коротким комментарием.
- Ответы в ветках к строкам кода и тексты ревью принимаются как ответы студента.
  Комментарии в проекте на паузе не сохраняются.
- Серьёзность не меняет ни модель, ни руководитель.
- Правила декомпозиции замечаний приняты (одно замечание — одна проблема; частичное
  исправление не закрывает; удаление — не исправление; поле «как проверить, что
  исправлено»); пустой `RESEARCH.md` — замечание «постановка задачи».
- Минимальная конфигурация модели — требование: текстовая, без интернета, окно от 32 тысяч
  токенов. Литературу для ежемесячного обзора ищет сервис через OpenAlex / Semantic
  Scholar.
- Отложено до запуска: регулярная сводка руководителю, пересчёт расходов, пересмотр областей
  и уровней серьёзности (через 1–2 месяца).

## Отвергнутые варианты

Рассмотрены и отклонены. Не предлагать заново без новых обстоятельств.

**Платная подписка GitHub (Team) ради закрытых репозиториев с защитой ветки.** Стоимость
считается за каждого участника организации; при нескольких десятках студентов это
существенные деньги на постоянной основе.

**Готовые ИИ-ревьюеры кода (CodeRabbit, Greptile, Qodo и подобные).** Они не умеют того,
ради чего система затевается: не ведут память проекта между проверками, не делают
содержательный обзор хода исследования и заточены на качество кода, а не на корректность
методики. Кроме того, тарифицируются за каждого разработчика, открывающего pull request,
то есть каждый студент — оплачиваемое место.

**Отдельный бэкенд на Python.** Машинного обучения на нашей стороне нет: мы обращаемся к
готовой модели по сети и разбираем данные GitHub. Отдельный язык и второй процесс дали бы
только усложнение.

**PostgreSQL.** Избыточен для этих объёмов данных и требует обслуживания отдельного
сервера.

**Хранение всего в обычных файлах без базы.** Состояние проекта изменяется из нескольких
мест сразу, и одновременная запись в файл молча теряет изменения.

**Готовые инструменты отчётности (Metabase, Grafana, Superset и подобные).** Хорошо рисуют
графики, но не показывают досье проблемы — фрагмент кода с подсветкой рядом с текстовым
объяснением, а это главное, ради чего панель существует.

**GitHub Discussions как канал общения со студентом.** У обычных задач полноценный простой
программный интерфейс, метки и понятные состояния; у обсуждений — нет.

**Дашборд в панели руководителя: KPI-плитки, графики распределений по категориям и
серьёзности, блок «Требуют внимания», «Нагрузка руководителей», трёхцветный статус внимания
с порогами.** Реализовано в первой версии этапа 5 и отвергнуто: руководитель действует по
конкретным замечаниям и PR, а не по агрегатам; график без вопроса, на который он отвечает, —
шум. Единственное, что может вернуться, — распределение находок по областям для методической
работы центра, отдельной страницей и после накопления реальных данных.

**Мини-полоска «разборы по неделям», таблица pull request'ов и итог под таблицей
проектов** (вторая версия этапа 5). Отвергнуты пользователем 2026-09-27: непонятно, что
показывают и зачем; руководителю нужны нерешённые замечания и их понятное описание, а не
активность по PR.

**Свободная категория находки от модели и единственное «файл:строки».** Заменены областью
из фиксированного списка и списком оснований: свободный текст нельзя сгруппировать, а
методическая или логическая ошибка часто не привязана к одному месту в коде.

**Статус проекта «архив».** Дублировал паузу; заменён настоящим удалением с подтверждением.
