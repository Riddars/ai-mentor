# Принятые решения

Зачем этот файл: чтобы новый участник не предлагал заново то, что уже рассмотрели и
отклонили, и не переигрывал решения, у которых есть причина.

Обновлено: 2026-09-14. Внешние факты проверялись 2026-08-23.

## Зафиксировано в детализированной концепции

Эти решения описаны в `детализированная концепция.md`. Здесь — только причина, по которой
выбрано именно так.

**Одно веб-приложение, а не набор сервисов.** Приём событий GitHub, анализ, память,
расписание и панель руководителя живут в одном развёрнутом приложении. Масштаб задачи —
несколько десятков проектов и несколько человек, смотрящих результат.

**Размещение на сервере университета.** Приложению нужен постоянный адрес, доступный извне:
GitHub должен доставлять на него события.

**Блокировка слияния через обязательную проверку от GitHub App.** Проверку выставляет
зарегистрированное приложение центра, указанное в настройках ветки как доверенный источник
статуса. Обычную отметку о прохождении проверки может отправить любой участник с правом
записи — отметку от приложения подделать нельзя. Отсюда же требование: студенты не должны
иметь административных прав на репозиторий.

**Отсутствие ответа не разрешает слияние.** Если сервис недоступен, pull request остаётся
заблокированным; предусмотрено ручное снятие блокировки ответственным сотрудником.

**Находки не блокируют слияние — куратор совещательный.** Разбор публикует замечания
комментарием, но всегда завершает обязательную проверку успехом: даже при найденных
методических проблемах слияние остаётся разрешённым. Решение по каждому замечанию — за
студентом и научным руководителем; система — первая линия проверки, а не запрет. Блокировка
остаётся только при недоступности сервиса (см. пункт выше).

**Повторный разбор только новых изменений.** Каждый новый коммит запускает проверку заново,
но система опирается на сохранённый контекст предыдущего анализа этого же pull request,
а не изучает проект с нуля. Это сокращает и время ответа, и расходы.

**Память системы — на сервере, а не в репозитории студента.** Иначе студент может
отредактировать историю собственных ошибок.

**SQLite для структурированных данных, файлы — для объёмных текстов.** SQLite — это один
файл на сервере: не нужен отдельный сервер базы данных, резервная копия делается
копированием файла. При этом состояние проекта изменяется из нескольких мест сразу —
обработчик событий GitHub, ежемесячный обзор и регулярный сбор статистики работают по
разным расписаниям, — а обычные файлы при одновременной записи молча теряют изменения.

**Next.js и TypeScript, интерфейс на Tailwind CSS.** Панель руководителя — часть того же
приложения. Набор компонентов — собственные лёгкие примитивы (`components/ui/`); готовая
библиотека (shadcn и подобные) не понадобилась.

**Ежемесячный обзор публикуется отдельным GitHub Issue.** Обычные задачи проще
автоматизировать, у них есть метки и понятное состояние «открыто — закрыто».

## Решено в обсуждении, но в концепцию ещё не внесено

Требует подтверждения при следующем обновлении документов.

**Репозитории проектов — открытые (публичные).** Это не косметика, а условие
работоспособности: на бесплатном плане GitHub защита ветки с обязательными проверками
доступна только в открытых репозиториях. Размещение в открытом доступе признано допустимым.
Важно: ранний документ `docs/видение/концепция.md` говорит о закрытых репозиториях — там это устарело.

**Платный план GitHub не покупаем, бесплатный доступ по программе GitHub Education
недоступен.** Из этого и следует решение об открытых репозиториях.

**Ограничений на передачу данных во внешний API языковой модели нет** — передавать можно
любые данные проекта. (Внешний сервис — тот, что настроен провайдером; сейчас provod.ai,
ранее предполагался Anthropic.)

**Провайдер языковой модели не зафиксирован; держим его сменным.** Конкретные модели ещё не
выбраны, поэтому привязываться к одному провайдеру нельзя: переход на Claude (Anthropic)
должен оставаться возможным в любой момент. Сейчас подключён provod.ai — российский
OpenAI-совместимый шлюз (ключ `sk_...`, оплата в рублях). Вызов модели изолирован в слое
`lib/llm/`, а разбор pull request от провайдера не зависит, поэтому смена провайдера — это
добавление одного адаптера, а не переделка. Более того, provod уже отдаёт модели Claude
напрямую по той же OpenAI-совместимой схеме, так что переход на Claude через provod возможен
вообще без нового адаптера — сменой `LLM_MODEL`. Важно: `детализированная концепция.md`
(разделы 8–9) пока называет провайдером Anthropic жёстко — формулировку нужно смягчить до
«провайдер не зафиксирован».

## Память проекта (этап 3)

Решено при реализации этапа 3.

**Оценка уверенности модели не хранится.** Механизм признан предварительной гипотезой, от
которой отказались: находка получает категорию и серьёзность, но не «уверенность». Раздел 4
`детализированная концепция.md` приведён в соответствие (поле убрано из модели данных). Если
понадобится — вернём отдельной колонкой через миграцию.

**Сопоставление находок между прогонами делает сама модель.** При новом коммите в промпт
кладутся прошлые находки этого PR и ответы студента; модель возвращает по каждой прошлой
находке актуальный статус (open / closed / dismissed / reopened) и список новых находок.
Эвристическое сопоставление по «отпечатку» (категория + файл + заголовок) отвергнуто как
хрупкое: переформулировка или сдвиг строк ломают совпадение.

**Объяснения студента разбирает модель.** Ответ студента (комментарий в PR) сохраняется и
передаётся модели; она сама решает, снимает ли объяснение замечание (→ dismissed). Ответ без
нового коммита обрабатывается через событие `issue_comment` и сверку на текущем head PR, без
создания нового check-run (проверка уже завершена, слияние разрешено — куратор совещательный).

**Хранилище — встроенный `node:sqlite`.** Ноль внешних зависимостей (Node 22+). Драйвер
помечен experimental, поэтому изолирован в `lib/db/`; замена — одна правка. Объёмные тексты
находок пока хранятся инлайн в SQLite, не отдельными файлами (масштаб мал; концепция это
допускает формулировкой «могут храниться отдельными файлами»).

## Панель руководителя (этап 5)

Подробности — `панель руководителя.md`.

**Две роли: `head` (руководитель центра) и `supervisor` (руководитель проекта).** Студенты
панелью не пользуются — они работают через GitHub. `head` видит все проекты и управляет
учётками и подключением; `supervisor` видит только назначенные ему проекты. Обеим ролям —
один и тот же интерфейс, ограниченный областью видимости, а не разные наборы виджетов.

**Вход — подписанный токен в httpOnly-cookie, пользователи в SQLite.** Пароли только хэшем
(PBKDF2). Без `AUTH_SECRET` панель открыта в разработке и закрыта в production (фейл-закрыто).
Первый `head` создаётся из `HEAD_LOGIN` / `HEAD_PASSWORD` при пустой базе.

**Таблицы с фактами вместо дашборда и «статуса внимания»** (2026-09-14). Первая версия
панели с KPI-плитками, графиками распределений, блоками «Требуют внимания» и «Нагрузка
руководителей» и трёхцветным статусом с порогами отвергнута пользователем как надуманная.
Из двух вариантов раздела 7 концепции выбран «показывать фактические данные без собственной
оценки»: одна сортируемая таблица проектов, страница проекта из списков (замечания, PR,
снятые, закрытые, разборы), досье. Приоритет — сортировкой по фактам (серьёзные открытые →
давность → последний разбор), решение — за человеком. Единственный график — мини-полоска
«разборы по неделям» в строке проекта, своим SVG; Recharts из раздела 8 отложен, пока нет
вопроса, на который отвечал бы график.

**Состояние проекта — `status`: `active` | `paused`; удаление — настоящее.** `archived`
убран (2026-09-14): по сути дублировал паузу. Миграция `user_version 4` переводит бывшие
`archived` в `paused`. Удаление проекта — каскадное (PR, разборы, находки, история, ответы,
назначения) с подтверждением вводом `owner/repo`; для завершённых проектов — пауза.
Переключатель паузы живёт в `/admin`, а не на главном экране — управление в одном месте.
Ранее: `status` заменил булев `connected` из схемы этапа 3 (миграция `user_version 3`).

**Полный CRUD в управлении; пароли меняет только руководитель центра.** Проекты: добавить,
переименовать (owner/repo — только пока не было PR, иначе рвётся связь с вебхуком), пауза,
удалить. Учётки: создать, изменить логин/имя, задать пароль, включить/отключить, удалить
(снимает назначения). Учётку `head` нельзя отключить или удалить; второго `head` не бывает.
Страницы «Аккаунт» нет. Смена пароля и отключение учётки отзывают все её сессии: токен
несёт `session_version` пользователя, несовпадение — отказ (миграция `user_version 5`).

**Замечания в PR, закрытых без слияния, не считаются открытыми.** Код не попал в основную
ветку; статус находки не меняем, но из счётчиков проекта исключаем и на странице проекта
показываем отдельной секцией.

## Куратор: правки при этапе 5

Три изменения поведения вебхука, без которых панель показывала бы неправду (2026-09-14).

**Разбираются только проекты, подключённые в управлении.** Раньше любой репозиторий с
установленным приложением создавался в памяти при первом PR; удалённый в панели проект
воскресал бы с чистой историей и без руководителя. Теперь незнакомый репозиторий вебхук
игнорирует целиком (без check-run — защита ветки для него не настраивается). Подключение
репозитория в `/admin` — обязательный шаг.

**Пауза отключает разбор.** Раньше пауза была лишь пометкой. Теперь PR проекта на паузе не
разбираются; чтобы пауза не блокировала слияние, обязательная проверка сразу завершается
`success` с пояснением «Проект на паузе — разбор не выполняется», комментарий не
публикуется. Что делать с накопленными замечаниями при возобновлении — не решено.

**Вебхук записывает состояние PR** (`pull_request.closed` → `merged` / `closed`; открытие и
новые коммиты → `open`). Без этого все PR в памяти оставались «open», и сценарий раздела 6
(«слияние без реакции на существенную находку») был неотличим от живого PR. Сверка по
комментарию берёт настоящее состояние PR из GitHub, поэтому ответ студента к слитому PR не
«открывает» его обратно. Сбой сверки по комментарию пишется в `analyses` как `error` (без
check-run — слияние он не блокирует). При ответе 500 запись о доставке снимается, чтобы
повторная доставка от GitHub не считалась дубликатом.

## Отвергнутые варианты

Рассмотрены и отклонены. Не предлагать заново без новых обстоятельств.

**Платная подписка GitHub (Team) ради закрытых репозиториев с защитой ветки.** Стоимость
считается за каждого участника организации; при нескольких десятках студентов это
существенные деньги на постоянной основе.

**Готовые ИИ-ревьюеры кода (CodeRabbit, Greptile, Qodo и подобные).** Они не умеют того,
ради чего система затевается: не ведут память проекта между проверками, не делают
содержательный обзор хода исследования и заточены на качество кода, а не на корректность
методики. Кроме того, тарифицируются за каждого разработчика, открывающего pull request,
то есть каждый студент — оплачиваемое место.

**Отдельный бэкенд на Python.** Машинного обучения на нашей стороне нет: мы обращаемся к
готовой модели по сети и разбираем данные GitHub. Отдельный язык и второй процесс дали бы
только усложнение.

**PostgreSQL.** Избыточен для этих объёмов данных и требует обслуживания отдельного
сервера.

**Хранение всего в обычных файлах без базы.** Состояние проекта изменяется из нескольких
мест сразу, и одновременная запись в файл молча теряет изменения.

**Готовые инструменты отчётности (Metabase, Grafana, Superset и подобные).** Хорошо рисуют
графики, но не показывают досье проблемы — фрагмент кода с подсветкой рядом с текстовым
объяснением, а это главное, ради чего панель существует.

**GitHub Discussions как канал общения со студентом.** У обычных задач полноценный простой
программный интерфейс, метки и понятные состояния; у обсуждений — нет.

**Дашборд в панели руководителя: KPI-плитки, графики распределений по категориям и
серьёзности, блок «Требуют внимания», «Нагрузка руководителей», трёхцветный статус внимания
с порогами.** Реализовано в первой версии этапа 5 и отвергнуто: руководитель действует по
конкретным замечаниям и PR, а не по агрегатам; числа есть в итоге таблицы; график без
вопроса, на который он отвечает, — шум. Единственное, что может вернуться, — распределение
находок по категориям для методической работы центра, отдельной страницей и после накопления
реальных данных.

**Статус проекта «архив».** Дублировал паузу; заменён настоящим удалением с подтверждением.
