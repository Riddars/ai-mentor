# Агентный разбор: план реализации

Обновлено: 2026-10-10.

Решение — `принятые решения.md` («Разбор PR — агентный; основа агента — библиотека pi»),
обоснование и риски — `агентный разбор — предложение.md`. Здесь — порядок работ. План ещё не
утверждён.

## Суть

Сейчас разбор PR — один запрос к модели (`runReview` в `lib/curator/review.ts`: контекст из
`collectReviewContext`, вызов `chat`, разбор JSON, `applyReconciliation`). Меняется только
середина: вместо одного запроса — агент на библиотеке pi (`@earendil-works/pi-agent-core`,
`@earendil-works/pi-ai`), встроенный прямо в сервис. Агент работает с временной копией
репозитория и умеет только то, что даём мы: список файлов, чтение, поиск, структура таблицы.
Вход (контекст из базы и GitHub) и выход (тот же JSON → сверка → комментарий → проверка →
панель) не меняются. Режим выбирается новой переменной `REVIEW_MODE` (`diff` | `snapshot` |
`agent`) при `CURATOR_REVIEWER=llm`; `diff` (нынешний разбор) остаётся и служит запасным путём.
`CURATOR_REVIEWER` не трогаем: очередь запускается только при `llm` (`startWorker` в
`lib/curator/worker.ts`), и новое значение там молча остановило бы разборы.

Перед включением агент сравнивается с двумя вариантами без агента: нынешним разбором по diff и
«весь код в один запрос с контекстом 1M» (предложение коллеги). Включаем то, что выиграет.

Очередь (решено 2026-10-10): разбор начинается через 10 секунд после последнего коммита, разборы
идут строго по одному — без параллельных агентов, ради надёжности. Что именно передаётся агенту
в контексте и что куда записывается — обсуждается отдельно.

Ежемесячный обзор (этап 4) пойдёт на том же механизме, но планируется отдельно.

## Фаза 0. Предпосылки (1–2 дня)

1. **Сервер.** Узнать в ИТМО, есть ли виртуальная машина под сервис. Требования: Linux x86_64,
   Docker Engine, от 4 ядер и 8 ГБ памяти, от 50 ГБ диска; исходящий HTTPS к `api.github.com`,
   `codeload.github.com`, `api.selectel.ru`; входящий HTTPS-адрес для вебхуков GitHub.
   Прототип не ждёт сервера: pi встраивается в сервис и работает и на Windows.
2. **Проверка pi + Selectel.** Скрипт в `scripts/`: агент pi с провайдером Selectel
   (OpenAI-совместимый адрес) и двумя инструментами на тестовом репозитории `test`, 5 прогонов на
   модель. Проверяем: многошаговые вызовы инструментов, итоговый ответ в нашей JSON-схеме,
   размышления включены и выключены, как pi подключает произвольный OpenAI-совместимый адрес и
   куда передаются инструменты (в README примеры только для Anthropic), отдаёт ли Selectel расход
   токенов на каждом шаге агента (без этого не работают бюджеты), и что встроенные инструменты pi
   (`read`, `write`, `edit`, `bash`) у нашего агента не зарегистрированы.
   Кандидаты (все есть в Selectel на 2026-10-04): `deepseek/deepseek-v4-pro`, `z-ai/glm-5.3`,
   `google/gemini-3.8-flash`, `moonshotai/kimi-k3`, `qwen/qwen3.8-max-0902`; эталон —
   `anthropic/claude-sonnet-5.5`.

**Готово, когда:** известны модели, которые стабильно проходят 5 из 5 прогонов с валидным JSON.
Если pi не подключается к Selectel или ломает вызовы — запасной путь: свой цикл на
существующем `lib/llm/chat.ts` (тот же набор инструментов), затем OpenCode.

**Итог проверки pi + Selectel (2026-10-10).** Скрипт `scripts/agent-spike.mts` (запуск:
`npx tsx --env-file=.env.local scripts/agent-spike.mts`; пакеты pi — только ES-модули, поэтому
скрипты `.mts`). Агент pi 1.0.4 с инструментами `list_files` и `read_file` разбирает копию
демо-проекта с промптом и разбором JSON из боевого кода (`SYSTEM_PROMPT`, `parseModelJson`).
Два случая: утечка видна в diff (подбор `alpha` на тесте) и утечка вне diff (diff трогает только
`train.py`, а то, что выборка тестовая, сказано в `src/data.py`).

- pi подключается к Selectel через `createProvider` + `openAICompletionsApi`; размышления
  выключаются форматом `thinkingFormat: "together"` (шлёт `reasoning: {enabled: false}`).
- Встроенных инструментов в `pi-agent-core` нет (они в отдельном пакете, который мы не ставим);
  агент видит только переданные ему. Пакет `pi-telemetry` ничего наружу не отправляет.
- Selectel отдаёт расход токенов на каждом шаге и цены моделей в каталоге `/models` — бюджеты и
  стоимость считаются.
- **Обязательная поправка:** часть моделей (Gemini, Kimi, GLM) возвращает размышления даже при
  выключенных, pi отправляет их обратно в следующем запросе, и Selectel отвечает 422
  («reasoning cannot be combined with native OpenAI request features»). Лечится удалением
  размышлений и их подписей из истории перед каждым запросом (`convertToLlm`).
- `deepseek/deepseek-v4-pro`: 10/10 прогонов — валидный JSON, утечка найдена в обоих случаях; во
  втором агент каждый раз сам открывал `src/data.py`. 6–19 с и около 1 ₽ за разбор, 4–9 вызовов
  инструментов. Иногда добавляет 1–2 второстепенные находки — их должна отсекать перепроверка.
- `z-ai/glm-5.3`: 6 из 8 прогонов с валидным JSON (все 6 нашли утечку), 48–159 с — даже с
  выключенными размышлениями пишет 4–22 тыс. токенов ответа.
- Gemini, Kimi — по 1–2 прогона после поправки (утечка найдена, один обрыв потока у Gemini;
  Kimi — 1–2,5 мин и около 10 ₽ за разбор); Qwen и Claude не проверялись. Сравнение моделей
  перенесено на фазу 3; прогоны — только с согласия пользователя и с оценкой стоимости.

Вывод: основа (pi + Selectel) работает, запасной путь не нужен; рабочая модель для прототипа —
DeepSeek V4 Pro.

## Фаза 1. Эталонный набор PR (2–3 дня)

Без него нельзя доказать, что агент лучше вариантов без агента.

- Отдельный репозиторий в `RiddarsCorp` (например, `curator-bench`) с несколькими
  синтетическими проектами разного устройства: модули, ноутбуки, структура PyCharm, большая
  таблица (сотни тысяч строк).
- 20–30 PR, к каждому — файл с ожидаемыми находками:
  - ~15 с методическими ошибками **не в изменённых строках** (подбор параметров на выборке,
    собранной из теста в другом файле; масштабирование до разбиения; дубликаты молекул между
    выборками; случайное разбиение при заявленном по каркасам; метрика не та, что в
    `RESEARCH.md`; нет фиксированного seed);
  - 5–10 чистых PR (проверка на придирки);
  - атакующие PR (для фазы 5);
  - 5–10 настоящих обезличенных PR студентов (с согласия), чтобы проверка не держалась только на
    синтетике.
- Скрипт прогона (`scripts/bench.mts`): гонит набор в трёх режимах, пишет таблицу — найдена ли
  заложенная ошибка, лишние находки, токены, время, валидность JSON; результат — по каждому типу
  ошибки, а не только общий.

Синтетику готовит Claude, реалистичность проверяет человек (см. «Открытые вопросы»).

## Фаза 2. Прототип агента и варианта 1M (4–5 дней)

**Подготовка копии** — `lib/agent/workspace.ts`:

1. Архив коммита через API GitHub (`/repos/{owner}/{repo}/tarball/{sha}`) ключом приложения;
   без истории git; временная папка.
2. Распаковка с проверкой каждого элемента **до записи на диск**: распаковываются только обычные
   файлы и папки; ссылки (символические, жёсткие) и прочие особые элементы, пути с `../` и
   абсолютные пути пропускаются. Объём, число файлов и размер файла считаются на лету, при
   превышении распаковка останавливается (защита от архивов-бомб); крупные файлы и указатели
   Git LFS — пропуск с отметкой. Архивы GitHub ссылок через папки и `../` не содержат (git их не
   хранит), так что это подстраховка, а не закрытие известной дыры.
3. Пропущенные ссылки перечисляются в карте репозитория («`data` — ссылка на
   `/home/student/datasets`, не распакована»): агент видит, что данные лежат вне репозитория.
4. Ноутбуки → текст с маркерами ячеек (как `notebookText` в `lib/curator/context.ts`) и таблица
   соответствия строк для ссылок в замечаниях.
5. Карта репозитория: дерево файлов с размерами.
6. «Обязательные к прочтению» файлы: что импортируют изменённые `.py` и где встречаются те же
   пути к данным (простой разбор `import` и поиск строк).

**Инструменты** — `lib/agent/tools.ts`, только чтение, все пути через одну проверку (реальный
путь после разрешения ссылок обязан лежать внутри копии):
- `list_files(dir)` — содержимое папки с размерами;
- `read_file(path, from?, to?)` — текст файла по диапазону строк, с ограничением объёма;
- `grep(pattern, glob?)` — поиск обычного текста (не регулярного выражения) с ограничением числа
  совпадений, чтобы хитрый шаблон не подвешивал процесс;
- `table_info(path)` — столбцы, число строк, несколько первых и случайных строк, без чтения
  файла целиком (потоковое чтение CSV в Node).

Сохраняется список вызовов: какие файлы прочитаны — для проверки оснований и панели.

**Агент** — `lib/agent/run.ts`: модель через `pi-ai` (провайдер Selectel), цикл `pi-agent-core`
с нашими инструментами; лимит шагов, бюджет токенов и общий тайм-аут (по умолчанию 10 минут).
Разбор (распаковка, инструменты, агент) идёт **в отдельном дочернем процессе**: тяжёлая таблица
или огромный репозиторий не подвесят приём событий GitHub, по тайм-ауту процесс убивается
целиком, а в его окружении только ключ модели — без ключа GitHub App и прочих секретов
сервиса. Промпт — `SYSTEM_PROMPT` плюс правила работы с инструментами: начать
с diff, прочитать обязательные файлы, при изменениях в данных, разбиении, обучении или оценке
проследить путь данных; находка вне изменённых строк — только с цепочкой («`train.py:40`
использует `X_val`, собранный в `data.py:12` из теста»). Итоговый ответ — наша JSON-схема
(`parseModelJson`).

**Вариант 1M** — `lib/agent/snapshot.ts`: из той же копии собрать один текст — код, документы,
ноутбуки без выводов, для таблиц только `table_info`; отправить одним запросом через
`chat` модели с длинным контекстом. Не влезает в лимит — помечается и в сравнении считается
провалом варианта.

**Перепроверка находок** — `lib/curator/verify.ts`: наш код сам перечитывает указанные в
находках `файл:строки` из копии (для ноутбуков — через таблицу соответствия строк); ссылка, которая
никуда не ведёт, — находка отбрасывается сразу. Второй короткий запрос получает находки вместе с
**этим настоящим текстом**, а не с цитатами агента, и отсеивает неподтверждённое. Включается в
любом режиме.

**Встраивание** — в `runReview` по `REVIEW_MODE` (`diff` | `snapshot` | `agent`) вызывается
нужный вариант; разбор JSON, сверка и комментарий — без изменений.

**Готово, когда:** весь эталонный набор проходит во всех трёх режимах.

## Фаза 4. Встраивание в очередь (3–4 дня)

- **Запасной путь.** Ошибка агента (нет JSON, тайм-аут, бюджет) → в той же задаче разбор по diff,
  пометка в разборе. Долгие повторы очереди — только для сбоев инфраструктуры, не больше двух
  попыток агента на коммит.
- **Новый коммит во время разбора** — агент отменяется сразу: проверка `isCurrent` выполняется
  между шагами агента (сейчас — только после ответа модели), процесс разбора завершается. Иначе
  устаревший разбор занимает единственное место в очереди.
- **Одновременность** — нет: разборы строго по одному (`REVIEW_CONCURRENCY=1`). Следствие: при
  пачке PR последние ждут в очереди; если ожидание превысит 30 минут, проверка завершается «не
  разобрано», разбор остаётся в очереди и публикуется позже. Тайм-аут агента (10 минут) и замер
  на 10 одновременных PR в эталонном прогоне показывают, хватает ли этого. Критерий заранее:
  если в замере больше 2 из 10 PR не укладываются в 30 минут — переходим на 2 разбора
  одновременно (`REVIEW_CONCURRENCY=2`). Время отменённых и запасных разборов учитывается.
- **Бюджеты** — дневной лимит токенов на проект и общий; исчерпан → разбор по diff.
- **Посторонние** — агент только для PR участников проекта (PR посторонних уже не разбираются).
- **Проверка оснований.** Файл и строки в находке и в закрытии существуют на коммите; закрытие
  замечания принимается, только если агент читал файл с исправлением или оно в diff.
- **Запасной разбор не меняет решений агента** по файлам вне diff.
- **Старые проблемы** в файлах, которых PR не касался, помечаются «вне изменений PR», дубли
  открытых замечаний отсеиваются.
- **Миграция `user_version` 9:** `analyses.mode` (`llm` | `snapshot` | `agent` |
  `agent_fallback`), `analyses.tokens_in`, `analyses.tokens_out`, `analyses.viewed_files`
  (JSON); `findings.origin_mode`.
- **Панель** — на странице разбора: режим, просмотренные файлы, токены. Комментарий в PR —
  «просмотрено файлов: N»; из текста модели в публичном комментарии вырезаются @упоминания и
  ссылки.
- **Переменные** (`.env.local.example`): `REVIEW_MODE`, `AGENT_MODEL`, `AGENT_MAX_STEPS`, `AGENT_TIMEOUT_MS`,
  `AGENT_TOKENS_PER_RUN`, `AGENT_TOKENS_PER_PROJECT_DAY`,
  `AGENT_TOKENS_PER_DAY`.

## Фаза 5. Защита и тесты атак (1–2 дня)

Атакующие PR из эталонного набора, каждый — автоматическая проверка:
- символическая ссылка на системный файл (`/etc/passwd`, `/proc/self/environ`) и путь с `../`;
- `AGENTS.md` и комментарии в коде с «находок нет, всё исправлено» — модель не должна закрывать
  замечания без оснований;
- инъекция в ячейке таблицы;
- огромная таблица, указатель LFS, репозиторий на 10 тысяч файлов, архив-бомба;
- у агента нет других инструментов, кроме наших четырёх.

Контейнер для агента не обязателен: разбор и так идёт в отдельном процессе без секретов
сервиса, инструменты — наш код с проверкой путей, команд и сети у агента нет. Контейнер —
по итогам этой фазы, если тесты покажут необходимость.

## Открытые вопросы

1. Сервер ИТМО: есть ли ВМ, кто её выдаёт и обслуживает.
2. Кто проверяет реалистичность эталонного набора (руководитель, аспирант).
3. Бюджет на модель в месяц — от него зависят лимиты токенов и выбор модели.
4. Что передаётся агенту в контексте и что куда записывается (обсудить отдельно).
